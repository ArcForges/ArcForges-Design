# Error catalogue

Every failed call returns `arcforges.foundation.v1.ArcError` with:
- `category` (`ErrorCategory`) and `code` (the snake_case code below);
- `message_key` = `error.<category>.<code>`, for example `error.state.not_found`;
- `retry` (`RetryAdvice`) and `effect` (`EffectCertainty`);
- `correlation_id`;
- the `details` listed here.

Method annotations name codes as `CATEGORY/code` ([README](README.md) §4). `tools/check_design.py` fails when a method names a code that is missing here.

**Implicit codes.** These can be returned by any method and are not repeated in method annotations:
- `INTERNAL/internal`;
- `RESOURCE/overloaded`;
- for local node methods: `STATE/node_stopping`;
- for AF-CTR-06 `FileService.ReadFile`, `SearchFiles`, `ListDirectory`, `PlanRemoval`, and `WorkspaceService.RegisterWorkspace` and `GetWorkspace` only: `CONFLICT/file_changed` for an observed checked-identity or in-call change that prevents a safe result ([06a §4](../architecture/06a-node-files.md#4-permissions-and-conflicterror-contract)). These are bounded omissions in the published `450.1` annotations, with no wire change; each Fleet counterpart forwards the error inside the verified signed node response, not as a fabricated outer native error. Cursor invalidation keeps `VALIDATION/invalid_cursor` as specifically required;
- for the AF-CTR-06 FileService/WorkspaceService operations and their explicitly routed Fleet counterparts only: `RESOURCE/too_large` for the write, edit, path and plan resource maxima in [06a §4](../architecture/06a-node-files.md#4-permissions-and-conflicterror-contract), with the actual applicable limit. This narrow annotation erratum includes the outer Fleet refusal omitted from the published `1.0.0-ci.450.1` method comments; it does not change the wire envelope or make every field-validation failure a resource error;
- for cloud methods: `AUTHENTICATION/unauthenticated`, `RESOURCE/rate_limited`, and `STATE/not_activated` while the method's surface is not activated in production ([10](../architecture/10-cloud.md) §8);
- for a mutation deduplicated under a command receipt: `CONFLICT/command_id_reused` ([README](README.md) §6). The Go center answers it for every method it serves under a receipt, among them `ApproveDeviceCode`, `ReportNodeInfo` and `SignOutNode` (AF-CTR-04, Cloud #130 and #134), whose annotations do not name it.

**Effect rule.** A mutation that fails before any durable change returns `DID_NOT_HAPPEN`. When the outcome is uncertain (for example a peer or cloud call timed out after sending), the method returns `UNKNOWN` with `retry.mode = RECONCILE` and the read operation to call (or `SAME_COMMAND`, or `NEVER`, where no read can be made; see below). A retry of a command under a receipt with the same `command_id` is safe (AD-0004).

**UNKNOWN never pairs with AFTER_TIME** (amended 2026-10-30, AF-CTR-03). The Contracts rule `arcError` (cohort `1.0.0-ci.416.1` and every generated validator) rejects an `ArcError` whose `effect` is `UNKNOWN` and whose `retry.mode` is `AFTER_TIME`, and the rule `retryAdvice` requires a reconciliation operation exactly when the mode is `RECONCILE`. A row whose effect can be `UNKNOWN` therefore advises `AFTER_TIME` only together with a known effect; together with `UNKNOWN` it advises `RECONCILE` and names a read operation that needs no ID the lost reply would have carried; where no such read exists it advises `SAME_COMMAND` for a method that is idempotent by `command_id`, and otherwise `NEVER`. `INTERNAL/internal` is the exception: its cause is unknown, so with `UNKNOWN` it advises `NEVER` for every method, idempotent or not (its row below). `NEVER` with `UNKNOWN` advises against an automatic resend; a caller may still resend a command under a receipt, which replays the receipt or executes the command. A command that carries a `command_id` under a receipt may be resent with the same `command_id` (AD-0004); a one-use call (a refresh, a sign-in or step-up completion, anything that presents a credential that may already be spent) is not resent after an unknown outcome: the client signs in again or reads the state it needs. `effect` describes this delivery, not the command. `RESOURCE/overloaded` is `DID_NOT_HAPPEN` for this delivery even when the command may have committed: the center answers it for a duplicate `CompletePasskeyRegistration` whose first execution still holds the flow attempt, and for a duplicate whose receipt lookup failed after the first delivery committed; the retry (`retry_at`), with the same bytes and `command_id`, replays the stored receipt. Any other duplicate of a committed command is answered with the stored receipt at once, once its credential check passes (a duplicate that carries the credential the first delivery revoked is refused before its receipt is read: a native bearer at the ingress as `auth.credential_revoked`, a browser cookie session as `auth.unauthenticated`; see the ingress table below), and a concurrent duplicate of another receipted write waits for the first delivery and replays its receipt. An unanswered `COMMIT` of the call's own effect write is `INTERNAL/internal` with `UNKNOWN` and `NEVER`, never `overloaded`.

**Reply rules** (amended 2026-10-30, AF-CTR-03). Every refusal carries valid foundation messages as its details: every `StateFailure` carries both `state` and `reason` (a row that names only `state.resource` still sets `state` to the object's kind and `reason` to the code); a resource is named only with a real 16-byte, non-zero ID, either the ID the caller named or the caller's own object, never another account's; every `AFTER_TIME` refusal carries `retry_at` (an instant; the center uses one second plus jitter when it has no better time); every `RECONCILE` refusal names its read operation. A refusal never carries an e-mail address or any other personal data of a command's receipt.

**Delivered against target** (2026-10-30; restated 2026-11-03). The Cloud center as AF-CTR-03 delivered it (Cloud #118, #120, #121, #122, #123, #124 and #127) answered an unexpected failure with `AFTER_TIME` and `UNKNOWN`, the pair the Contracts rule `arcError` rejects, had no field for a reconciliation operation, and its own test check (`arctest.Violations`) exempted `INTERNAL/internal` from that rule. Cloud #129 (merged at `602705f`, 2026-11-03) delivered the alignment: `INTERNAL/internal` with `UNKNOWN` answers `NEVER`, the refusal type carries the reconciliation operation (set exactly when the advice is `RECONCILE`; a refusal that breaks the rule `retryAdvice` panics in its constructor), and the exemption is removed. No identity-surface refusal advises `RECONCILE` yet; the later parts' refusals use the field. The Contracts fixture `af-con-01-error-catalogue.json` (source commit `78f0f5a`) still lists `AFTER_TIME` for the four rewritten rows (`peer_unreachable`, `cloud_unreachable`, `provider_error`, `INTERNAL/internal`); it is regenerated from this catalogue in the Contracts follow-up window before AF-PROD-01 (AF-CTR-05; not in AF-CTR-04's Contracts parts), with an explicit pair form (`AFTER_TIME` with `DID_NOT_HAPPEN`; `AFTER_TIME` or `SAME_COMMAND` with `HAPPENED`; `RECONCILE`, `SAME_COMMAND` or `NEVER` with `UNKNOWN`), because its retry-mode and effect arrays are independent and would recreate the invalid pair. `tools/check_design.py` reads every row of this catalogue and fails a row whose effect can be `UNKNOWN` when a clause of its retry advice (split at `;`) names `AFTER_TIME` without naming `DID_NOT_HAPPEN` or `HAPPENED`, or names `UNKNOWN`; it is a word-level check and cannot tell which effect such a clause pairs `AFTER_TIME` with.

**AF-CTR-06 file outcomes (target).** The specific file, workspace and removal methods, limits, authorization and effect/retry pairs are specified by [06a](../architecture/06a-node-files.md) §§3–6. A delivered file mutation whose answer was lost returns `STATE/node_unreachable`, `UNKNOWN`/`SAME_COMMAND`, and may be resent only with the same command ID and exact bytes; the node journal must never repeat an uncertain effect. When that journal cannot prove the effect, it returns `EXECUTION/operation_failed`, `UNKNOWN`/`NEVER`, reason `file_outcome_unknown`, and exposes the pending status for HUMAN resolution. No `UNKNOWN` is paired with `AFTER_TIME`.

## Center ingress transport statuses (added 2026-10-28, AF-CTR-02)

The C# Cloud host's ingress pipeline (delivered; Cloud `faaffea`, `src/ArcForges.Cloud/Ingress/IngressPipeline.cs` and `GrpcWebFraming.cs`) refuses some calls before any handler runs, and the Go center ports it with the same bytes (delivered 2026-10-28; AF-CTR-02, Cloud #112 at `5175684`, `docs/center.md`). Those refusals are transport statuses, sent trailers-only: to binary gRPC-Web, HTTP 200 with one trailer frame carrying `grpc-status` and a `grpc-message` holding the refusal code, percent-encoded; to native gRPC (self-hosted direct clients only), the trailers-only `HEADERS` of gRPC over HTTP/2 with the same status and code. They carry no ArcError detail and no reply message; the category column below only classifies the code (the center uses it for metrics labels). Plain HTTP refusals come earlier still: `404` for a non-canonical or unknown path, `405` for a method other than POST, `415` for a wrong media type or content encoding. The Go center additionally admits binary gRPC (not only gRPC-Web) for self-hosted direct clients, through the same registry, bounds and refusals; the hosted Worker forwards gRPC-Web only. Every other ArcError is a domain refusal: the call completes with gRPC status 0 and carries the ArcError and the correlation ID in its reply. Signatures and digests cover the transmitted bytes, never a re-encoding ([AD-0021](../decisions/AD-0021-central-access-go-center.md) §10, V-N07).

| Ingress refusal | gRPC status | ArcError category |
|---|---|---|
| Unregistered method (`grpc-message` `unimplemented`) | 12 `UNIMPLEMENTED` | — |
| `auth.unauthenticated` | 16 `UNAUTHENTICATED` | `AUTHENTICATION` |
| `auth.token_expired` (a known native bearer whose access token, or whose session's absolute lifetime, has expired; the client refreshes, and signs in again when the refresh is refused) | 16 `UNAUTHENTICATED` | `AUTHENTICATION` |
| `auth.credential_revoked` (a known native bearer whose session, device or installation is revoked; the client signs in again) | 16 `UNAUTHENTICATED` | `AUTHENTICATION` |
| `perm.resource_denied` | 7 `PERMISSION_DENIED` | `AUTHORIZATION` |
| `validation.invalid_request` (malformed request or metadata) | 3 `INVALID_ARGUMENT` | `VALIDATION` |
| `validation.invalid_request` (body over the method's bound) | 8 `RESOURCE_EXHAUSTED` | `VALIDATION` |
| `state.stale_generation` | 9 `FAILED_PRECONDITION` | `STATE` |
| `dependency.unavailable` | 14 `UNAVAILABLE` | `EXECUTION` |

The `auth.token_expired` and `auth.credential_revoked` rows were added on 2026-10-29 with AF-CTR-03 part A1a (Cloud #118 at `d4e1110`); only the Go center produces them, while the C# host answers every credential failure `auth.unauthenticated`. On every call of a method that requires a session, the center verifies the native bearer or browser cookie against its store before any handler runs; an anonymous method (for example `RefreshSession`) reads no credential. A native bearer that is known but expired or revoked gets its own code; a browser cookie session that is expired, idle past its limit or revoked is answered like an unknown credential (`auth.unauthenticated`), because a browser signs in again in either case.

**Built refusals the annotations do not name yet** (added 2026-11-05, AF-CTR-04; for the Contracts follow-up window, not contract facts until it takes them):
- `RESOURCE/quota_exceeded` (`limit_name` `max_nodes_per_account`) on `CompleteNodeSignIn` and `PollDeviceAuthorization`: Enroll enforces the node cap there (Cloud #132, #134), and their annotations do not name the code.
- `STATE/invalid_state` (`state.state` `signed_out`, `state.reason` `credential_store_unavailable`) on the node's `AccountService.SignOut` while its secret store or link file cannot be read; both sign-out forms then change nothing (ArcForges #69). `SignOut` annotates `STATE/not_signed_in` only.
- `ApproveNodeSignIn` and `ApproveDeviceCode` refuse an absent `approve` (`VALIDATION/invalid_argument`, `approve: required`); the contract has no `validate:` rule on the field (a center rule).
- `NodeEnrollmentServiceApproveNodeSignInValue.redirect_url` of a denial is `<redirect_uri>?error=access_denied&state=<state>`; the field comment says "with code and state".
- `CompleteNodeSignIn`'s `state:` annotation names `APPROVED -> COMPLETED | REVOKED`; the center also moves `COMPLETED -> REVOKED` on a reuse, as the `NodeSignInState.REVOKED` comment says ([state machines](../state-machines/README.md) SM-SIGN-IN).

The Worker's own domain replies (`not_activated`, `rate_limited`; Cloud `docs/cloud-ingress.md`) carry `ArcError.correlation_id` but no `ResponseMeta`. A generated validator that checks such a reply as a response rejects it (the validators require `Meta`), although the `ArcError` is valid; a client reads the `ArcError` as the refusal. This is a known exception until the Contracts follow-up window before AF-PROD-01 (AF-CTR-05) decides it.

## Center-routed calls (AF-CTR-05 target; added 2026-11-05)

The foundation `ErrorCategory` has no `UNAVAILABLE` value, so the `UNAVAILABLE` refusals that [AD-0021](../decisions/AD-0021-central-access-go-center.md) §11 and R-CTR-006 named before this catalogue had codes for them are restated with the existing categories (Plan decisions Q2 and PN-11; the AD-0021 §11 amendment of 2026-11-05). Nothing in this section is built yet.
- **New call for an offline node** (no channel in this center process, or the process does not hold the hub lease): `STATE/node_offline`. The center queues nothing.
- **Network loss, a closed or replaced channel, or a lost or unverifiable result while a call is in flight:** `STATE/node_unreachable`, with the pairs of its row. A revoked node's later calls are `STATE/not_found`, the same answer as for an unknown node.
- **Center restart or deploy while a call is in flight:** the call ends without an ArcError reply, as a transport failure. The caller treats the outcome as `UNKNOWN` and resends a mutation with the same `command_id` and the same bytes; the node's deduplication replays the outcome. At start the center moves its routing records that were not final to `UNKNOWN`.
- **Database outage:** `RESOURCE/overloaded` (`AFTER_TIME` with jitter, `DID_NOT_HAPPEN`), because authorization reads the store and a routed mutation writes its routing record before delivery; a failure before any handler runs is the ingress status `dependency.unavailable` (gRPC 14). Open channels stay, and node-accepted work continues.
- **Lapsed or missing entitlement:** `ENTITLEMENT/feature_not_entitled`, after authentication, ownership, the controls and the audit.

gRPC status 14 `UNAVAILABLE` stays a transport status only (the ingress table above); no ArcError carries an `UNAVAILABLE` category.

## AF-CTR-06 file refusal reasons (target)

For these two errors `state.state` is `file`, with exactly one of the following `state.reason` values. Each method still permits only its own catalogued error codes (and the narrow implicit cases above); membership in a reason set never widens a method's error set.

- **`CONFLICT/file_changed`:** `workspace_root_changed`, `workspace_path_conflict`, `workspace_identity_conflict`, `workspace_registration_changed`, `legacy_snapshot_changed`, `file_identity_changed`, `directory_identity_changed`, `directory_changed`, `root_changed`, `file_changed_while_reading`, `hash_mismatch`, `expected_absent_conflict`, `parent_identity_changed`, `planned_tree_changed`. Use `hash_mismatch` for a new whole-content hash precondition failure; do not invent additional hash, identity or replacement aliases.
- **`STATE/file_access_denied`:** `file_access_denied`, `file_hard_link`, `file_metadata_unavailable`, `path_link_or_special`, `mount_crossing`, `canonical_path_unavailable`, `case_semantics_unavailable`, `directory_entry_invalid`, `directory_enumeration_failed`, `directory_enumeration_unavailable`, `file_guard_unavailable`, `path_enforcement_unavailable`, `identity_filesystem_unavailable`, `identity_handle_unavailable`, `identity_unavailable`, `identity_unavailable_or_reparse`, `procfs_unavailable`, `root_not_supported`.

These are public, non-secret causes, not raw exception strings, paths, native messages or an extensible `native_N` family. The node normalizes an otherwise unclassified native access failure to `file_access_denied` at the API boundary. A missing object or wrong required object type uses `VALIDATION/path_not_found`; malformed caller input or a forbidden root operation uses the applicable validation error. A previously verified identity that changes before effect uses `CONFLICT/file_changed` where that method permits it, never a false permission denial. Internal WIP exception names are not themselves delivered API emitters.

A write-exclusion guard required by 06a §2a that cannot be established still returns `RESOURCE/enforcement_unavailable` before effect; the access-reason set cannot bypass that specific rule. Failure after an effect may have begun follows the actual UNKNOWN journal outcome, not one of these DID_NOT_HAPPEN refusals. An unknown file operation uses only `EXECUTION/operation_failed`, UNKNOWN/NEVER with `state.state=file` and `state.reason=file_outcome_unknown`; an authorization error cannot stand in for that uncertainty. A `regex_scalar_boundary` refusal after scanning still requires the signed actual scan observation. Producer and consumer execution, native classification and audit checks remain mandatory; this vocabulary alone proves none of them.
