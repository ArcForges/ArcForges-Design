# Node store and retention

[Target SQLite DDL](node-store.sql) specifies V2's normalized persistence and is executable for structural validation. It is not an upgrade script. Actual Node schema is version/min-reader **15** at the audited source. The future migration appends new steps; it never edits applied 0001–0015. See [migrations](migrations.md) and the [source audit](../research/runtime-audit.md).

State integer mapping is exactly the corresponding protobuf enum: Sandbox 1 CREATING, 2 READY, 3 DELETING, 4 DELETED, 5 ERROR, 6 RECOVERY_REQUIRED; Run 1 STARTING, 2 RUNNING, 3 STOPPING, 4 DRAINING, 5 EXITED, 6 FAILED, 7 RECOVERY_REQUIRED. `payload_started` is 1 UNKNOWN, 2 NOT_STARTED, 3 CONFIRMED. Foundation effect certainty is 1 DID_NOT_HAPPEN, 2 HAPPENED, 3 UNKNOWN. Wire state UNSPECIFIED is rejected on writes. `limit_application.state` is persisted; resource readback must still be refreshed after recovery before enforcement is called effective.

## Durable mutation identity and compaction

The Node is the sole metadata writer. Durable business mutation/receipt/event updates share a transaction; native effects are coordinated by durable intent and post-effect reconciliation. Do not keep a SQLite write transaction open across a long network/native operation. Acquire the documented scope/ownership lease, persist intent, execute, then finalize or mark UNKNOWN. Concurrent starts and deletion take the same Sandbox gate. The transient terminal methods below are expressly excluded from this database path.

Create a cryptographically random 16-byte `owner_epoch` once when creating an owner store or its initial V2 durable-mutation namespace. It is a `foundation.Id` on the wire and a 16-byte BLOB in SQLite, not a timestamp or the Node event/Run-supervisor generation. `NodeService.Handshake` returns the current epoch. Every durable Node mutation carries that epoch in its explicit request field 100; the Node checks it before admitting an effect. A saved request keeps its original epoch across retries, reconnects and Node restarts. It is never silently rewritten using a newer handshake. A retired, missing or different epoch returns `CONFLICT/owner_epoch_retired` with no requested effect.

The receipt key is `(owner_id, owner_epoch, command_id)`. Canonicalization binds the method, owner epoch, target, effect-bearing fields and admitted configuration/grant/profile revisions. Compute its HMAC-SHA-256 using the epoch's protected key; store only the keyed digest and key reference, never the key or a bare low-entropy secret/input hash. Restoring the epoch requires the same protected key. The immutable method/keyed digest/aggregate identity prevents a conflicting replay after its response body is gone. A matching admitted request resolves the existing operation and cannot allocate a second Run or repeat a deletion. Preserve the original outcome/effect identity after Run or Sandbox detail retention has expired.

`resolved_utc` is set only for a definite settled outcome with known effect and no unresolved native/data ownership. `expires_utc` is the earliest allowed **response-body compaction time**, at least 24 hours after `resolved_utc`; it never expires the command key, keyed digest, target or effect identity. A compactor may clear `response_json` and set `response_compacted_utc` only after that boundary and after checking all referenced effects are resolved. ACCEPTED/UNKNOWN operations and any unresolved delete/transfer keep their full bounded reconciliation body with no compaction deadline. No routine sweep deletes active-epoch identities, and there is no routine purge API.

For a matching compacted receipt, **mutation replay** returns `STATE/receipt_compacted` together with the retained original aggregate reference, operation state and effect certainty; it does not reconstruct a successful response body or execute the request. `GetOperation` is instead a successful read of the retained `Operation`, with `response_compacted=true` and the original state/effect/aggregate. A different method/digest under the same key still returns `CONFLICT/command_id_reused`. `STATE/not_found` must never turn a known compacted operation into an apparently unused key. Clients display the retained result and request an explicit new user action when appropriate; they do not mint a fresh Start automatically.

Retain command identities for the entire admitted epoch. Epoch retirement is separately authorized **offline owner maintenance**, with exclusive store/control locks, no live Runs or transfers, no unknown effects, reconciled journals, and revoked remote enrollments/leases. It cannot be a scheduled retention action or an automatic response to disk pressure. Retirement is irreversible; a new epoch gets a new random identity/key and fresh remote authorization. Any subsequent offline removal of retired-epoch command rows must preserve the retired-epoch rejection boundary and all required history/reconciliation references. Retired epoch metadata is not deleted. Normal operation can increase its approved storage budget instead of retiring authority.

A complete coherent restore preserves the original epoch, protected key and **all** admitted command identities/effects. An older backup that omits post-backup commands cannot serve under that epoch merely because SQLite integrity passes: reconstruct and reconcile the missing history first, or remain in maintenance until the separate safe retirement/new-store procedure is authorized and its guards are satisfied. Creating a genuinely new store generates a new epoch, so saved requests for a previous store are rejected even if they use the same OS owner and command ID. Copying only the database without its consistent keys, owner records and receipt history does not create a ready Node.

## Terminal authority and operational storage

`RunService.AcquireTerminal`, `WriteTerminal`, `ResizeTerminal` and `DetachTerminal` use only a live RunSupervisor's bounded in-memory acknowledgement cache. They create no `command_receipt`, no durable per-frame event and no `GetOperation` result. Raw input, input-derived digests and the acknowledgement cache never enter the database, supervisor control files, audit, telemetry or support logs. Safe lease-acquisition/revocation metadata may be audited without frame content, frame fingerprints or durable input-command identities. The SQL receipt-method guard excludes these four canonical method names.

Terminal writer leases expire after 30 seconds unless renewed. Sequence high-water marks, request comparisons and acknowledgements exist only within the bounded live lease window. Missing/evicted/lost acknowledgements return `EXECUTION/terminal_ack_unavailable` with UNKNOWN effect and no automatic retry; `GetOperation` cannot recover them. Node restart invalidates leases and their acknowledgement authority; supervisor loss ends it. Reacquisition creates fresh authority but does not establish whether earlier input was delivered. Output epochs/segments may persist independently. A copied database therefore cannot revive terminal input authority.

Center identity/enrollment storage remains the existing protected credential store and guarded cloud-link/key files, reached through the fixed local-only `CenterControlService` adapter. Do not create a second plaintext SQLite authentication store. Preserve account/Center binding, credential generation, atomic replacement, protected key reference, interrupted-sign-in and sign-out/revocation certainty across migration. Its durable local control operations still use owner-epoch receipts; receipts contain only redacted flow/status/credential references. Cross-store effects use a durable control intent, the existing two-phase operational files and reconciliation, not an assumed atomic transaction across SQLite and the secret store. Disconnect disables future links while preserving a reconnectable credential; SignOut additionally ends local credential authority and reports unresolved remote revocation honestly.

## Capacity, deletion and acceptance

Retention defaults are engineering safety limits, not subscription tiers. Before accepting a new Run, grant, transfer or other effect, reserve bounded journal/receipt/WAL capacity for its completion and at least its required Stop, revocation or reconciliation workflow. The reserve is unavailable to new nonsafety mutations, output logs and response retention. Reject new nonsafety admission before this reserve is exhausted; never evict executable identities to make room. Existing matching receipt lookups and safety controls retain a reserved processing lane. Once an authorized safety operation has been admitted, repeated controls converge on its existing intent and readers inspect that operation rather than allocating unbounded new safety receipts. Failed native/storage writes still report their true effect; no design can reserve disk against arbitrary privileged host writes.

Requested deletion accounts for managed active use. A COMPLETE export with `closed_utc IS NULL` still holds use against Sandbox deletion until CloseTransfer or proven-safe expiry releases its snapshot and records `closed_utc`/`close_reason`; reading that snapshot does not hold the original source quiescent or block a new Run. COMPLETE remains the successful transfer outcome after closure, but reads then fail explicitly because the snapshot is no longer retained. Final ReadExport does not close it. Independently opened host file handles are outside the earlier owner's agreed protection scope, while ordinary OS access/identity failures still stop unsafe deletion.

AFV2-DATA-01 acceptance includes Start replay after 24-hour body compaction and Node restart with no second payload; conflicting replay after compaction; UNKNOWN body retention; insufficient-capacity refusal with existing Stop/revocation/reconciliation still available; stale epoch after new-store creation; coherent restore and refusal of a backup missing later identities; and no automatic epoch rotation. AFV2-CLI-02/AFV2-REC-01 include terminal window expiry, Node/owner loss, partial-write uncertainty, and a direct check that raw input and input-derived hashes never reach durable storage/audit. These are future implementation acceptance requirements, not execution results of this design specification.
