# Contract, runtime and data migration

## Published contract versus runtime retirement

The audit records the actual consumers and pinned cohorts. New `arcforges.sandbox.v2` and `arcforges.management.v2` namespaces describe V2; the existing `arcforges.local.sandbox.v1` remains DesktopPlatform ContentSandbox. Never reuse a v1 message/field number for a different meaning or repurpose ContentSandbox as CLI Sandbox Core.

**Stop consuming:** migrate ArcForges and Go Center to explicit V2 APIs and remove their obsolete runtime route/client registrations. **Document retirement:** mark old source schemas as retired for ArcForges V2 with their replacement and last consumer inventory. **Incompatible source deletion:** only after the consumer inventory proves no retained independent product needs the schema; use an explicitly new major namespace/package surface when incompatibility is unavoidable. Already published versions remain downloadable and unchanged; no registry unpublish/deprecation/delete action is authorized. Continued old packages are immutable distribution history, not a maintained V1 execution path.

The consumer cutover inventory includes ArcForges, Go Center, old C# Cloud, Web, DesktopPlatform, Mobile, AI, ArcScope, ArcSlate and ArcNotes. Do not force unrelated products to implement V2. Keep only shared APIs they actually use, remove ArcForges-specific obsolete consumers and build dependencies, and verify independent product compile boundaries in the designated venues.

2. Resolve or preserve all unknown file-operation receipts, quarantine entries, held native identities, recovery-generation floors and pending audits. A new schema must not discard them. If an unsafe unresolved operation prevents contraction, keep the migration checkpoint blocked, not a permanent old service route.
3. Create a consistent backup and manifest of owned paths outside arbitrary host mounts. Append expand migrations with V2 tables and migration receipts. Establish the initial random 16-byte owner epoch and its protected canonical-digest key exactly once, with a checkpoint that survives interruption. Historical V1 run/task records can be exported as read-only history with original IDs; they are never relabeled as V2 executions or admitted under that new epoch. 4. Start new Core against V2 tables with old execution APIs disabled. Test fresh install and schema15 upgrade. Preserve rollback to the pre-migration backup until acceptance; after a V2 mutation is admitted, any rollback/restore must preserve its owner-epoch command identities and effects or remain in maintenance. After irreversible contraction, binary downgrade alone is refused by min-reader.
5. Remove old Task/Attempt/queue/dependency/AI/cache/CAS/toolchain/LAN/mobile live tables and views through a forward contract migration, after receipts/journals are settled or copied to the retained reconciliation store and all runtime consumers removed. ### Owner-epoch and receipt migration rules

The V2 `owner_epoch` is independent of the host boot, Node event epoch, Run supervisor generation and Center enrollment. Node restart preserves it. All durable Node mutation requests carry it explicitly; clients retain it with the command ID and never substitute a newly observed epoch into an old saved request. Existing V2 stores migrating to a later schema keep the same epoch, protected HMAC key and complete immutable command identities.

Known response bodies may compact after their explicit `expires_utc` boundary, at least 24 hours after a known settled result. This migration never treats that field as permission to delete `(owner_id, owner_epoch, command_id)`, method, keyed request digest, aggregate or effect identity. ACCEPTED/UNKNOWN/unresolved operations keep their full reconciliation body. A compacted replay returns `STATE/receipt_compacted` with its retained original identity/effect; a stale owner epoch returns `CONFLICT/owner_epoch_retired`. Neither response starts another Run. Preserve these semantics through database pruning, upgrade, backup and restore.

A restore is coherent only when its metadata, owned records, protected key material and command history include every admitted effect for the restored epoch. An older backup missing later successful Start/Stop/config/file identities cannot serve under that epoch; a valid SQLite checksum does not repair the missing replay boundary. Reconstruct/reconcile the complete history first, or keep the Node in maintenance until a separately authorized offline retirement/new-store procedure satisfies the no-live-Run/no-unknown-effect guards. A genuinely new owner store uses a new random epoch, refuses all saved requests from the old store and requires fresh remote authorization. Never automatically rotate the epoch after corruption, key loss, response compaction or budget exhaustion.

Explicit epoch retirement requires exclusive store/control locks, no active or unresolved Runs/transfers, settled deletion journals, no UNKNOWN effects, and revocation of remote enrollments and client authority before issuing the new epoch. Keep retired epoch metadata so it cannot reactivate. There is no routine purge or epoch-reset API. Reserve receipt/journal capacity for the Stop, revocation and reconciliation of already admitted effects; stop new nonsafety admission before that reserve is exhausted. AFV2-DATA-01 owns real SQLite post-compaction/store-reopen, capacity-admission and incomplete-backup fixtures with only the explicitly permitted effect-counter callback. AFV2-CORE-02 owns actual settled Start replay after cold Node restart; AFV2-REC-01 owns live-owner recovery, real safety controls under saturation and restore guards around actual admitted effects. AFV2-CLI-01 owns saved-command/Handshake behavior; database fixture results cannot close these later integration gates.

### Operational credentials and transient terminals

The fixed V2 `CenterControlService` reuses the audited credential store, cloud-link/key files and sign-in state machine. Its migration preserves credential/account/Center binding, key identity, two-phase write recovery and unknown remote-revocation facts; it does not import plaintext credentials into Core SQLite or preserve the old general Node-v1/Task dispatcher. A receipt records only redacted flow/status identity. Cross-store state becomes ready only after the protected operational files and corresponding Core control intent agree.

Terminal Acquire/Write/Resize/Detach are transient supervisor-memory operations, excluded from durable command receipts. Migration or restore never carries their lease authority, input bytes, input-derived hashes, sequence acknowledgements or pending resize authority forward. Node restart requires fresh local acquisition; owner loss ends the old authority. Durable output segments can be retained independently, with byte cursors/gaps and no inference about earlier input delivery.

## Center schema 10 and 11

The last recorded deployment baseline is schema10 with narrow/Hello-only evidence; schema11 code includes the security-successor admission floor. The user's earlier external bootstrap/deployment remained deferred. **Appending 0012 is not itself a valid upgrade path.** Applied SQL checksums and 0011 safeguards cannot be deleted or edited. A dedicated V2 migration task must qualify source/runtime producer identities, the existing credential floor and restore safeguards, then supply a reviewed finite maintenance transition or an officially admitted successor that passes them.

Test three fixtures separately: fresh database, actually deployed schema10, and schema11 already applied. Document the source cohort, native/Go/Contracts compatibility, changed grants, backup, stale receipts, credential epoch, rollback/restore compatibility and exact migration order. An unproven provider authority boundary keeps activation blocked. No production data or credential is read by an agent as an expedient probe. See [Center store](cloud-store.md) for the target PostgreSQL model and exact migration constraints.

## Removal order and rollback

Retire disconnected desktop scaffolding and cancelled future configs first. Preserve the old critical executor only until both MXC profiles and resources are proven. Cut over new Core and local CLI, then the explicit Center methods and Web pages. Drain old consumers; remove old launchers, Task/Attempt/DAG/retry, file workspace routes, C# Center and dead dependencies. Finally contract live schemas and packaging inventories. Do not leave TODO implementations, disabled empty projects, a generic old dispatcher or a permanent feature-switched dual runtime.

Rollback before any newly admitted V2 effect restores the last accepted cohort and coherent database backup without rewriting history. After a V2 effect, an older backup alone is insufficient: retain/reconstruct every owner-epoch identity and reconcile any intervening effect before admitting work. Rollback after irreversible deletion additionally requires explicit restore and data-loss accounting; it never pretends newly created V2 data is readable by a V1 binary. A failed engine experiment blocks executor deletion. A failed data migration leaves service in maintenance and preserves backup/journal; it does not erase the database or rotate replay authority to make tests green.
