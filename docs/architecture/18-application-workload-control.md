## 2. The positioning

### 2.1 The owner's words

On 2026-10-19 the product owner wrote: *"ArcForges is a cross-platform, local-first application and workload control infrastructure that unifies resource coordination, process lifecycle management, policy enforcement, verifiable access restrictions, and operational diagnostics."* And: *"The operating system remains responsible for actual scheduling and security enforcement. ArcForges provides a coherent management, coordination, policy, and reporting layer over the mechanisms that each OS genuinely supports."*

**The study's reading, as one sentence the product can keep (not the owner's words):** ArcForges lets the owner write one policy per application or workload and turns it into operating-system mechanisms on each machine. For every program it launches or the owner adopts, it states what was asked, what the operating system actually enforces (per limit and per access dimension, at a stated strength, and against whom), what happened, and whether a limit the owner set caused a failure. For everything else on the machine, it observes and says so.

| Function (the owner's words) | What the owner gets | Mechanism family (never an ArcForges-built boundary) |
|---|---|---|
| Resource coordination | Applications, games and background work share the machine by the owner's priorities: the owner's own applications are never squeezed below the owner's own values to protect the owner's headroom; handed-over work yields, waits or asks | Admission, budgets and the root container ([03](03-resource-control.md)); job objects; cgroup v2 through the user manager; the cooperative family (§9) |
| Process lifecycle management | Launch, supervise, stop gracefully, restart services, and know which processes belong to an application | Tasks and attempts (M1); holders; transient units; kill tree; restart on the existing retry path (§7.4) |
| Policy enforcement | One per-application policy, written by a local HUMAN, realized per OS, refused when a REQUIRED part cannot be met | `PolicyDocument`; require → refuse (AD-0017 principle 4; R-RES-008, delivered for resources) |
| Verifiable access restrictions | Files, network, registry, IPC and process creation restricted **at launch** for compatible applications, GUI or not, with the realization read back and the escape cells stated | The backends of chapter 17 §5 (AppContainer and LPAC; the Linux view chain, Landlock and seccomp policy filters); vendor sandboxes reported as the package's |
| Operational diagnostics | Every failure under a configured limit or restriction gets a verdict and a cause that leads with the truth, "cannot tell" included | One diagnosis schema ([07](07-records-diagnosis-memory.md) §4) |

**The workloads** (the owner's list): AI agents and their commands; MCP servers and tool processes; compilers and background builds; native desktop applications; first-party ArcForges applications; third-party closed-source desktop software; media production and rendering applications; IDEs and background indexing services; compatible games and game launchers; long-running local services and utilities. A GUI application "is simply another native application workload with a graphical interface" (the owner, 2026-10-19). AI workloads stay the first family, the one release 1 is built for; they no longer define the product.

**What is new against release 1 is breadth, not a new kind of machine.** Release 1 already designs owner-directed resource control for any same-user process it launches ([03](03-resource-control.md) §2–§8 name no workload class), and the product definition already says the platform is general-purpose. The gaps are specific: no per-application identity; no limits on adoption; session-keyed owners; no per-task CPU cap contract; no per-limit status; batch defaults that harm interactive applications; no application-facing identity or grant service; over-claiming limit evidence; and confinement scoped to headless work.

### 2.2 "Your machine. Your rules.", bounded

The owner's own reading: *"This means that the machine owner determines what applications may access, how much resource capacity managed workloads may consume, when work should be admitted or deferred, and which policies are actually enforced."* And: *"Do not turn this into an unrealistic promise of controlling every process on every operating system."*

- **"Your rules":** the owner writes one policy per application or workload, and every launch or adoption ArcForges performs either realizes it or is refused with a reason. "Actually enforced" means the realized value read back from the operating system, never the number typed. This holds today for resource requirements of attempts (R-RES-008); for per-application limits, access, lifecycle and diagnosis it is direction, effective row by row.
- **"Your machine":** ArcForges runs as the user and never elevates at run time, so it **controls only what it launched or what the owner explicitly adopted** (and, from EX-15's holds stage and only by the owner's decision, what the owner held). It observes what a standard user can see and labels it. It never claims more than the operating system enforces. The phrase "local workload control infrastructure" is accurate only with the qualifier "launched or adopted" ([17](17-delegated-execution.md) §16), and is used with it.

### 2.3 Against whom: the promise levels

| Promise | Holds against | Where | How it is obtained |
|---|---|---|---|
| **Contain** (the default, for every control, GUI and headless alike) | **A1** accidental damage; **A2** an over-privileged honest tool or application (uses too much, writes where it should not, connects where the owner said no). GUARDRAIL against an application that works against the owner (A3), because it runs as the owner and can reach ArcForges' own objects and controls (T-22) | L2 and L3 resource limits; L4 access dimensions | The operating-system strength of each realized value, read back. Where a route that honest software uses in ordinary operation leaves the container, the promise covers "the copy ArcForges started" (chapter 17 §3.2, `reach`) |
| **Distrust** (an owner requirement, never implied) | Adds **A3** | Only an L4 realization on a build class whose **every** launcher cell is measured denied, the display and bus cells included | `min_holds_against = A3` on the application's profile. Before the labs it refuses everywhere, by design, and names the open cell. Never on an unconfined application. Where no confinement exists, the card names the alternatives: another account, a VM-class backend (EX-18), or not running the application |
| Never claimed | A5 for any same-kernel tier; A6 at P0; "tamper-proof", "locked" or "cannot be undone" for any owner-directed limit | — | — |

Three same-user paths defeat owner-directed limits against A3: the **object** path (the containers are the user's), the **control plane** (a HUMAN origin is accepted from any same-user client presenting as HUMAN; the store and `node.json` are user-writable; the Desktop is drivable; an endpoint can be taken while the node is down) and the **escape** path (brokered work never joins). The weakest route is simply asking the node as HUMAN, so hardening ArcForges' objects is never tamper resistance; only confinement addresses all three (D2-gf07-tamper-human-12). Hardening is still adopted at the first owner-job row as GUARDRAIL hygiene, never as tamper credit (§6.5).

## 3. The correction of the earlier GUI conclusions

The 2026-10-18 direction excluded GUI applications from confined profiles ("No GUI confinement in any stage proposed here"; portable GUI applications "UNCONFINED only"; "GUI applications from confined profiles (all OSes)" as an excluded class; "Application sandbox: Rejected" partly because "most Win32 GUI applications cannot run in an AppContainer"). The owner rejected that reading on 2026-10-19. The superseded texts stay as history in [17](17-delegated-execution.md) §8.5, §11.1, §11.3, §14 (EX-19) and §16, each naming its successor.

**What was wrong, in one paragraph.** Facts about GUI *interaction* isolation (X11 isolates no clients, D-lnx-projects-28; separate desktops isolate messages, hooks, clipboard and atoms, D-win-primitives-completion-13) were used to exclude GUI applications from *process-level* confinement, which neither fact addresses; X11's escape condition was generalized to every display system; a "headless first" order became a "headless only" scope, although the chosen backends are the mechanisms that Win32 app isolation and Flatpak use for GUI applications (D2-win-confine-4, -23; D2-lnx-confine-3); the direction was centred on AI and delegated work; and general native application resource management, which job objects and cgroups give GUI processes like any other (D2-win-resource-1; D2-lnx-resource-2), was under-stated.

**The correction, as two rules.**
1. *GUI and IPC facts decide the `holds_against` cap of a realization and its disclosed limitations; they never decide whether an access dimension may be requested, realized and read back.*
2. *GUI interaction isolation is not a product direction.* No separate desktops, nested display servers, secure surfaces or approval devices are proposed for GUI applications as ways to lift a cap; the holder-owned window station that [17](17-delegated-execution.md) already gives headless attempts, which have no window of their own, is kept. Where a display system leaves a launcher cell open, the cap is a documented limitation, and the owner chooses between capped confinement, an unconfined run with resource control, another account, a VM-class backend, or not running the application.

**Not overcorrecting.** A display, bus, broker or input route by which confined code can make an unconfined process act is a bypass of process-level confinement: a launcher cell of the realization, counted as an escape gap until a lab measures it denied, which caps every dimension's `holds_against` at {A1, A2} without lowering its strength ([17](17-delegated-execution.md) §3.2). Only those "drive" cells are measured. What the screen, the clipboard and typed input expose is stated in one fixed sentence per platform, with no lab ([17](17-delegated-execution.md) §3.5).

## 4. Four facts, five levels, two models

### 4.1 Four independent facts on one attempt record

The owner's five levels look like a ladder; they are recorded as **four independent facts**, each with an existing home.

| Fact on the attempt record | Values | Existing home | Level |
|---|---|---|---|
| **Lifecycle hold** | observed · adopted · launched | Process labels `UNMANAGED`, `ADOPTED`, `MANAGED` ([03](03-resource-control.md) §9); task kinds `ADOPTED`, `COMMAND`, `SERVICE` | L1, L2, L3 |
| **Resource policy** | none · owner-directed limits per resource, each with a verb | `res.<resource>` values of the Realization; placement on the container | L2, L3 |
| **Access profile** | UNCONFINED · CONFINED | `profile_ref`; the realization's access dimensions ([17](17-delegated-execution.md) §2.5) | L4 |
| **Cooperation** | none · a cooperative session (grants, declarations) · tasks it submits | `ActorRef` caller fields; the cooperative family's grant records; task records | L5 |

**The only couplings**, each physical, none a product choice:
1. **CONFINED requires "launched".** Tokens, namespaces, Landlock domains and App Sandbox entitlements are fixed when a process is created; no documented interface imposes a useful access restriction on a running process at P0 (D2-win-resource-21; D2-lnx-confine-1). An adopted application can be resource-controlled but never sandboxed; its access dimensions read `NONE(reason: same-user tier; access can only be restricted at launch)`.
2. **An enforced cooperative grant requires a container.** A grant to an application that is neither adopted nor launched is coordination only.
3. **Placement is orthogonal to all four facts.** A confined interactive application runs inside an owner-placement container; a confined background MCP server in managed placement.
4. **Matching is not control.** Attributing an observed process to an application is L1; attaching limits automatically needs a strong identity anchor or a HUMAN confirmation (§7.5).

A level is per instance; a policy is per application. The same application may be adopted today and launched tomorrow; its record and rules do not change.

### 4.3 Owner-directed enforcement and cooperative coordination

| | Owner-directed enforcement | Cooperative coordination |
|---|---|---|
| Who acts | ArcForges, through OS mechanisms on the application's container | The application: it asks, learns its grant and adapts |
| Needs the application to change | Never | Yes, by definition |
| Needs ArcForges to hold the process | Yes (L2 or L3) | No: an uncontained application can cooperate ("coordination only") |
| What binds | The owner's numbers on the container, read back: ENFORCED with the same-user qualifier | Two faces, always shown apart: the limit on the requester, ENFORCED only when ArcForges resized the requester's own container, otherwise OBSERVED ("coordination only: nothing stops this application from using more"); the capacity held back from managed work, whose root-cap part is ENFORCED (same-user qualifier) and whose admission part is GUARDRAIL |
| Bound | The OS mechanism's measure | Authorization: `granted ≤ min(request, per-application maximum, aggregate cooperative cap left, B)`. Admission: it fits now or the answer is DEFERRED ([03](03-resource-control.md) §10) |

**The clamp is the authorization bound; admission is a separate rule** ([03](03-resource-control.md) §10). *Memory:* a grant, a resize or a hold is admitted only if, afterwards, the accounted memory of running attempts and outstanding guest grants (the requester's own usage moved out of `U` inside its smoothing, so that it is counted once) is at most `B_mem`, computed with every live hold, the new one included, in `K_mem` (so `avail_mem ≥ 0`, and a hold is counted once); otherwise the answer is DEFERRED, `exceeds_budget` or `exceeds_capacity` ([03](03-resource-control.md) §4). A resize that raises `mem_expected` is an admission event. Memory is granted in part only within `avail_mem`. *CPU:* clamped to `B_cpu` and counted in `cpu_load ≤ overcommit_cpu × B_cpu`; a partial grant is allowed. A no-wait request and a resize of a running attempt are decided in one pass of [03](03-resource-control.md) §4's loop at the entry's effective class and owner key, under [03](03-resource-control.md) §7's admission restrictions (Tight admits only INTERACTIVE); they are granted only if such an entry would be admitted now and would not delay an active large-task reservation, otherwise the answer is DEFERRED.

**Composition rules:** owner-directed enforcement is the ceiling and cooperation moves inside it; cooperation never lowers a hard bound below current use and never raises one above the owner's maximum; owner-directed enforcement never depends on cooperation (if the SDK is absent, crashed or lying, the owner's limits are unchanged); cooperation alone is never called a limit; **one engine**: both models enter [03](03-resource-control.md) §4's ordering, feasibility classes and pressure ladder. A distinct abstraction would be justified only by its own fairness policy that cannot be expressed as owner keys and pool weights, or its own persistence independent of tasks; none of the owner's examples needs either. There is no second scheduler.

## 5. Placement and accounting

### 5.1 Two placements of the one container

- **Managed placement** is release 1's only placement: an attempt job nested in the root job, or a transient unit in `arcforges.slice`. It is for work the owner hands to the scheduler: builds, agent commands, MCP servers, background services, render queues, an integrated application's heavy work.
- **Owner placement** is the same container beside the root. On Windows: a top-level job with the attempts' own name pattern, held by `exec-wrap`, never kill-on-close, with no UI limits and no lethal limit at assignment. On Linux: an XDG-named `app-arcforges-<id>@<random>.service` in `app.slice` for a launch, or the desktop's own unit adopted in place (D2-gf01-placement-10, -13, -14). It is for the applications of the owner's own interactive life.

**Why owner placement is required, not stylistic.** The root exists to keep managed work out of the owner's headroom ([03](03-resource-control.md) §5.1, §5.4). An owner's interactive application inside it would be squeezed by the root CPU cap that follows `B`, by the Tight level and by the interactive guard; on Linux it would become an OOM candidate of the slice's `MemoryMax` when builds grow; on Windows the root's commit bound could fail its allocations; and `accounted_mem` never decreases, so a long-lived peak would hold `B_mem` for days (D2-gf01-placement-2). A child cannot escape its parent's bounds, so exempting interactive attempts inside the root is impossible. Owner placement is one immediate branch of the admission algorithm, like light routed commands: QUEUED → RUNNING at once, outside `global_max_running`, pool limits and DRR, so SM-TASK is unchanged. It is a second placement (beside managed placement) of the same job and unit mechanisms, which [AD-0005](../decisions/AD-0005-resource-enforcement.md) names, effective at RM-18's promotion; it is not a concept and not a third container type.

**Who chooses.** A per-application role with a default per class, settable only by a local HUMAN. A SCRIPT or AGENT launch of an application whose profile says owner placement runs in managed placement or is refused; it never inherits the role, because owner placement would otherwise make an escape look owner-made. An AI client run as an application is managed, inside its session envelope, by default; owner placement only by an explicit HUMAN choice, with a warning that the session budget no longer bounds it. Games get no placement by default: they are observed, and the guard acts around them (§10).

**The reactions follow placement.** The pressure ladder ([03](03-resource-control.md) §7) and the interactive guard act on managed placement only. An owner-placed application never reaches Tight, Pressure or Critical, is never a guard target, and may be a presence source. A kill at an owner application's own limit is not machine pressure and must not trigger Critical. **The one exception to "never reaches the ladder":** a cooperative grant that an owner-placed application asked for can be withdrawn (by lease end, release, a budget fall, revocation in its intent order, or starvation revocation) only back to the base the owner set, never below it, and nothing is killed. Nothing else of the ladder or the guard reaches owner placement. Residual, stated: commands attached to a terminal are work and stay managed, so they keep a stutter risk under the guard: the root cap that follows `B` is a quota that lets work run and then stalls it each interval (D2-games-13; D2-gf01-placement-22), mitigated by weights instead of caps and "enter fast, leave slowly". A direct memory floor for owner applications is UNAVAILABLE at P0.

**This is the product's fairness model.** Three kinds of load share a machine: the owner's own (owner placement: never shaped by ArcForges below the owner's own values), managed background work (shaped first) and managed interactive work (terminal-attached commands: admitted first, shaped last). Every fairness feature (the guard, cooperative declarations, conditions on admission, group budgets) acts by changing the budget or the order of **managed** work. That is the only fairness ArcForges can deliver honestly at standard-user privilege, and it never touches an application the owner did not hand over (goal candidate GC-1).

### 5.2 Accounting: one budget formula

The arithmetic is [03](03-resource-control.md) §10's: `managed_*` narrowed to managed placement; requesters leave `U` inside its smoothing; owner-placed applications, launched or adopted, are a reported part of `U` (`U_owner`), measured and smoothed like any other load the owner runs, their caps shown and never reserved; the hold term `K` enters `B = max(floor, C − R − U − guest_other − K)`, per resource: `K_mem = presence_mem + Σ_r max(granted_mem_r, peak_observed_mem_r)`, the peak held while the grant lives (its duration is clamped by policy); `K_cpu = presence_cpu + Σ_r max(granted_cpu_r, ũ_cpu_r)`, where `ũ_cpu_r` is the requester's CPU smoothed with [03](03-resource-control.md) §2's asymmetric alpha, never a peak. For an owner-placed requester, `granted_r` is the amount of the grant itself, never the owner's cap, and its base is the owner's own values. `K` lowers admission, the root CPU cap, `MemoryHigh` and the Windows root notification limit; it never lowers the slice's `MemoryMax` or the root's hard commit limit, which follow `C − R`, so a presence or a grant never causes an OOM kill or a commit failure at ArcForges' own hard bounds. It can slow running work, and a wall-clock timeout may then fire. On Linux hosts where systemd-oomd watches user units (Ubuntu 22.04 and 24.04 desktops: `user@` at 50 % for 20 s; Fedora: every user slice, `arcforges.slice` included, at 80 %), lowering the slice's `MemoryHigh` below managed use raises memory pressure that may lead oomd to end an attempt regardless of its limits (E4; D2-lnx-resource-16; LAB2-LNX-06). At a grant's start the requester's current usage moves from `U`'s smoothed state into `K`, and at its end back, so the same memory is neither counted twice at the start nor missed at the end (a state transfer; G43 checks both ends). A form that subtracts a separately smoothed usage from each grant is rejected: with 03 §2's asymmetric smoothing it under-counts in the unsafe direction (D2-gf01-placement-16 … -19). Gate G43 (LAB2-X-04's crossover leg, with its CPU leg) tests that the formula never under-counts beyond 03's accepted rise lag.

**The simpler alternative every stage must beat:** report-only delegation, in which the owner sets limits with OS tools and ArcForges only observes and diagnoses.

## 6. Holding an application

### 6.1 Launch (L3) and attach (L2), per platform

All values are attainable and pre-lab (E4 as ArcForges behaviour; mechanisms E1 or E2).

| | Windows | Linux | macOS (capability statement only) |
|---|---|---|---|
| L3 launch | Created suspended by the holder, assigned to the top-level owner job alone, resumed ([AD-0005](../decisions/AD-0005-resource-enforcement.md) Windows §6 pattern) | `StartTransientUnit` in `app.slice`; `exec-launch` with the class's environment passthrough (`DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_ACTIVATION_TOKEN`, `MEMORY_PRESSURE_WATCH`); `ExitType=cgroup` from systemd 250; `CollectMode=inactive` | No container; a spawn-time QoS clamp, nice and per-process rlimits only |
| L2 attach | The safe attach: identify by `(pid, creation time)`; check current commit; no lethal limit at assignment; assign; sweep descendants; read back. A process already in a foreign job is refused until LAB2-WIN-01, then nests at PARTIAL only under a job without UI limits | `unit_in_place`: `SetUnitProperties(runtime=true)` on the desktop's own unit, prior values journaled (EX-08) and read back; never moved out of Snap, Flatpak, GNOME or KDE units; `scope_migrated` into `app.slice` only for programs without a unit, with migration's losses (charges, children, identity) stated (D2-lnx-resource-12) | Observe, demote priority (HINT), stop; nothing attaches |

**Attach gaps, stated:** on Windows, commit made before the attach "is not examined", earlier children outside the sweep stay outside, the association is permanent (releasing it lifts the limits) and the attach is racy (D2-win-resource-17); active-process and time limits kill at assignment, so they are never set at attach. On Linux, in-place control keeps existing charges, but a running scope's `OOMPolicy` is fixed; GUI programs started from WSLg have no unit. **Launch comes before attach** in every stage order.

### 6.2 Four realization rules

1. **Strangers in an owner container.** *Windows:* a handler started through a classic file or protocol association, while it is not already running, is created inside the caller's job and cannot be moved out (D2-win-confine-27). ArcForges detects executable mismatches among the owner job's members. Before a stop, it lists them and offers "stop everything" or "stop only this app": terminate the app's own processes, keep the job until the rest exit, and lift the job's limits once only detected strangers remain. `lifetime = CONTAINER` ends when only detected strangers remain. A Chromium-family default browser started this way is expected to break its own sandbox (§6.4, E4) until LAB2-WIN-10 shows otherwise. *Linux:* GNOME's `gio open` spawns the opened handler in the **caller's** unit unless the handler is D-Bus-activatable, moves itself into its own scope (snap and Flatpak applications; Ubuntu's default browsers are snaps) or is already running; a deb or rpm browser started this way runs inside the messenger's unit and counts against its limit (D2-lnx-resource-26). A stop or tree kill of the messenger would end the browser windows the owner opened from it; a container lifetime would keep the attempt running while the browser lives; under `MemoryMax` the kernel's victim may be the browser. **Rule (Linux):** detect executable or desktop-ID mismatches among the unit's members; before a stop, list strangers and by default move them out to `app.slice` (with migration's known losses) or ask the owner; let a container lifetime end when only detected strangers remain. On both, the card says "programs this app opens may run inside its limits".
2. **"Container empty" on Windows by polling.** Only notification-limit messages are guaranteed job messages; the empty-job message is best effort (D2-win-resource-4). The holder therefore polls job membership on a timer as well as on the message. On Linux the service manager stops an `ExitType=cgroup` unit when its cgroup empties (systemd 250 and later); where that is unavailable, the card says "lifetime: root process" until LAB2-X-19 proves a fallback.
3. **Adoption placement is additive.** Release 1 specifies root-first adoption ([04](04-execution.md) §10; AF-SEC-01). On Windows a job association cannot be broken, so a process adopted under the root in release 1 can never move into an owner job. At RM-18's promotion, placement on `AdoptProcess` arrives as an optional additive field whose default keeps release 1's behaviour (contracts stay additive within `v1`); already-adopted instances stay under the root until they exit, and the card says so.
4. **The holder strategy gates launch, not only attach.** Every long-lived Windows job needs a holder, about 6.65 MB each ([15](15-performance-targets.md) §2's published value): 133 MB at 20 applications and 333 MB at 50 (estimated). The strategy (a shared holder, supervisor-held handles, RM-14's executable, or per-application holders capped in number) is an owner judgment after LAB2-X-14, before the first Windows stage of RM-18 or EX-25.

### 6.3 Brokered and handed-off work

Every brokered or handed-off child runs outside every level's container and is labelled `UNMANAGED`; work done for the application by shared services is not charged to it (D2-win-resource-29, -30; D2-lnx-resource-25). On Windows, COM `DelegateExecute` verbs, packaged activation, the WinRT launcher, `runas`, WMI, Task Scheduler, services and notification activation start work outside the job, while a classic file association starts its handler inside it (D2-win-confine-27). On Linux, session-bus and portal launches run elsewhere. A relaunch that hands off to a running instance raises `HANDED_OFF_TO_UNMANAGED_INSTANCE`. A vendor's own autostart starts the application outside ArcForges at logon; until the owner's decision under boundary 3.4 (§19, decision 10), the card says "also starts itself outside ArcForges at logon", and a hold of that entry is EX-15's later stage.

### 6.4 The Chromium and Electron family: a job-nesting fact, never a GUI fact

- **Windows.** Chromium assigns its sandboxed children to UI-limited jobs at creation; UI-limited jobs do not nest; so even a limit-free outer job is expected to break the application's own sandbox (D2-win-resource-16). Because Electron, CEF and WebView2 hosts are a large share of desktop software, this is the first Windows gate of RM-18 and EX-25. **Three branches, chosen per family by LAB2-WIN-10, never by assumption:** (1) the application keeps its sandbox in a no-breakaway owner job → the normal owner-placement rows; (2) it keeps its sandbox only in a breakaway-permitted owner job → `res` and kill-tree PARTIAL with the gap "children that break away are not limited or contained" (E5 until the leg runs); (3) neither → resource control `UNAVAILABLE(reason)` for that family on Windows: L1 observation, HINT levers and an opt-in GUARDRAIL monitored stop, with the application's own sandbox untouched. Turning an application's inner sandbox off (where it offers a switch) is the owner's recorded trade-off, never a default.
- **Linux.** The inner sandbox needs user and PID namespaces; a view that denies nested namespaces aborts it. Under Ubuntu's AppArmor user-namespace restriction, an application whose path has no AppArmor profile granting userns is expected to lose its own sandbox even unconfined (E4; the setuid fallback is probably not taken); Ubuntu ships such profiles for several Chromium-family applications. Neither case affects L2/L3 resource control, which uses no namespace. A strict profile refuses with `APP_SANDBOX_NEEDS_USERNS`, never a silent `--no-sandbox`; the owner chooses between the inner sandbox off inside the outer boundary, a separately named nested-namespace view, or the vendor's Flatpak (D2-gf08-linux-gui-compat-7 … -9).
- **The basis fact `app_inner_sandbox`** (`on`, `off(by owner choice)`, `unavailable(reason)`) is on the card.

### 6.5 Hygiene of ArcForges' own objects

Adopted at the first owner-job row, as GUARDRAIL improvements, never as tamper credit (D2-gf07-tamper-human-16 … -18): explicit descriptors on every Windows object ArcForges creates (only the rights the node and holder use, plus SYSTEM; no ALL APPLICATION PACKAGES; OWNER RIGHTS; a label; read back); a holder descriptor that grants the user synchronize and limited query and withholds handle duplication and process creation; limits and descriptors re-read at apply time and on an interval, a change raising `ENFORCEMENT_DEGRADED` with reason `limit_changed_outside`, re-applied only where the owner's policy says so. A change reverted between reads is unseen, and the record says so. A privileged holder is rejected for A3 (it closes the object path only and adds a second trust domain) and deferred under EX-20.

## 7. The per-application record

### 7.1 Why a record, and where it lives

Nothing in release 1 is keyed by application: `ADOPTED` is per instance, pools per pool, envelopes per session. The positioning needs one key for at least eight uses: L2 matching, L3 selection, L5 maximums, the scope of failure attribution, storage budgets, state roots, the L4 default access profile, and group budgets. AD-0017 principle 8's test therefore passes for *a* record; the question is which existing concept carries it, so that no second set of identity anchors appears.

| Part | Content | Concept status |
|---|---|---|
| **Key: the Installation** ([17](17-delegated-execution.md) §2.2, concept 3) | Identity anchors with strength and binding; state roots; later `update_owner`. "Installation" never implies that ArcForges installed anything: the OBSERVED level covers vendor-installed software | An existing proposed concept, **entering earlier** |
| **Resource body:** a keyed, repeated per-application message in the delivered `PolicyDocument` (beside `ResourcePolicy`), keyed by `installation_ref` | The placement role; per-limit verb-number requests with REQUIRED or PREFERRED; class and traits; lifetime and restart policy; storage budget (roots, kind, interval, action order); cooperative maximums, class ceiling, interactivity designation, minimum identity strength, and the aggregate cooperative cap | Not a concept by AD-0017 principle 8's record-kind clause: persistent, keyed by `installation_ref`, survives GONE; uses: owner-directed limits, cooperative maximums, designations, storage budgets, restart policy. It is written through the delivered policy-revision operations (`UpdatePolicy`, `ValidatePolicy`, `RestorePolicyRevision`) and needs no operations of its own; if it ever needed operations of its own, they would count as a concept |
| **Access body:** the Installation's default access profile ([17](17-delegated-execution.md) §2.2, concept 2) | UNCONFINED (no grants) until a confined backend is promoted; typed grants with CONFINED intent by HUMAN choice per application | Unchanged in definition and timing (EX-27 stage b) |

**Rejected homes:** a profile keyed directly by identity (duplicates the anchors); the APPLICATION group kind as a home (it may return only as a group-budget realization that references the Installation, EX-14); no record; amending concept 2 to carry resources (every resource-only application would then carry an "access profile", and concept 2's rule "UNCONFINED profiles carry no grants" would change).

### 7.2 What "entering earlier" brings, and what it does not

1. **Early subset:** the entity with the OBSERVED (SEEN → GONE) and DELEGATED (RECORDED → ACTIVE → REMOVED_BY_MANAGER) levels only; identity anchors with strength and binding; state roots. The acquisition record, versions, `update_owner` and the OWNED lifecycle stay with EX-13 stage b.
2. **Creation:** only by a HUMAN action (configuring an application, writing a standing rule) or by the owner's explicit observation opt-in; never one per executable the node happens to see, because observation of unlaunched software stays off until enabled ([17](17-delegated-execution.md) §10).
3. **Rebinding:** the per-application policy entry survives GONE; a re-appearance rebinds only on a strong anchor (`PACKAGE`, `FILE_PUBLISHER`, `PROTECTED_PATH`); a weak-anchor match only observes.
4. **Service surface at this stage:** read and list, plus the owner's create and forget; no acquisition operations.

### 7.3 Classes and traits, not a catalogue

**The application class replaces each batch default** that would harm an interactive application: standard output discarded and standard error captured with a notification instead of a terminating output limit; the user's temp (or a persistent measured temp under the Installation's state root) instead of a per-attempt temp deleted at the end; readiness `NONE`; no wall-clock timeout; a 30 s graceful stop after `WM_CLOSE` or SIGTERM; the Linux session-environment passthrough; `kill_with_node` forbidden; owner placement outside freeze and requeue; `lifetime = CONTAINER`, so tray and single-instance applications are not cut short. That lifetime needs one additive SM-ATTEMPT trigger, "container empty" → FINALIZING without the leftover kill ([04](04-execution.md) §12). No new execution kind.

**Two classes** (*interactive application*, owner placement by default; *background service*, managed by default) and **five composable traits**, each tied to a mechanism fact: `realtime_threads` (a CPU number becomes a weight; a cap is an override labelled "dropouts expected; real-time threads not limited"), `own_supervisor` (`OOMPolicy=continue`; the application restarts itself), `persistent_helpers` (build daemons; "may run in shared daemons"), `uses_gpu` (deferred, never throttled, while the owner is present; "GPU and compositor work: not limited"), `locked_memory` (a hard limit below the locked set is refused). Class presets ("messenger", "IDE", "media editor", "local server") are values the **owner** picks; ArcForges never matches a third-party application to a preset by itself, because matching an application by executable or package is recognition data with a maintenance cost (AD-0017 boundary 3.13; the tool adapters of [05](05-toolchains-caches.md), which classify build and package tools by executable and subcommand, are tool-class knowledge and are unchanged).

### 7.4 Restart policy for services

Modes `NEVER`, `ON_FAILURE`, `ALWAYS`, never for `COMMAND` or `ADOPTED`; one restart owner per Installation (ArcForges, the application, or none), so ArcForges never races an application's own supervisor; backoff 5 s × 2ⁿ up to 60 s, reset after 10 healthy minutes; more than 5 ends in 10 minutes raises `RESTART_LOOP`; never after an owner cancellation; after an own-limit failure once, then the owner decides. Realized on the existing retry path (SM-TASK's retry wait and [04](04-execution.md) §8's backoff), through admission, with an SM-TASK guard and a clean-exit trigger as amendments, not new machines. Rejected: systemd `Restart=` and holder restarts, which would run several runs per attempt outside admission. Whether the owner wants a standing policy or the existing `retry_safety` assertion first is the owner's decision (§19, decision 15).

### 7.5 Standing rules, matching and identity

**Standing rules.** An owner-written rule "when this application appears, hold it with this profile" is explicit adoption by a recorded HUMAN decision. It inherits attach's gaps (helpers started before the attach, foreign-job and protected processes, brokered children) and states them; on Linux the in-place unit and its journaled drop-ins are the cleaner form, and a drop-in counts only after a launched instance was read back. A rule that matched nothing is a finding; a match running outside its profile raises `APPLICATION_OUTSIDE_PROFILE`.

**Three identity questions, one ladder.** Selection (which profile applies to a launch or adoption), matching (which running processes belong to an application) and caller (which application calls the cooperative API) use the Installation's anchors and one ladder: `SANDBOX` > `LAUNCH` > `CODE_REQUIREMENT` (macOS, stated only) > `PACKAGE` (Windows package identity from the token; on Linux `.flatpak-info` only; scope names and snap labels are `ASSERTED`) > `FILE_PUBLISHER` > `PROTECTED_PATH` > `USER_PATH` > `ASSERTED`, each with its binding (a handle, a pidfd, an audit token; a PID with its start time is `RACY`) (D2-gf04-coop-api-17). **This ladder extends [17](17-delegated-execution.md) §7.2 for application callers.** `LAUNCH` means that ArcForges launched a file it verified through a handle, and the caller is a member of that attempt's container; it is GUARDRAIL (on Linux, `RACY` without the pidfd interfaces; on Windows bound to the held handle), it only selects the per-application record whose owner maximums clamp the caller's cooperative grants, and it never authorizes an access decision ([17](17-delegated-execution.md) §7.2 as amended). **The honest ceiling:** no unconfined caller on Windows or Linux is identified better than GUARDRAIL; `SANDBOX` is ENFORCED only for a realization without an escape-class gap; on Linux the binding stays `RACY` until the pidfd interfaces (kernel 6.5 with systemd 253, or 6.13). Identity is derived by the node, never accepted from the caller; launch provenance is the strongest unconfined anchor, one more reason to prefer L3 over L2. Two enum values carry the new caller: an application client kind and an application origin; client-kind verification (AF-SEC-01) is a prerequisite of every application-facing row.

**Authority.** The proposed permission rows are in [11](11-security-privacy.md) §1 (direction). Writing an entry, the role, maximums, ceilings, designations and minimum strengths are HUMAN-only, which is a GUARDRAIL against same-user code that presents itself as HUMAN or drives the ArcForges Desktop, as release 1 already says.

## 8. What an owner's number means

**The owner's rule:** "A requested limit must have an explicit enforcement status, mechanism, scope, and explanation." and "Do not promise arbitrary resource limits merely because a UI allows the user to enter a number."

**A limit is never a bare number.** It is entered, stored and shown as a **verb plus a number on a named quantity**. The verb is chapter 17's `limit_behaviour` basis field made an input, so it is not a concept. The verb recommended for the application's class is preselected, so the owner's effort is the same as typing a number, but the verb is visible in the entry, on the card and in every record. In owner placement, owner-directed numbers are applied as follows; managed placement keeps release 1's formulas.

| Verb | `limit_behaviour` | Windows | Linux | Default for |
|---|---|---|---|---|
| "Tell me above 256 MiB" | NOTIFY | Job commit notification limit at exactly the number; the node re-arms it by querying. OBSERVED: "nothing stops it" | Sampled `memory.current` and `memory.peak` plus a notification. OBSERVED | Interactive classes on Windows (Windows has no non-lethal memory *budget*: its per-process working-set maximum is a paging control the application can undo) |
| "Slow it down above 256 MiB" | THROTTLE | Not available; a REQUIRED request is refused | `MemoryHigh` = the number: ENFORCED, "slowed above 256 MiB, not limited to it"; may show "not responding"; on Ubuntu 22.04 and 24.04 desktops systemd-oomd watches the user manager at 50 % for 20 s and may close it | Interactive classes on Linux |
| "Hard limit at 256 MiB: may end the app" | Windows REFUSE; Linux KILL | Commit limit at exactly 268,435,456 bytes, notification at 90 %: "allocations above fail; the app may crash or lose data; resident memory is not limited" (V-W05) | `MemoryMax` = the number with `MemoryHigh` near 90 %; `OOMPolicy=continue` on an ArcForges-created unit, or the desktop scope's fixed `stop` when adopted in place, stated before confirmation: "the system ends a process of the app" | Opt-in for interactive classes, one click away with its consequence printed; background classes in managed placement may preselect it |
| "Cap at 0.5 CPU" | THROTTLE | Top-level `CpuRate = round(0.5 / N × 10000)`, rounded half away from zero (313 at N = 16, 0.5008 LP): "CPU time, any cores, not affinity; may stutter"; the cap interval is undocumented (LAB2-WIN-02) | `CPUQuota=50%` with a 20 ms period for interactive classes, 100 ms for background; "Not available on this host" where `cpu` is not delegated (Ubuntu 22.04); real-time threads are not limited | Only when the owner types a CPU number |
| "Give it a low CPU share" | PREFERENCE | Job weight: PARTIAL, gap `weight_vs_unjobbed_undocumented`; a weight and a hard cap cannot be combined in one job (V-W04) | `CPUWeight` or `idle`: ENFORCED among sibling cgroups only | Offered beside any cap; the default when no CPU number is typed |
| "Refuse the next launch above 2 GiB stored" / "Stop it above 2 GiB stored" | REFUSE_LAUNCH / STOP | Measurement of owner-declared data roots plus ArcForges' own action: GUARDRAIL, with the interval and overshoot bound | The same; a sized tmpfs is a real capacity only for scratch data inside a view, never for a growing data store | Storage budgets, never called "quota" |

**Rules that complete it:**
1. **Exact on the stated quantity.** An owner-typed number is applied as typed ("private committed memory" on Windows; "memory charged to the app" on Linux, never "resident"; "CPU time, not cores"). Release-1 attempt formulas, including the commit factor for derived ceilings and caller hints, are unchanged.
2. **No lethal limit below current use.** A hard limit is refused at attach unless current commit plus a margin is below it (Windows), and applied stepwise from `MemoryHigh` (Linux).
3. **REQUIRED refuses**, before workload code runs, with the reason: "Slow it down" on Windows; any CPU verb where `cpu` is not delegated; resident memory on Windows; storage capacity at P0; `min_holds_against = A3` with an open or unmeasured cell.
4. **Runtimes adapt only to hard limits.** .NET sizes its heap to 75 % of a hard job limit and ignores notifications and `memory.high` (D2-win-resource-20; D2-lnx-resource-21). The card says so under "Tell me" and "Slow it down": "the app does not see this number". A first-party application closes the gap itself (§13.4).
5. **The quota period follows the class** (20 ms interactive, 100 ms background) only if LAB2-LNX-05 measures both burst and sustained work, because for short bursts the long period is faster.
6. **Read-back.** Every shown value comes from the OS, never from the request.
7. **Hints are never limits.** Priority class, EcoQoS, memory priority, process affinity and CPU sets applied from outside, `SCHED_IDLE`, nice and I/O priority, and macOS background demotion are HINT ("a hint; the app can undo it"), never GUARDRAIL ([17](17-delegated-execution.md) §3.2).
8. **Trial limits and suggested numbers.** Any number may first run as "Tell me", reporting "would have been reached N times while observed" (never above CORRELATED; on Windows the count is a lower bound because of the re-arm rule). Suggested numbers come only from peaks observed in runs where no limit acted; a peak observed at a limit is a lower bound and is never offered as a number.

**Scope wording on every value:** "processes in this job or unit; work other processes do for it (display server, compositor, audio, GPU services, brokers) is not counted; programs it asks the OS or the desktop to start through a broker are not included; programs started into its job or unit (a classic file association on Windows, `gio open` on Linux, while the program is not already running) are counted."

**The owner's words on the card** ("Enforced" never appears for GUARDRAIL, HINT, OBSERVED or a coordination-only grant):

| Ladder value or behaviour | On the card |
|---|---|
| ENFORCED | "Enforced by Windows/Linux (<measure>)": "(committed memory)", "(memory charged to the app)", "(CPU time share)" |
| MEDIATED | "Only through ArcForges' broker" |

| NONE / UNAVAILABLE | "Not available here: <reason>" |

**The burden budget.** The default view of an application is **one headline**, only when something must be known first (a routine escape route, an open launcher cell named per display system, a REQUIRED shortfall, "commands started inside this app are not managed"); **one "against whom" line** (Contain: "Protects against mistakes and over-reach, not against an app working against you." Distrust: "Also protects against an app working against you, on this computer's measured setup."); and **one row per limit** with the verb and number, the owner's word and the measure. Everything else (adversary letters, basis, policy source, intervals, gaps, read-back times, the realized value where it differs, the diagnosability preview of [07](07-records-diagnosis-memory.md) §4) is one tap away. The full view is five facets, *Seen* (L1), *Held* (L2 or L3), *Limits*, *Access* (L4) and *Works with ArcForges* (L5), each "requested → realized", never a level number or a single "sandboxed" bit. **Words that never appear alone:** "sandboxed", "contained", "protected", "secure", "capped", "limited to" for a soft limit, "tamper-proof", "locked", "blocked" for a hold, and "confirmed" for anything below CONFIRMED. **Tested before it ships:** the mock-up leg of LAB2-X-13 (no machine); a misreading changes the words, never the ladder; the pass line is the owner's (§19, decision 22).

## 9. The cooperative resource API

The owner's second resource model: an integrated application "requests resources, learns what was granted, and adjusts its own behavior accordingly", and "must never be able to bypass the owner's maximum limits merely by asking for more resources".

### 9.1 An extension of the resource model, with one new concept

- **Reused:** `ResourceDemand` (`cpu_millicores`, `mem_expected_bytes`, `mem_ceiling_bytes`) as the request's numbers; [03](03-resource-control.md) §4's ordering, feasibility classes and `ExplainTask` numbers as the answer; the pressure ladder for revocation; the attempt container and the node's limit updates for enforced grants; the tool-concurrency formula for recommended parallelism; the guest link's meanings of demand, decision, release with usage and sequence, but **not** its preempting revoke or its aggregate lease.
- **New, and the only new concept of this chapter** (AD-0017 principle 8): **the cooperative resource-grant message family and its service**, with its grant lifecycle (requested → queued → granted → updated → released, expired, revoked or lost) recorded as a state sketch inside the concept, under chapter 17 §2.2's convention that a concept includes its own lifecycle. Its uses: an application's own running process (through the SDK, the CLI sidecar or the published protocol); a confined cooperator's attempt endpoint (EX-09), where starting work is forbidden; and EX-26's designated declarations. `TaskService` starts work; the cooperative operations must also exist where starting work is forbidden, so they need their own service. **The MCP leg** (RM-09's existing AI-client leg) gives an agent Advise, Explain and undesignated declarations for its own session, and the honest wait; capacity for an agent's work comes from its tasks' admission and the EX-14 envelope budget, with no hold term ([17](17-delegated-execution.md) §7.3): task slots, if requested, clamped by `max_running_per_session`; capacity within the session envelope's budget (EX-14).
- **Three entry kinds, one engine:** the existing task API for work an application can hand over (an export, a render, an indexing pass: the admission decision is the grant, completion releases it); the cooperative family for the application's own running process; and nothing for owner-directed enforcement, which never depends on the SDK.
- **Rejected:** a coordination service with its own budget table and policy (a second scheduler), a reservation entity, a reservation task kind, a grant table, a stage-1 cooperative-only endpoint, and "act for another process" requests. The simpler alternative every stage must beat: owner-set per-application policies with no integration, plus `TaskSpec` hints and `ExplainTask` for applications that hand over tasks.

### 9.2 Operations and answers

Six operations (names illustrative; nothing is reserved, [17](17-delegated-execution.md) §12): **Request** (an intent class, an optional demand, a smallest useful amount, a duration clamped by policy, a wait mode, a reason; or, with no numbers, a declaration of activity; no-wait is the default), **Watch** (updates with an increasing sequence number: grant changes, "shrink to X by T" notices, advice changes; heartbeats renew the lease), **Renew** (for clients without streams), **Release**, **Advise** (whether to defer, the pressure level, recommended parallelism, and whether the caller is coordinated at all; no grant needed) and **Explain** (the numbers behind the caller's own grant). No operation names another process, starts work, changes policy, or reads other applications' grants beyond D1 summaries. "On behalf of" exists only as "launch the child through ArcForges". The caller's identity, process and scope are derived by the node, never carried in the request.

**What an answer may say:** both faces separately (§4.3); the realization, not the request (CPU requested in millicores of CPU time and realized as a quota, a weight or a hold against managed work, and the answer says which: a weight guarantees no amount; memory a commit bound on Windows and charged memory on Linux; storage the owner's budget and the node's latest measurement with its time, never a reserved capacity; GPU unavailable or report-only; disk I/O observed); the bounds that clamp it (the per-application maximum, the class ceiling, whether the caller met the owner's minimum identity strength); the derived identity; and the grant's diagnosability (an enforced grant follows the OS rules of [07](07-records-diagnosis-memory.md) §4; a coordination-only grant can only ever yield CORRELATED). Intent classes: `DEFERRABLE`, `USER_VISIBLE`, `USER_BLOCKING`, plus a latency-sensitive flag.

### 9.3 Admission, accounting and caps

- **One queue.** A waiting request sits in the pool the owner assigned, under [03](03-resource-control.md) §4's ordering, with the derived application identity as an owner-key kind for deficit round robin; aging as for tasks (R-EXE-014). A managed task starved by holds beyond the starvation bound revokes deferrable and user-visible holds, never a user-blocking grant of an application the owner designated (effective class INTERACTIVE); an undesignated user-blocking grant is revoked as user-visible. For an owner-placed application, revocation withdraws a grant only back to the owner's own values (§5.1). The owner may exempt owner-placed grants from starvation revocation, at the cost of holding managed work back by up to the aggregate cap for one lease (§19, decision 19).
- **Fits now or DEFERRED.** Every grant, resize and hold passes [03](03-resource-control.md) §10's admission rule (§4.3): memory only within `avail_mem` and never above `B_mem` once granted; CPU clamped to `B_cpu` within `overcommit_cpu × B_cpu`.
- **Accounting.** A grant to an application in managed placement resizes that attempt's request. A grant to an application outside managed placement enters `K` (§5.2).
- **A cap on the total:** the sum of grants stays below `coop_fraction × B_pre-hold`, where `coop_fraction` is set by the owner and `B_pre-hold` is `B` computed without cooperative holds; an impersonator can claim every identity its anchors satisfy, so the exposure is a capped sum, and one connection obtaining grants under several identities is flagged.
- **Zero default allowance.** Unlisted identities get no grant by default; yielding and advice need no allowance.
- **Holds without persistence.** Capacity holds for uncontained applications are live, in-memory scheduler state, lost at a node restart, which errs safely. The no-wait form is built first; the waiting form only if retrying clients are shown to lose to managed work.

### 9.4 Dynamic changes, expiry and release

A lease of 60 s, renewed every 15 s, and a caller gone for 5 s releases (values for LAB2-X-03 to confirm). For a contained caller, the container's limits rise **before** the update is pushed; a shrink is announced as "target X by T", CPU is cut at once, memory is lowered soft first, and a hard memory bound is never lowered below current use; only [03](03-resource-control.md) §7's Critical level stops work, and only preemptible work. Release, expiry and revocation return the attempt to its base request; a hard memory bound returns to the larger of its base and current use and follows use down; nothing is killed. For owner placement, the base request is the owner's own values. After a node restart, contained grants keep their OS limits and the restarted node restores the base request when the lease would have lapsed; this needs three persisted columns of the attempt record (a schema change at promotion, not an entity). Runtimes see a change only if they look: .NET's GC sees a new memory limit only through `GC.RefreshMemoryLimit()`, which the SDK calls on opt-in. **No delivered path resizes a running attempt today**: the OS calls are proven for attempts, the resize is new node logic.

### 9.5 One interactivity declaration, bounded twice

One request with an intent class and no numbers. Its effects are bounded by origin and by an owner designation: an **undesignated** declaration: the caller's own grant at high priority at most; by itself it is advice. A **designated** declaration (the owner designated the application by a HUMAN-only entry, and the caller meets its minimum identity strength): its own grant interactive; deferral advice for deferrable cooperators; a capped presence term in `K`; the owner's interactive profile actions on background and low pools; never a freeze, never a lowered hard memory bound, never an action outside managed work. The **owner toggle**, the owner's own interactive mode: the full profile, including the Linux freeze of pausable work; agent clients are never frozen. A declaration is not an authorization and is not trusted: an impersonator of a designated identity gets designated-declaration effects within the caps, recorded as "presence trigger: declaration by <identity> (<strength>)". Presence is a state, so live declarations contribute the largest cap, not a sum.

**Clients.** The C# SDK is optional, thin and permissively licensed (the licence is the owner's decision), generated from the Contracts protos and never linked to AGPL node or client libraries. Its rules: absence is a normal result (a connect budget of about 250 ms); never start, install or prompt for ArcForges; never block a UI thread; clamp advice to the application's own bounds, because an endpoint can be squatted while the node is down; nothing leaves the machine; never change the application's own OS scheduling on its behalf. **The published local protocol** for any language is the delivered local RPC wire contract restated as obligations, with one MUST: a Windows client opens the pipe with an anonymous or identification impersonation level, or checks the server's owner before its first write (against a squatter: another account holding the impersonation privilege, such as a service account, that pre-creates the computable pipe name). Cooperating clients share the node endpoint's connection budget (64 by default). A per-process connection cap at accept and a reserved share for HUMAN surfaces are new node logic; a second listener is the fallback if LAB2-X-03's connection-count leg shows crowding. **A CLI sidecar** (a grant-holding mode that prints JSON lines and releases on end of input) gives every language a path at stage 1; its identity is ancestry-derived and capped at GUARDRAIL. **Rejected:** loopback TCP, gRPC-Web, a Linux D-Bus transport, a C ABI shim, and first-party per-language packages before two external integrators. The product does not become an SDK ecosystem; the specification, fixtures and SDK are published so that cooperation is possible in any language (goal candidate GC-4).

**Not exposing privileged operations to arbitrary same-user processes.** Maximums, ceilings, designations, the aggregate cap, minimum strengths and the enforcement mode are HUMAN-only, and the application permission column is narrower than SCRIPT's, except designated-declaration effects through an owner designation, which an impersonator of a designated identity also obtains within the designation's caps ([11](11-security-privacy.md) §1, direction). The owner's invariant holds **for what a caller obtains through the cooperative operations under the application origin**. A caller that presents another origin through the same endpoint gets that origin's rights, against which the maximums are a GUARDRAIL, as they are against a store edit, a container change, or driving the ArcForges Desktop by synthetic input or UI automation; they become ENFORCED only for callers confined to their attempt endpoint whose realization has no escape-class gap, **the display path into ArcForges' own client included**. That bounds the claim; it makes no application ineligible for cooperation.

Linux: resizes go through the user manager; where `cpu` is not delegated the CPU face reads OBSERVED; any same-user process can set properties on user units, so the cooperative API is never the weakest path; a memory shrink makes the writer reclaim, which can stall the user manager on older systemd. macOS (capability statement): grants are advisory to the OS; only ArcForges' admission and its monitored stop bind; cooperation is the main lever for *quantities* there.

## 10. The interactive guard and admission conditions

"Game resource management and game sandboxing are separate questions. The former may be useful long before the latter is feasible." (the product owner).

- **The benefit is a property of the background work, not of the game.** Every lever acts on managed work; no lever depends on the absence of a window.
- **The touch ladder:** T0 nothing; T1 reads that need no handle; T2 a query-only handle; T3 changing the game's environment unopened; T4 its scheduling; T5 ownership; T6 execution or memory. **By default ArcForges stays at T0–T1.** The owner may lift that per title with the risk stated. **As proposed to the owner** (§19, decision 12): titles protected by kernel anti-cheat are never adopted, launched or opened.
- **Presence inputs**, each a forgeable policy input, never an authorization: the owner's toggle (HUMAN origin; the reliable input, only as strong as HUMAN classification); owner rules ("while this executable is in front"), matched on the process list, never by a handle to the game; foreground detection (on Windows the foreground window's process without a handle, never in-context hooks; Wayland offers no portable signal); cooperative declarations (§9.5); the game's own GameMode registration on Linux, observed and never replaced; a leased toggle from the phone (Pro), never a freeze.
- **Levers, all on managed work, in rank order:** the presence term in `K` (lowers admission, the root CPU cap and `MemoryHigh`; never `R`, never the hard bounds; enter fast, leave slowly: at EX-26's promotion a rise of the presence term updates the root limits at once, outside [03](03-resource-control.md) §5.1's 10 s rate limit, and its fall follows the hysteresis, LAB2-X-06); Tight-level deferral of background and low pools; Linux slice weight or `CPUWeight=idle`, effective only as a peer of the game's cgroup; freezing pausable Linux work (HUMAN toggle only; never agent clients, network services or workspace-key holders; Windows has no supported pause); Windows below-normal priority, EcoQoS and low memory priority on managed background attempts (HINT); deferral of GPU work (`uses_gpu`; EX-03's deferral stage); outside EX-26, jobserver shedding of build concurrency by RM-11's jobserver stage (accepted future work on 2026-10-19, §19, decision 27; exploratory until its lab gate). **Never:** affinity or CPU sets, multimedia scheduler classes, power plans, timer resolution, or the game's own priority.
- **Admission conditions** ("when idle", "on AC power", "outside work hours", "no game running") are inputs of the same family, admission-only, with deferral bounded by aging; they belong to EX-26 stage a.
- **Measurement honesty:** no frame-rate claim; frame rate and power are not measurable at P0; "boosted the game" is never written. Gate G50 decides per OS whether the guard is offered at all, on a benefit beyond run-to-run spread, with the build cost stated; LAB2-X-08 (the actions that break agent-like work) must pass before any action becomes a default. Over-throttling is the likeliest harm. **The baseline to beat:** pausing the `agents` pool by hand.
- **Launchers and DRM:** a launcher, a store URL or a bootstrapper creates the game outside the attempt, and a direct launch skips an anti-cheat bootstrapper, so L3 is not generally available for games.
- **Game sandboxing** is a later question inside the GUI stages of EX-10 and EX-11 (E5 in general; never for titles protected by kernel anti-cheat), not a rejected direction and never a precondition of the guard.

## 11. Interactions between applications

- **Delegated tasks with inherited floors.** When an application hands work to another (a render, a compilation), the target runs at `meet(requested, profile(caller), profile(target), floor(target))`, with no access to the target's private state; this closes confinement laundering ([17](17-delegated-execution.md) §7.2 rules R1–R7; EX-09, a stage).
- **A hand-off broker for confined applications** keeps confined messaging and document applications usable when they open a link or a file; it is never stronger than the display, desktop and forwarding cells, and a standing rule to an unconfined target is itself a launcher cell (EX-09, a later stage, after LAB2-X-10 shows it beats the in-process baseline; G48).
- **Shared-service exposure.** A reachable service's reach is the caller's reach, shown on the caller's card (EX-27 stage b).
- **Controlled interaction** is exactly the set of `ipc` grants between workloads ArcForges launched, plus the hand-offs and delegated tasks the node starts for a calling attempt ([17](17-delegated-execution.md) §8.3).
- **Not built:** a mediated clipboard or a general mediated drag (AD-0017 boundary 3.11).

### 12.3 Compatibility, per class, never per window

- **Windows rungs (estimates):** first-party applications designed for confinement, high; portable, medium; closed-source, low; applications needing administrator rights or drivers stay UNCONFINED.
- **Formats decide more than windows.** Installation formats confine nothing; confinement is decided at launch. Full-trust MSIX can still access most system resources directly. Win32 app isolation is a preview, on Windows 11 24H2 or later; it falls back to full trust on earlier builds, so a package is reported confined only after a token read-back, and sideload trust of a test-signed package is a P1 step. On Windows a profile-wide or Roaming-wide live grant is not offered (`user_path` is copy-in, copy-out or refused, [17](17-delegated-execution.md) §7.1); the always-forbidden set's shell-profile and `.git/hooks` entries apply to GUI applications unchanged; the Startup folder and Start Menu programs under Roaming AppData join the always-forbidden set at EX-10's GUI stage, and the APPDATA decision never grants write access to them. On Linux, `no_new_privs`, set in every tier, defeats setuid helpers, so an application that needs one is refused with the reason (`APP_NEEDS_SETUID_HELPER`), never run silently weaker; AppImages run through extraction, never `/dev/fuse`; `.deb` and `.rpm` applications under `/opt` are the primary closed-source class; Flatpak and strict snaps are delegated, never nested; classic or devmode snaps are no confinement; a write grant on all of HOME is escape-class in every tier. "Launch at login" and "make default" silently do nothing in a view, and the card says so.
- **No compatibility share is stated** before LAB2-X-01 (with LAB2-WIN-06, LAB2-LNX-13 and LAB2-LNX-19) runs, and then only per class, OS and display system, under chapter 17 §11.2's corpus rule (80/60).

### 12.4 Media, IDEs and services

- **Media.** Batch renders (Blender in background mode, FFmpeg, HandBrakeCLI, `melt`) fit the delivered attempt container today as `COMMAND` tasks in managed placement; a render started from a GUI inherits the GUI's placement and cannot be split out without cooperation (child-match splitting is rejected as racy); real-time audio cannot take a CPU cap (buffers of 1–5 ms do not survive a quota stall), so `realtime_threads` turns a number into a weight; capture applications get owner placement and a weight, never a freeze; no frame-rate, GPU-time or I/O-priority guarantee at P0; a capped software-rendering fallback moves CPU and memory inside the limit, and the card says so where known.
- **IDEs.** An IDE is one process tree: hosts, language servers and terminals stay in its container, with owner placement, a weight, soft memory and `OOMPolicy=continue` (one helper kill must not close the IDE). **Commands started inside the IDE, AI agents included, run under the IDE's owner placement and escape admission and the root cap**; the card says "commands started inside this IDE are not under ArcForges' managed limits; use `arcforges run` for work you want managed". Build daemons are hand-off routes (`persistent_helpers`). A heap the IDE sets itself from a value ArcForges did not give it is an external limit in a diagnosis ([07](07-records-diagnosis-memory.md) §4). Indexing yields only through the IDE's own controls or an extension using the protocol (L5). Confining a whole IDE is E5.
- **Long-running services.** `SERVICE` tasks in managed placement with the background class; owner placement by the owner's choice; the restart policy of §7.4 with one restart owner; model servers as managed services the guard may defer or stop (mapped weights reclaimable, locked weights not, VRAM not limited); an access grant inside a sync root is egress, and confining a sync engine is rejected (its function is the whole root); container desktops: only the VM worker is measurable, and ArcForges suggests, never writes, its configuration; tray utilities restart never.

### 12.5 From "compatible" to "default", one measured class at a time

**"First-class candidate", defined operationally:** no rule excludes an application for having windows; every class is in the corpus; every class gets the same realization rows; compatibility is measured class by class, OS by OS and display system by display system. It does not mean that every application will run confined.

| State | Entry criteria (all, per class, OS and build class) | What the owner sees |
|---|---|---|
| **Unconfined, labelled** (today's default) | — | Held + Limits + Diagnosis; Access "not restricted (same-user tier)" |
| **Opt-in per Installation** | Allowed as soon as the backend's GUI stage is promoted, before the class's launcher cells are measured, as an owner opt-in labelled per dimension with the cap and the routes on the card (§19, decision 21) | "Confinement available for this application (cap: …)"; local compatibility memory per run |
| **Default for the class** | The four criteria below; ≥ 80 % of the class's corpus; the editions check; the lock-out rules in force; an owner decision | The class preset proposes CONFINED; the owner confirms per Installation |

**The four promotion criteria:** (1) **compatibility:** the class's corpus in LAB2-X-01 meets the 80/60 rule with derived grants and no per-application tuning; (2) **escape cells:** every launcher cell of the build class, display cells included, is measured denied, or the owner accepts a default that holds against {A1, A2} only, stated on the card together with any routine routes; (3) **cost:** the class's reference applications stay within the owner's ceilings (§15) and within the X % rule for batch work inside them; (4) **diagnosis:** the class's failure signatures are calibrated in LAB2-X-13 (no wrong CONFIRMED; the share that reads "cannot tell" measured). **Rejection:** if LAB2-WIN-06 misses its pass line and its appSilo comparison shows AppContainer-inherent breaks, third-party GUI confinement on Windows stays owner-opted and labelled per application. A class whose failures come from its function (sync engines, applications that need administrator rights or drivers) stays unconfined by function, with the reason, and keeps every other facet. Capture tools and assistive technology are not proposed for a class default; they stay an owner opt-in per Installation where their corpus runs, with the expected break stated. **The order of broadening:** first-party applications; cooperating third-party applications that follow the confinement-ready guideline (§13.5); vendor-packaged applications whose OS sandbox ArcForges reports; unmodified applications, only where the criteria hold. It never broadens by assuming that a first-party result transfers.

### 12.6 The honest near-term offer

Near-term, ArcForges offers every compatible application, GUI or headless, first-party or closed-source, owner-directed resource control and supervision with stated, read-back values and evidence-bounded failure diagnosis, on Windows and Linux, launch first and attach after its labs. It offers access confinement first to its own first-party applications and reports the confinement of packaged applications whose sandbox the vendor ships. It offers confinement of compatible third-party applications as an owner opt-in, labelled per dimension, at the Contain promise, whose compatibility is unknown until the corpus labs run. It does not protect against an application designed to work against the owner, and every card says so. "First-class candidate" means that a GUI application enters the same pipeline as headless work, gets the same per-dimension values, and is never refused or weakened because it has windows; it does not mean that most closed-source GUI applications will pass.

## 13. The first-party strategy: ArcSlate as the reference, staged

"My own applications, including ArcSlate, must be included in the long-term vision." (the product owner). Everything below is reference design (E4) for later first-party decisions; **nothing changes ArcSlate**.

### 13.1 Starting point and rules

- **ArcSlate today** is a one-window Native AOT Avalonia bootstrap that shows a screen and makes one gRPC-Web call: no files, pickers, workers, media pipeline, node client, installer or package identity (D2-first-party-15). On Linux it is an X11 client as built, because Avalonia's Wayland backend is experimental (D2-first-party-13). The strategy is green-field guidance, not a migration.
- **Usable without ArcForges, always.** Every first-party application starts, works and stays secure at its own level with no node installed; ArcForges adds management, cooperation and ArcForges-owned confinement and is never a prerequisite. One binary, two modes chosen at run time: launched by ArcForges, it connects only to the endpoint it is handed; launched by the user, it may find the user-wide endpoint, never auto-starts the node, and treats "no node", "incompatible" and "access denied" as normal states.
- **No common sandbox backend is assumed** for first-party and third-party applications. The first-party path is the one that can be adapted to a backend; the third-party path takes applications as they are.
- **The ArcForges Desktop is not one of them.** It is the HUMAN surface and never a confined attempt (R6).

### 13.2 Why first-party applications are the reference: routine routes removed by design

A first-party application is the only place where the application's own design removes routine use of launcher routes. It removes by construction only what the application itself owns (its registrations, its settings, its data root, its display choice, where it parses content); every route the OS owns stays a measured cell.

**Routes the application's own design stops using (routine reach removed; OS-owned cells stay measured):**

| Launcher cell or gap | First-party design rule | What it removes |
|---|---|---|
| Notification activation; tray | Do not register unpackaged notifications or a tray icon outside the container; or ship packaged with the vendor-documented capabilities | The app-owned toast registration: removed by construction |
| Shell launches; URL hand-off (egress under `net{none}`) | No shell launches from the confined process; hand-offs only through an ArcForges broker with inherited floors (§11) | Routine reach removed; the brokered cell stays measured |
| In-process file dialogs that see only granted folders | A brokered picker: the dialog runs outside the container and returns a handle or a grant; files only through Avalonia's storage streams and bookmarks | Routine reach removed; the picker broker is cooperation with ArcForges |
| Hostile content parsed in the UI process | Media and document parsing only in content workers, with or without ArcForges | Worker parsing: removed by construction |
| A content-worker job with UI limits, which fails closed inside any ArcForges job | Drop the job UI limits and set the Win32k system-call-disable mitigation, which removes the window-manager system-call surface; it is not shown to cover everything UI limits did (the global atom table), and whether the runtime starts under it is unverified (LAB2-WIN-09) | The nesting conflict, if LAB2-WIN-09 passes |
| `LOCALAPPDATA` left to OS rerouting | One data-root resolver (the launcher's root, the container folder under a stable per-Installation identity, or the per-user path without ArcForges) | The data root: removed by construction |

**What stays measured even here:** the cells the OS owns. On Windows: WMI, Task Scheduler, COM activation, WSL interop, the window-message filters of unconfined receivers (ArcForges' own UI included), brokered handler classes (COM `DelegateExecute`, packaged activation, the WinRT `Launcher`, `runas`), forwarding to a running instance, the print spooler, the visible-caller activation APIs and the preview surrogate. On Linux: the compositor's withholding, the bus, and portal OpenURI and OpenFile where a bus or portal is granted. First-party design narrows routine use; it does not close those cells. A confined first-party window's `net.out` stays PARTIAL until LAB2-WIN-05 and LAB2-WIN-06 deny these routes; those two labs are the A3 and `net.out` gate of a first-party Windows GUI realization. So Distrust for any GUI realization, first-party included, waits for the launcher-cell labs on the build class. "First-party first" is not "first-party already A3".

**A capability list per release** is the first-party application's declared expectation of its grants. The node compares it with the realization read back at launch and raises a finding on any difference: a comparison of existing data, not a concept, which turns "the profile is what the app needs" from an assertion into a check. It is also why first-party grant profiles ship with the application and never in an ArcForges catalogue (AD-0017 boundary 3.13).

### 13.4 First-party resource integration

- **Placement of its parts:** the UI process in owner placement; heavy work (export, render, proxies, transcription) as managed tasks of its own worker executable with clamped hints, an owner-assigned pool, preemptible and pausable with checkpoints; the admission decision is the grant (`cpu_granted` sets the worker's parallelism) and completion releases it; playback decode stays inside the UI's container, where the owner's limit covers it without cooperation; the UI is never pausable by default.
- **The UI's own process** uses the cooperative family through the C# SDK: a designated declaration during playback, an enforced grant to raise its own container's memory for a large timeline within the owner's maximum, Watch for shrink notices.
- **The runtime honours the owner's number even under a soft limit:** a cooperating first-party application reads its budget and sets `System.GC.HeapHardLimit` at start, and calls `GC.RefreshMemoryLimit()` after a hard limit changes. It reports both over its endpoint, so a failure diagnosis treats that heap as a cooperative budget, not an external limit ([07](07-records-diagnosis-memory.md) §4). This is the one place where L5 closes a gap owner-directed control leaves open.
- **Diagnostics get better, not stronger.** A first-party application can report its rendering mode, its heap limit and a handled refusal that disabled a feature without a crash; all of it is application-asserted, decisive at most for PROBABLE, never CONFIRMED.

### 13.5 From first-party to third-party, without a catalogue

- **A published "confinement-ready" guideline** (documentation only; an exploratory approach): the §13.2 design rules written for any developer. An application that follows them is designed to run under the Windows and Linux backends and OS packaging (E4; unmeasured until LAB2-X-01 and, for the picker, LAB2-WIN-08). The rules do not address every break class (named objects, out-of-process COM, loopback, registry, fonts), so compatibility is still measured per class. It needs no ArcForges SDK for resources. Under W2, access to the user's files needs either folders the owner granted or the ArcForges picker broker, and hand-offs need the ArcForges hand-off broker; both are cooperation with ArcForges through its endpoint. On Linux, §14.2's compatibility surfaces and their costs apply: an X11 build's input methods need named portal grants (escape-class before LAB2-LNX-20); a Wayland-native build gets input methods through text-input-v3 where the compositor and toolkit support it (Avalonia.Wayland's support unverified); withheld accessibility means silent screen-reader loss. The guideline aims to widen third-party compatibility through vendors' own design choices instead of an ArcForges-maintained profile catalogue.
- **The same pickers and brokers serve both:** the Windows picker broker and the Linux Documents-portal broker are offered to any cooperating application, first-party first. On Windows a picker broker helps only cooperators: a third-party in-process dialog still sees only granted folders.
- **Open first-party decisions, never taken here:** ArcSlate's opt-in to the Wayland backend; which builds ship (Flatpak, archive, MSIX with app isolation, App Sandbox); code signing or an installer (the identity anchor a user-launched copy needs to cooperate); whether it ships notifications or a tray icon; its storage layout; its SDK use.

## 15. The interactive cost measure

**Completion time does not price interactive applications.** AD-0017 principle 9 bounds a CONFINED default at X % in median completion time; for interactive applications and games the cost of a resource policy or a confinement is start latency, input latency and frame-time tails. An application class therefore carries both: the interactive cost measure for its interactive surface, and X % for batch work inside it.

**Definition:** the application under a policy P (a resource policy, a confinement, or both) against a baseline B (the same application, venue and load, launched as the owner does, with no ArcForges limit or confinement), as P − B and P / B with spread: **ICM-1** start latency to the first frame of a top-level window, warm and cold; **ICM-2** input to displayed frame; **ICM-3** frame-time tail and stutters; **ICM-4** hangs; **ICM-5** CPU inside and outside the container; **ICM-6** memory inside the limit, ArcForges helpers outside, and node cost per application; **ICM-7** persistent cost; **ICM-8** real-time deadline misses for the `realtime_threads` trait. The product sees only proxies, and no surface calls a proxy "ready" or "input latency". A GPU-less lab VM renders in software, so results from it read "software-rendered venue"; the GPU path needs neutral lab hardware, a requirement and never a purchase.

**Ceilings, set by the owner as X is** (§19, decision 13; the proposed values): **Y-start** warm p50 increase ≤ max(100 ms, 10 % of baseline), cold reported, more than 1 s shown on the card; **Y-input** p95 increase ≤ one refresh period (16.7 ms at 60 Hz), p99 ≤ 50 ms; **Y-frame** p99 increase ≤ one refresh period; **Y-hang** zero new hangs; helpers outside the application ≤ 10 MB per application ([15](15-performance-targets.md) §2); memory inside the limit never bounded silently. They bind only application-class defaults (gate G20-I). A verb default is measured at the number the node would suggest, from peaks in runs where no limit acted, in an uncrossed and a crossed scenario; a THROTTLE default passes Y-hang only in the uncrossed scenario, and its crossed cost is shown on the card. Linux L4 per-view helpers may exceed the 10 MB helper ceiling until LAB-LNX-19 measures `exec-init`. Never "faster", "no overhead" or "+N % FPS"; an unmeasured cost reads "cost unmeasured", never "negligible".

**Bounds from vendor semantics** (estimates): under sustained load at 0.5 CPU, k runnable threads run Q/k and then wait P − Q/k, so a busy application's input can wait 50–97 ms at P = 100 ms and 10–19 ms at P = 20 ms, which is why 20 ms is the interactive default; for short bursts the long period is faster, which is why LAB2-LNX-05 decides it; a cap does not limit GPU time, DWM, audio or display-server work; a software-rendering fallback moves CPU and memory inside the limit.

**Maintenance** (probe, never compare versions; unknowns fail toward the weaker claim): compositor audits (withholding source-verified for few compositors; stop crediting A3 if results change more than once a year, LAB2-X-15); launcher unit names; first-party grant lists per release (a third-party catalogue is rejected); diagnosis rules per OS capability set; no anti-cheat or launcher list shipped; one SDK language until two external integrators; launcher cells re-measured per Windows feature update; fix gates for bubblewrap, the D-Bus proxy, Flatpak and PipeWire, continuous and security-critical. **The GUI compatibility corpus** (LAB2-X-01 with LAB2-WIN-06, LAB2-LNX-13 and LAB2-LNX-19) is re-measured before a class default is kept on a new build class (a Windows feature update; arm64 as its own build class) or a new supported distribution release: a High cost, recurring. The simpler alternative: no class defaults; confinement opt-in per Installation with local compatibility memory ([07](07-records-diagnosis-memory.md) §4). Beside it: the Chromium-family branch re-measured per family (§6.4, LAB2-WIN-10; Medium) and the picker and hand-off brokers kept working per OS release (§13.5; Medium).
