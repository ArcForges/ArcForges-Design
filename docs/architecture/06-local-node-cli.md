# Local Node, CLI and terminal sessions

Status: current V2 design. AFV2-CORE-01 through AFV2-CORE-03 implement the common core and Run owner; AFV2-CLI-01/02 deliver Core/admin commands and terminal behavior; AFV2-FILE-01/02 add data and deletion commands with their actual implementations; AFV2-CENTER-02 adds typed Center control. SDK/profile qualification is a prerequisite, not an assertion of present terminal compatibility. [Resource](04-resource-management.md), [filesystem](05-filesystem-data.md) and [lifecycle](07-lifecycle-recovery.md) define the shared behavior.

## 1. First-class local use

The local CLI is the normal product entry point. The default target is the current user's local Node. Listing/creating/configuring Sandboxes, starting/stopping Runs, terminal interaction, resource observation and owned-data operations require local authorization but no account, subscription, Center connection or remote token. Signing out, an expired official subscription and an unreachable Center do not stop local Runs or disable local commands.

Center connectivity is an optional Node subsystem. Remote requests and local requests enter the same typed command dispatcher and Sandbox Core. The remote transport performs its own authentication/authorization and attaches a verified principal; it does not bypass local policy or call a raw host command runner. A remote command may execute arbitrary argv **inside an already authorized Sandbox profile**, which is distinct from an unrestricted host shell.

Remove current HUMAN-only diagnostic submit restrictions and the old Task/Attempt route. Do not expose `--test-mode`, fake HUMAN classification or `ARCFORGES_TEST_ALLOW_LOCAL_SCRIPT_SUBMIT` as ways to use the product. Generic scripts, interactive terminals and AI CLIs are ordinary local callers with the same user-granted Sandbox boundary; the core does not infer AI session identity.

Current contrary behavior is source-backed: [LocalSubmission](https://github.com/ArcForges/ArcForges/blob/10f692224f94916cfc93fbad971f80ec340c5edf/src/ArcForges.Node.Core/LocalSubmission.cs) and [RunCommand](https://github.com/ArcForges/ArcForges/blob/10f692224f94916cfc93fbad971f80ec340c5edf/src/ArcForges.CommandLine/RunCommand.cs) at the audited baseline.

## 2. Composition and dependencies

The product retains one `arcforges` CLI/Node host and the necessary platform service bootstrap. A durable internal RunSupervisor process owns each Run's official backend, terminal master/pipes, resource-scope identity and finalization record. It is a trusted implementation detail launched by the Node through a fixed executable and a private capability-bound handshake, not a second public CLI or arbitrary remote helper. Windows' existing service supervisor may remain as infrastructure; it is not a desktop client.

The Node owns Sandbox configuration/storage metadata, the single-writer command processor, operation receipts, recovery, Resource Manager, local API and optional Center link. It holds no exclusive terminal handle whose loss would kill a Run merely because the Node restarts. The RunSupervisor persists only the bounded facts needed for Node rebind and recovery; the Node remains authoritative for product state and permissions.

The local endpoint reuses DesktopPlatform LocalRpc service mode: current-user Windows named pipe or Unix-domain socket in an owner-only directory. Verify the OS peer identity; no unauthenticated loopback TCP fallback. Preserve bounded control lanes so stop, detach and health cannot wait behind large file transfers or terminal viewers. The Node exposes V2 Node/Sandbox/Run/Resource/Data operations and the fixed local-only V2 CenterControl adapter; delete old task/queue/workspace/Fleet and general Node-v1 method registrations after the compatibility cutoff.

## 3. Node startup and stop

Startup resolves and validates the owner configuration/data root, obtains the per-user singleton, opens the store with its existing backup/forward-migration checks, compares boot identity, reconciles persistent Sandbox and Run ownership, then publishes readiness. While recovery is in progress, read-only health/state calls may respond with `recovering`; new Starts and destructive mutations remain refused. Independent healthy Sandboxes may become available once their own reconciliation is complete; an unresolved Run keeps its Sandbox blocked from deletion.

Autostart reuses the installed user-service/supervisor mechanism. If OS/session policy prevents safe autostart, return `node_unavailable` with the explicit manual `arcforges node start` remedy. Do not bypass a foreign Job, impersonate another user, elevate silently or install services without the normal installer path.

`node stop` requests Node shutdown while allowing durable supervisors to continue under their existing immutable policies by default. `node stop --stop-runs` is a distinct explicit operation that requests orderly Run stops and reports any unresolved scope; it is not silently performed on sign-out. Host reboot does not restart Runs automatically. Upgrades drain old binaries and negotiate ownership/rebind as defined in the lifecycle and migration design.

## 4. Command surface

Each row names fixed typed business operations or the local installed-service bootstrap; none dispatches arbitrary host commands. Exact short aliases may be added only where unambiguous. Durable mutations print their command ID **and owner epoch** on diagnostic/JSON output. Transient terminal calls return lease/sequence acknowledgements and have no durable operation to inspect.

AFV2-CLI-01 delivers Core/admin CLI mapping, JSON and target/receipt handling; AFV2-CLI-02 delivers actual terminal commands. AFV2-FILE-01 delivers usage/list/import/export/transfer CLI together with its data implementation, and AFV2-FILE-02 delivers deletion preview/apply/resume CLI together with guarded deletion. CenterControl registration and its actual `center` commands are delivered together by AFV2-CENTER-02. Do not register empty file/deletion/connection placeholders in an earlier task. The V2 adapter reuses the existing [CloudLinkService](https://github.com/ArcForges/ArcForges/blob/10f692224f94916cfc93fbad971f80ec340c5edf/src/ArcForges.Node.CloudLink/CloudLinkService.cs), [SignInOrchestrator](https://github.com/ArcForges/ArcForges/blob/10f692224f94916cfc93fbad971f80ec340c5edf/src/ArcForges.Node.CloudLink/SignInOrchestrator.cs) and [typed CenterClient enrollment calls](https://github.com/ArcForges/ArcForges/blob/10f692224f94916cfc93fbad971f80ec340c5edf/src/ArcForges.Node.CloudLink/CenterClient.cs), plus protected credential/cloud-link/key files. It exposes no token, PKCE secret, general host action or old Node-v1 dispatcher. Connection origins/modes are explicit; credentials cannot silently follow a changed Center. A sign-in URI/device code is a transient local flow response and never a durable receipt/audit field.

Global `--json` selects versioned machine-readable results; command data goes to stdout and diagnostics to stderr. Terminal raw output and JSON control output are never mixed on one stream: `run start --json` returns the start receipt/Run ID, and a separate attach command owns the terminal. Commands accept explicit timeout/cancellation, with unknown-effect results when the deadline passes after dispatch. Durable requests preserve the original owner epoch, command ID and canonical request; the caller can inspect that original operation and must not mint a new Start ID or replace its epoch after a timeout. Known compacted responses return `STATE/receipt_compacted` with retained original identity/effect and no reexecution. Transient terminal uncertainty follows §7 and cannot be resolved through GetOperation.

The default is local. A global `--device <id>` selects a remote registered device through the explicitly configured/authenticated Center; `--center <origin>` disambiguates that existing authenticated target and never switches credentials implicitly. The CLI displays the remote target before destructive confirmation. A remote target never silently falls back to local if offline. Remote device status and authorization failures are distinct from local Node health. These options route typed operations, not SSH or a raw command tunnel. Node process/service commands, doctor, grant expansion, ERROR repair, deletion resume and CenterControl are local-only; an incompatible remote target is a validation error.

Remove old `tasks`, `queue`, `jobs`, session/agent, dependency, retry, toolchain, compiler-cache, worktree and placement options from help/completions and code. Do not leave deprecated commands as permanent no-op shells. The compatibility document gives the one-time migration mapping.

## 5. Start snapshot and effects

`RunService.Start` requires Sandbox ID, expected configuration revision and the persistent owner epoch; argv (or an explicit shell program and script), working directory relative to an allowed directory, validated environment overrides, terminal mode/initial dimensions and resource request including preemptibility. The CLI obtains an epoch for a fresh intent through Handshake and saves it with that intent; an old intent never adopts a newer epoch automatically. Attach/detach is a client decision after the Start result, not a different execution policy or lifetime. The default working directory is owned `work/`. Executable lookup uses the validated Sandbox environment/profile, not arbitrary Center environment or Node secret-bearing process variables.

Persist the final redacted argv/environment/profile/grants/resource snapshot and its digest before user code may execute. Explicit secret injections are referenced by protected local secret identity/version and delivered only to the owner launch handoff; do not store plaintext secret environment in the snapshot. Sensitive values are excluded from ordinary audit/telemetry; the API returns redacted display fields. The snapshot includes official SDK/executor version, backend/profile identity and capability evidence reference. One Run cannot switch profiles mid-execution to bypass an unsupported capability.

Start returns an operation receipt and Run ID. `payload_started` uses canonical UNKNOWN, NOT_STARTED or CONFIRMED according to trusted evidence; an official executor's existence does not by itself confirm that the sandbox payload reached execution. Inspect displays `safe_command_display` (executable basename plus redacted argument count by default), the bound Sandbox revision and profile version. The display is not the executable request and cannot be copied as an exact replay. All errors include effect certainty. A definite pre-launch refusal becomes FAILED and releases reservations after confirmed no effect; uncertainty becomes RECOVERY_REQUIRED until ownership reconciliation. Nonzero payload exit after confirmed execution is still EXITED, not a launch failure.

## 6. Genuine terminal modes

`--terminal auto|on|off` selects terminal behavior. Auto uses an actual terminal only when the initiating CLI has an interactive terminal and the selected profile supports the qualified terminal mechanism. If an interactive terminal is requested but unavailable, refuse with `STATE/terminal_unavailable`; do not silently claim a pipe is a terminal. Off uses ordinary stdin/stdout/stderr pipes, useful for redirection and machine scripts. Terminal mode emits one PTY output byte stream; stderr is not falsely separated after the terminal merged it.

The Windows qualified candidate uses C# Native AOT RunSupervisor plus unchanged official `wxc-exec.exe` under ConPTY, with explicit published configuration and fail-closed fallback policy. Linux uses the official published profile's supported terminal composition. These candidates become supported profiles only after AFV2-MXC native tests. Do not invent .NET SDK PTY/startup-attribute APIs or fork MXC. The official executor's stdout may contain workload bytes or backend messages; **never parse it as a trusted lifecycle/control channel**.

The RunSupervisor owns the PTY master for the full Run. CLI disconnect, loss of a viewer, Center outage or input-lease expiry must not close that owner handle. The program may block awaiting further input while detached. Reattach binds to the same live terminal and current output cursor. A terminal cannot be recreated around an already-running process after its real owner died; record that loss honestly.

Long-running services must keep their foreground root alive. The stable one-shot ProcessContainer backend finalizes when the root exits and stops remaining descendants. Background child processes are managed while the root runs, but daemonization/double-fork is not a promise of survival after root exit. Use `--detach` to detach the CLI while leaving the foreground program under its durable Run owner.

## 7. Terminal leases, input and resize

AcquireTerminal, WriteTerminal, ResizeTerminal and DetachTerminal are transient operations owned by the live RunSupervisor. They never create a durable command receipt or GetOperation result. There is at most one write lease per Run terminal, with caller identity, opaque lease ID, generation, 30-second renewable expiry and input/resize sequence high-water marks. Read-only observers have independent bounded output cursors and no input/signal/resize authority. A fresh attachment can observe current writer identity in privacy-preserving form; it cannot steal control automatically. Explicit takeover requires the authenticated local owner permission, revokes the old lease and increments generation. A safe audit event may record that lease authority changed, without input, input-derived hash or per-frame command identity.

Input frames are bounded bytes with lease ID/generation, command ID and sequence. Before a native write, the owner consumes the sequence and retains a volatile comparison/result slot. Within the live acknowledgement window, the same ID/sequence/request returns its original acknowledgement without another write; a conflicting replay or sequence gap is refused. Cache size, retained comparison bytes and age are bounded by fixed local policy; entries expire no later than the 30-second window or lease generation invalidation. Volatile equality fingerprints are permitted only inside that memory cache. No raw input, input-derived hash, acknowledgement cache or per-frame transcript goes to the database, control record, audit, telemetry or support log.

If an acknowledgement was evicted/lost, a native write became uncertain, the Node restarted or the supervisor died, return `EXECUTION/terminal_ack_unavailable` with UNKNOWN effect and no automatic retry. The consumed-sequence high-water mark must not turn a missing acknowledgement into a new write. `accepted_bytes` records only a known native result; a sequence mark alone does not prove byte delivery. The CLI stops automatic input forwarding on uncertainty, explains that earlier input may have arrived, and requires an explicit fresh attachment/continuation decision. It must not resend old bytes under a new command ID, sequence, lease or owner epoch. GetOperation cannot recover terminal input. Acquisition/release also have only bounded live acknowledgements; after that boundary there is no exactly-once claim or recovered old authority.

Resize requires a valid writer lease, positive bounded rows/columns and a monotonic resize sequence. It uses the same volatile acknowledgement discipline and cannot restore a stale generation. The owner applies the native terminal resize and reports the result; a read-only observer cannot resize the application. On platforms that cannot resize a particular profile, report unsupported and keep prior dimensions. Node rebind invalidates all terminal leases/acknowledgement authority; reacquisition never establishes whether a prior uncertain input or resize happened.

Ctrl+C in attached terminal mode is delivered to the terminal's foreground application using the qualified native terminal mechanism. It is not automatically translated to a whole-Run cancel command. In pipes mode, the CLI's interrupt can request the explicitly documented Stop operation. The default local detach escape is Ctrl+] followed by `d`; document how to send a literal escape and allow disabling the escape handling for raw workflows. An explicit `run stop` always remains available through the reserved control lane.

For pipe mode, EOF is explicit `WriteTerminal(close_stdin=true)` owned by the input lease, mutually exclusive with input bytes and using the same sequence/acknowledgement rules. Detach and connection loss do not implicitly close stdin. Terminal mode preserves the PTY; an EOF character is input interpreted by the terminal/application, not a fabricated transport close.

## 8. Output retention and backpressure

Frames carry Run ID, stream kind, byte offset, length and generation; retained terminal bytes and piped stdout/stderr have documented independent cursor spaces. The transport uses bounded frames and per-subscriber queues. When a viewer falls behind, discard that viewer's queued copy and emit GAP with the earliest available offset; do not block a running application forever because one remote browser stopped reading. File-backed retention has an explicit per-Run byte cap and rotation policy. Reaching the cap emits a retention event and advances the earliest cursor; it never silently claims a complete log.

Raw output is untrusted. Web renders plain escaped text or a constrained terminal emulator, never raw HTML. Terminal escape sequences may influence a terminal display but cannot become trusted Node control messages. Binary bytes are permitted in pipe logs; text decoding errors must not corrupt byte offsets. File transfer and telemetry channels are separate from terminal bytes.

The program/terminal may echo user input into its output; those bytes are ordinary output subject to the selected output-retention policy. ArcForges never creates a second input transcript or fingerprints input in durable control records. The absence-of-input-records acceptance probe disables terminal echo and uses a program that consumes input without printing it, so it tests the control path without confusing legitimate program output with retained input.

A terminal byte transcript is not a full screen-state snapshot. A reconnecting TUI receives recent bytes plus a resize/redraw request when supported, and the user can request redraw; do not claim perfect screen reconstruction from a truncated tail. The V2 remote surface watches output and controls Run lifecycle but exposes no terminal input/resize or browser terminal. A remote CLI attach request is refused as unsupported; it may explicitly watch read-only output instead. No secret-bearing terminal screen state is automatically recorded remotely. Output read/stream access requires the same Run authorization as inspection and is audited at the operation level without logging the content.

## 9. Exit and error presentation

Run state and raw exit observation are separate. Record `exit_source` (`payload`, `official_executor`, `supervisor`, `unknown`), raw exit code/signal when observed, `payload_started`, termination reason, timestamps and effect certainty. The CLI mirrors a trustworthy payload/executor exit according to its provenance and OS shell range; it prints a clear message when only wrapper failure or cleanup uncertainty is known. An unknown result is not success merely because a wrapper returned zero.

Control-command exit mapping is stable and documented: 0 confirmed successful requested control effect/read; 2 usage/validation; 3 conflict/revision, in-use or compacted-response refusal; 4 authorization; 5 unsupported capability; 6 resource unavailable; 7 transport/Node unavailable; 8 operation effect, terminal acknowledgement or cleanup uncertain. A compacted replay still prints the original known effect/aggregate; it never claims a new execution. `operation inspect` can successfully display that retained metadata. An attached Run's process-exit mapping is a separate channel and does not reuse these values as product control semantics. A detached Start exits 0 only for confirmed acceptance and prints Run ID, command ID and owner epoch; the Run can later fail and must be inspected.

## 10. Acceptance

AFV2-CLI-01 proves every applicable local Core/admin action in the table while signed out, without a Center, and with expired official entitlement; all must reach the same Sandbox Core and respect filesystem/resource policy. Include resource set, grant set/list/revoke, durable operation inspection, doctor and guarded ERROR repair, plus JSON stability, help/completion removal, target disambiguation, post-compaction/restart Start replay, stale owner epoch, immediate resource refusal and recoverable timeout effects. Data CLI acceptance belongs to AFV2-FILE-01; deletion preview/apply/original-journal resume CLI acceptance belongs to AFV2-FILE-02 after their implementations exist. AFV2-CENTER-02 proves the six CenterControl mappings against real retained identity/enrollment code and the declared external fixtures; no placeholder center commands close CLI acceptance.

AFV2-CLI-02 proves genuine native terminal behavior: shell and full-screen TUI, raw input and Unicode, foreground Ctrl+C, window resize, stdin EOF in pipe mode, byte-exact piped output, detach/reattach, writer contention/takeover, stale lease refusal, slow viewer backpressure, GAP recovery, canceled attach, Node restart with the same live owner, root exit with background descendants drained, and offline Center while a local terminal remains usable. Include acknowledgement-window expiry, partial/unknown native write, owner/Node loss, no automatic retry under a new lease, and inspection of durable storage/audit to prove absence of raw input and input-derived fingerprints. Use actual PTY/ConPTY on the designated native hosts; tests that use only ordinary pipes do not close terminal acceptance.
