# 16 — Testing strategy

Decisions: [AD-0014](../decisions/AD-0014-delivery-method.md) (verification responsibilities, fakes only at unavailable boundaries), [AD-0016](../decisions/AD-0016-local-first-verification.md) (local-first verification, testing techniques). Requirements: R-TEST-001..003.

**Development-stage target:** complete functionality proven by automated closed-loop tests. Fakes are used only where a real external environment is unavailable. The OS secret stores are unavailable to routine tests by the user's decisions of 2026-10-17. Only the separate OS secret-store integration tier (§1) reaches them, behind a fail-closed structural guard, and everything else uses the isolated secret-store backend (§2). Practical real tests run on the Windows workstation and on a native Linux host ([AD-0018](../decisions/AD-0018-native-platforms-without-wsl-integration.md) §5). Final real-world user acceptance comes later, through the Plan's acceptance register.

Coverage-guided fuzzing and mutation testing are not adopted now; the reasons and the conditions for revisiting them are in [AD-0016](../decisions/AD-0016-local-first-verification.md) §5.

**OS secret-store integration tier** (the user's decisions of 2026-10-17, quoted in [AD-0016](../decisions/AD-0016-local-first-verification.md) §5, amendment). Credential Manager stays the node data key store. These rules govern only how tests reach real OS secret stores. The production read-back policy is separate ([04](04-execution.md) §2): every read-back and absence check below is **test verification only**.
- **Where it runs.**
  - The adapters' tier runs in **DesktopPlatform** (the `ArcForges.Security.Secrets` backends).
  - The node binding's tier runs in **ArcForges** (the node data key through `NodeDataKeyRing`, with a fresh random node ID per test).
  - Both run on disposable GitHub-hosted Windows runners for external PRs, manual dispatch and a weekly schedule. Linux Secret Service runs on the isolated Linux secret-store test host reached through the Linux MCP server, which carries the root-owned marker `/etc/arcforges/isolated-secret-store-test-host` ([AD-0019](../decisions/AD-0019-mcp-first-verification.md) §6; it replaces the `ArcForgesTest` WSL distribution).
  - DesktopPlatform's existing opt-in Credential Manager tests move into the tier, under its rules and its single opt-in name: today they use `ARCFORGES_LOCAL_OS_SECRET_STORE`, the production name format and a `cmdkey` sibling process (which then runs sequentially, inside the operation limits).
- **No suite other than the tier's own.** The tier's tests live in a dedicated project per repository, which the default suites' project globs do not match (in ArcForges, outside `tests/*/*.Tests.csproj`). They carry `[Trait("env","os-secret-store")]`. No default suite (`unit`, `ci`, `exclusive`, `store`, `node-core`, `all`, the real-OS and closed-loop suites), no pre-push profile, no repeat-mode run and no deep-tier run selects them. The guard below enforces this. Every other test that needs a secret store uses the isolated secret-store backend (§2), including routine and pre-push runs on the workstation.
- **Structural guard (fails closed).** The user's requirement: "Ensure that routine tests cannot access my real OS credential store" (2026-10-17).
  1. **One opt-in.** In a test process, the real OS adapters are reachable only through the tier fixture, and only when the opt-in `ARCFORGES_OS_SECRET_STORE_TESTS=1` is present. This one name serves both ArcForges and DesktopPlatform, and only the tier runner or the hosted tier job sets it. Any other attempt to reach a real OS store fails the test with the guard's error before any OS call. It never skips, and it never falls back to another backend. A node started with `--test-mode` follows the same rule for every OS-wide key or secret store it uses, the CNG user key store of the node key included ([02](02-node-service.md) §4). A stray value must not lift the guard for routine tests:
     - `eng/test.ps1` and `eng/test.sh` remove the variable for every suite except the tier's.
     - The host verification (the repository's step table; before 2026-10-22 the pre-push verification) refuses to run when the variable is set. The shared core stays unchanged; ArcForges and DesktopPlatform implement this in their step tables.
     - The hosted tier job sets it only on the tier's own test step, never at job or workflow level.
  2. **Runtime tripwire.** Every test project of ArcForges and DesktopPlatform, the tier's included, sets the AppContext switch `ArcForges.Security.Secrets.DenyOsStores=true`, for example through the tests' `Directory.Build.props` into the runtime configuration.
     - **What checks it:** the DesktopPlatform OS adapters (Windows Credential Manager, Secret Service), and from AF-LAN-01 the node key's CNG access. Each checks the switch before any OS call and throws the guard's error unless `ARCFORGES_OS_SECRET_STORE_TESTS=1` is set.
     - **Scope:** the tripwire applies to the user's stores.
       - Windows Credential Manager is always in scope.
       - Secret Service is in scope on the user's session bus: no explicit address, or an explicit address equal to `DBUS_SESSION_BUS_ADDRESS` or to the user's standard `unix:path=/run/user/<uid>/bus` socket.
       - Only a bus address that a test supplies explicitly and owns is outside it: a private daemon in a temporary directory, or a path that does not exist. Only reviewed allow-listed tests may supply one (item 3).
     - **Refusal:** `OsSecretStore.SelectForCurrentPlatform` propagates the guard's error. It never treats a refusal as an unavailable backend and never falls back to the file store, so "never falls back" (item 1) holds.
     - **Production:** release builds never set the switch, so production is unchanged.
     - **Delivery:** this is a DesktopPlatform adapter change, a new `ArcForges.Security.Secrets` package version that ArcForges admits ([AD-0016](../decisions/AD-0016-local-first-verification.md) §5, amendment of 2026-10-17).
  3. **Repository check.** A check runs in the host verification (formerly the pre-push hook) and in external-PR CI: `ArcForges.Repository.Tests` in ArcForges, and DesktopPlatform's `ArchitectureTests` policy. It fails when test, tool or benchmark sources outside the tier project do any of these:
     - reference `OsSecretStore.*`, `WindowsCredentialManagerSecretStore` or `SecretServiceSecretStore`, or (from AF-LAN-01) the node key's CNG API;
     - build a `NodeHost` without overriding `SecretStore`;
     - start a node without `--test-mode`.

     It also fails when any suite other than the tier's own selects the tier's tests. It permits only reviewed allow-list entries that cannot reach the user's store, each with its reason, for example DesktopPlatform's Linux selection tests over a private, test-owned bus.

     In production sources, calls to `OsSecretStore.*`, the two adapters and (from AF-LAN-01) the node key's CNG API may appear only at reviewed, injectable composition roots. Each of those roots follows the `--test-mode` and opt-in rule ([02](02-node-service.md) §4).
  4. **Negative test.** A routine test proves that an attempt to reach the real store fails with the guard's error. It tries three paths without the opt-in: the fixture, a direct adapter call (refused by the tripwire), and a node started with `--test-mode`. It also starts a routine suite with `ARCFORGES_OS_SECRET_STORE_TESTS=1` already present in the environment, and shows that the variable is removed and the access is refused. Because the guard decides before any OS call, the negative test itself never touches an OS store.
- **Opt-in locally.** On the workstation the tier runs only through the tier runner, with the opt-in set for that run. Without it the tier's tests do not run, and the selection reports them as not run with that reason. A local opt-in result is weaker evidence than the hosted run, because the workstation's store is shared with the user's applications. The hosted run is the tier's evidence. Linux Secret Service tests run only on the isolated Linux secret-store test host ([AD-0019](../decisions/AD-0019-mcp-first-verification.md) §6), never in the verification account, a WSL distribution or the user's session keyring.
- **Minimal and sequential.** One test at a time, in one process, with no parallel collection. No other test or node process of the run uses the store. Each test performs only the operations its contract needs. A fixture enforces hard limits per run: at most 4 test entries existing at once, at most 32 secret-store calls, a 10 s timeout per call and 5 minutes for the tier. Reaching a limit fails the run; it never continues past it.
- **Unique names within the canonical format.** The adapters accept only canonical targets: `ArcForges.Secrets.v1.` followed by 64 uppercase hexadecimal digits. A test entry is therefore named `ArcForges.Secrets.v1.` plus the uppercase SHA-256 hex of `arcforges.os-secret-store-test.v1|<run id>|<n>`, with a fresh random run ID. This is domain-separated from the node data key's `arcforges.node-data-key.v1|…`. Node-binding tests use a fresh random node ID, so their key names are new as well. **By name alone, test entries cannot be told apart from production keys.** They are distinguished only by the fixture's name list, which is written before each entry is created and kept with the run's evidence.
- **Safe cleanup with verified absence (test verification).** Exact-name cleanup from the fixture's list is the only safe cleanup. A test deletes only the entries on its list, by exact name, then reads each one back to verify that it is absent. A remaining entry fails the test and is reported by name. Cleanup never enumerates or deletes by pattern, and never touches an entry that is not on the list: production keys and unrelated credentials are never touched. A failed absence check is evidence (L-26). It is never retried.
- **Never stress or load.** No stress, load, soak or concurrency test runs against a real OS secret store, hosted runners included. Key lifecycle, sealing, failure injection and concurrency are tested against the isolated secret-store backend, and no test depends on a real store's behaviour under concurrent modification (L-26).

**Synthetic workloads are not fakes.** `TestLoad` (`tools/ArcForges.TestLoad`) generates deterministic CPU, memory, output and fork patterns as the *input* to the behaviour under test (scheduling, enforcement, capture, diagnosis). It replaces no external system, so every task may use it, and evidence names the workload that ran.

`IsolatedSecretStore` is never used for the adapters' own OS integration tests (§1), which exercise the real store. The owner-only file fallback under a test's temporary data root is not an OS store and stays real where a test needs it. Because routine tests cannot use the real OS secret store (the user's decision of 2026-10-17), this substitute stays within R-TEST-001 and [AD-0014](../decisions/AD-0014-delivery-method.md) §6 (as amended by [AD-0016](../decisions/AD-0016-local-first-verification.md)).

A fake is never used for the behaviour under test (R-TEST-001). Results from a fake-backed test are labelled `closed-loop` in evidence and never reported as real-world validation. The real billing flow on a Play-enabled emulator or device stays in the acceptance register (AR-06).

### 3.1 Local cloud stack

The cloud closed loop runs natively on the workstation and needs neither Docker nor WSL:
1. **Worker side.** `workerd` under Miniflare (the Cloud repository's local scripts) runs the Worker ingress, the relay routes, the `FleetHub` Durable Object, and local D1, R2 and Queue. Miniflare's local S3 endpoint, configured with test `s3Credentials`, serves the SigV4 presigned uploads of the support flow (F-C03 checks it first).
2. **C# host.** `ArcForges.Cloud` runs as a native process on a loopback port: the JIT build for most suites, the Native AOT binary for the AOT suites.
3. **Container shim.** In the local profile, the Worker's Container binding is replaced by a shim that forwards to the native host's loopback port. The host reaches D1, R2 and the Queue through the same signed internal routes as in production, with test keys. AF-CLD-01 builds the shim as part of the repository's local verification scripts.
4. **Clients.** Nodes, CLI, Desktop view models, the Blazor app (bUnit and HTTP) and the Android view models point at the local ingress.

Docker is optional (H-18). It enables only the Cloud repository's existing `test:container` diagnostics, which are never a gate. Live Cloudflare deployments are not part of any test.

Verification roles follow [AD-0014](../decisions/AD-0014-delivery-method.md) §4: the author runs targeted and affected suites, the reviewer adds only distinct evidence, and nobody repeats an identical full run on an unchanged head. The merge gate is the required host statuses for the owner's PRs ([AD-0020](../decisions/AD-0020-post-push-verification-and-required-checks.md); until 2026-10-22 the local pre-push verification) and hosted CI for external PRs ([AD-0016](../decisions/AD-0016-local-first-verification.md)).

## 4. Test organisation in the ArcForges repository

```
tests/
  ArcForges.Node.Core.Tests/            unit + component
  ArcForges.Node.Store.Tests/           store, migrations, crash consistency
  ArcForges.Node.Platform.Windows.Tests/ [Trait("env","windows-real")]
  ArcForges.Node.Platform.Linux.Tests/   [Trait("env","linux-real")]
  ArcForges.Node.Toolchains.Tests/       [Trait("tool","dotnet|cargo|cmake|npm")] real tools when present
  ArcForges.ClosedLoop.Tests/            local, multi-node, cloud (Trait "loop")
  ArcForges.Desktop.Tests/               Avalonia headless
  ArcForges.Mcp.Tests/                   ScriptedMcpClient, both protocol revisions
  ArcForges.Bench/                       performance (not run by default)
```

- **Selection.** Traits select suites. `eng/test.ps1` / `eng/test.sh` map task kinds to suites, so authors run exactly the affected set. Tool-dependent tests are skipped with an explicit reason when the tool is missing, and the reason appears in the evidence.
- **Deterministic time.** Node subsystems take an `IClock`. Tests use a controllable clock except in real-OS timing tests.
- **Determinism.** Tests assert the guaranteed product contract, never an optional OS notification or a timing assumption the platform does not guarantee (V-W03). Fixed sleeps are condition waits; generous timeouts apply only on the failure path. A flaky test is fixed at its cause, never hidden by retries or weakened assertions.
- **Parallelism and exclusive phase.** `eng/test.ps1` / `eng/test.sh` run test projects concurrently, bounded by a default chosen from recorded measurements (wall time, CPU, failures over repeated runs). Serial collections remain only where tests share machine-wide state. Timing-, CPU-share- and memory-sensitive tests carry `[Trait("isolation","exclusive")]` and run in a separate phase after the parallel one, alone.
- **Repeat mode.** The same scripts run selected suites N times, stop at the first failure and report per-iteration timing. Repeat mode never selects the OS secret-store tier.
- **Secret stores.** Tests that need a secret store get an `IsolatedSecretStore` (§2), and test nodes run with `--test-mode`. Only the tier project's tests (`[Trait("env","os-secret-store")]`, with `ARCFORGES_OS_SECRET_STORE_TESTS=1`) reach a real OS store. Three mechanisms enforce this (§1):
  - the runtime tripwire in every test process;
  - the `--test-mode` rule in child nodes ([02](02-node-service.md) §4);
  - the repository check before push.
- **Tiers.**
  - *Routine (inner loop):* the affected suites, built once, then rerun without rebuilding.
  - *Post-push (each host, [AD-0020](../decisions/AD-0020-post-push-verification-and-required-checks.md); until 2026-10-22 the pre-push hook):* the full CI-equivalent profile on the native Windows and native Linux legs, reported as commit statuses (§3).
  - *Deep (manual, release preparation, after a flaky failure):* repeat-mode stress runs, `ArcForges.Bench` performance, long property runs (CsCheck iteration and time settings), and ARM64 through a manual `workflow_dispatch` when wanted. Never against a real OS secret store.
  - *OS secret-store integration (separate):* §1; hosted for external PRs, manual dispatch and weekly; locally only on opt-in.
- **Isolation.** Each test node gets a temporary data root, a unique pipe or socket name, a unique node ID (so Windows job names cannot collide) and its own transient slice name on Linux (`arcforges-test-<id>.slice`). A fixture cleans up leftover jobs, units and processes and fails the test if any remain.

## 5. Release-candidate acceptance

The release candidate (AF-ACC-01) runs every journey J-01 to J-11 end to end with:
- **real core implementations**: node, CLI, MCP adapter, hooks, Desktop view models, cloud host, Worker and Durable Object code, Blazor and Android view models;
- **the approved external fakes** of §2 where the external system is unavailable: `FakePaddle`, `FakePlayDeveloperApi`, `FakePubSubPush`, `FakeFcm`, `FakeMailSender`, `FakeBillingClient`, `ScriptedBrowser`, `ScriptedMcpClient`, `HookPayloadFixtures`, `PeerProcess` for other machines, and `IsolatedSecretStore` for the OS secret store (the real stores are covered by the OS secret-store tier of §1). A fake never replaces the behaviour under test;
- **honest labels**: results are labelled closed-loop, and every remaining real-world validation stays in the acceptance register (AR-01 to AR-16).

## 6. Acceptance evidence per task

Each delivery task's PR records:
1. the exact commands run, with their results (author);
2. the environments covered (Windows real, Linux real on a native Linux host; for the owner's PRs each leg's `LEG PASS` line and the combined `arcforges-verify: PASS` line at the pushed head; for external PRs hosted CI);
3. which acceptance criteria each test proves, by requirement ID;
4. benchmarks when a measured path changed;
5. any acceptance-register entries created or advanced, with the human prerequisite stated.

The reviewer's record lists only the distinct checks performed and the diff review result ([AD-0014](../decisions/AD-0014-delivery-method.md) §4).
