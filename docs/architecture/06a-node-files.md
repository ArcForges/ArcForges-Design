# 06a — Center-routed node files and registered workspaces

**Target, 2026-11-09: AF-CTR-06.** This is the delivery design, not a claim that the APIs or either native leg have shipped. It amends [06](06-storage-workspaces.md) §§3 and 7, [11](11-security-privacy.md) §1 and [AD-0021](../decisions/AD-0021-central-access-go-center.md) §§7, 10 and 11. The [Contracts repository](../contracts/README.md) is the v1 wire authority; its additive node, fleet and relay changes, generated bindings and admission are part of this task. The limits below are product defaults and hard maxima for this first version, not claims about the maximum sizes of the transports. Managed worktrees and general storage analysis remain AF-WS-01 and AF-STOR-01.

## 1. Routing, authority and workspace identity

Ordinary operations use the configured center and an explicitly selected device; CLI workspace commands use the node's authenticated Fleet relay, defaulting to this installation's node. The node, not the center, resolves paths and performs I/O. Center authentication, account ownership and the `center.execute` entitlement precede routing; the target's center-routed and per-origin permissions decide last. The node credential relays these new methods only with the existing valid relay assertion, one-use channel nonce, request digest, target, method, caller and command ID binding; its bearer token alone is insufficient. AD-0021 §7's existing own-node default, cross-node local-HUMAN opt-in, narrowing of cross-node HUMAN to SCRIPT, and own-node-only relayed AGENT rule until AF-CTR-07 remain. Calls, results and refusals use the existing signed channel, expiry and before-effect recheck. An account session is still REMOTE at the target; the center's HUMAN authentication does not by itself turn an agent into HUMAN.

Registration and unregistration are fixed HUMAN-only operations, locally or through the center. An account-session HUMAN can register or unregister through the center only under a new explicit routed row: an account session needs the current high-risk step-up bound to that method and target; `mobile.limited` must upgrade; the target applies the center-routed policy. A node-relayed HUMAN may do so only when its verified relay is the target itself and the local origin is HUMAN; a cross-node claimed HUMAN is narrowed to SCRIPT and cannot register or unregister. AGENT and SCRIPT cannot override these fixed rows, even by approval. List and Get are read operations available to AGENT subject to the center and node policies; no caller can enumerate another account's device. A routed caller never decides an approval; a local HUMAN does. AF-CTR-07 adds agent grants later; until then a relayed AGENT can address only its own node.

Registration opens an existing absolute directory, records its canonical opened identity and path, a node-generated workspace ID, name (1–100 characters; default directory name), kind REGISTERED and timestamps in the node's SQLite workspace table. A duplicate of the same opened root returns the existing workspace. Windows equivalence is based on the filesystem and opened identity, not merely a case-folded SQL string. A registration survives restart. Each use reopens the root safely and compares its volume and file identity to the record; a moved, replaced, unavailable or no-longer-verifiable root is refused until a HUMAN unregisters and registers it again. Unregister forgets the registration and never changes its files; it is refused while an in-flight operation or a pending file cleanup/approval uses that workspace. `ListWorkspaces` uses the existing `PageRequest` limit 1–500 but caps its serialized response at 131,072 bytes, returning a continuation without omitting entries when the byte bound cuts a page; `GetWorkspace` returns that record and a bounded fresh git summary as its existing contract says. Any git metadata lookup used during registration follows the same safe execution rules. The summary has a 2-second deadline and 16 KiB output cap; a non-git root has no git summary, and a timeout or unavailable git returns an explicitly unknown summary. The implementation either computes this without launching git or runs a trusted fixed git executable by argument vector in an OS-enforced one-process guard: a Windows job with active-process limit 1 and no breakaway, or a Linux delegated cgroup with pids limit 1. Disable optional locks, hooks, external diff, text conversion, filters, submodule recursion and fsmonitor, and prohibit network and credential helpers; in particular override repository `core.fsmonitor`. The process guard is required even when configuration is hostile or changes after inspection; failure to set it, a forbidden helper or a timeout yields an explicitly unknown git summary. An untrusted repository cannot turn a read into arbitrary helper execution. Prove the guard on both hosts with repository-configured fsmonitor and clean-filter helpers that would create a marker if executed.

The older `storage.auto_register_workspaces=true` direction in 06 §3 does not grant registration to a task's origin. AF-CTR-06 performs no implicit registration for AGENT or SCRIPT, including an agent-submitted task; neither can obtain a new root by causing a task to run. A future automatic registration may only result from a HUMAN-origin request under the fixed registration rule and is not needed for this task. Neither an accepted task nor a policy default silently widens the registered roots.

### Routed method set

Add node `FileService.ReadFile`, `WriteFile`, `EditFile`, `SearchFiles`, `ListDirectory`, `PlanRemoval`, `ExecuteRemoval`, `GetFileOperation` and `AcknowledgeFileOperation`, alongside the existing four `WorkspaceService` methods. Add explicit Fleet counterparts `ReadNodeFile`, `WriteNodeFile`, `EditNodeFile`, `SearchNodeFiles`, `ListNodeDirectory`, `PlanNodeRemoval`, `ExecuteNodeRemoval`, `GetNodeFileOperation`, `RegisterNodeWorkspace`, `UnregisterNodeWorkspace`, `ListNodeWorkspaces` and `GetNodeWorkspace`. The acknowledgment is local HUMAN-only and has no Fleet route. Existing local node service entry points remain for internal dispatch and tests; ordinary CLI or AI operations cannot bypass the center through them. The request metadata of every mutation, including planning a persistent removal, carries a command ID; read/status/list calls do not.

For an account session, file and workspace reads, searches, lists, plan creation and own-operation status are low risk (no step-up; `mobile.limited` may reach them). File write/edit/removal and workspace registration/unregistration are high risk: each delivery needs target- and operation-bound step-up; `mobile.limited` must upgrade. A node-relayed caller cannot step up, so the existing signed relay and target-local policy rule applies instead. The center checks ownership, session, method and current entitlement on every delivery and never uses the client credential as a node credential. The node returns a signed result; it remains authoritative for root, permission, caller ownership and filesystem checks.

## 2. Path contract and native resolution

A file request names a workspace ID and a UTF-8 workspace-relative path. Components are separated by `/`; a backslash is refused on both platforms so a name has the same interpretation at every boundary. Registration walks its absolute path from the native filesystem root with the same no-follow component checks before recording the resulting root identity. The root itself is represented by the empty path only for list/search; it can never be written, edited or removed. Reject NUL, invalid UTF-8, absolute/drive/UNC/device paths, empty components, `.`, `..`, embedded separators in a component and more than 4,096 UTF-8 bytes in the full path. Windows additionally refuses colon/alternate-data-stream names, trailing spaces or dots, reserved device names including their extensions, and names Windows normalizes ambiguously; use native case semantics per directory, never string-prefix containment. A rejected path has no effect. Only regular files and directories are served; links, junctions, mount/reparse points and special files encountered in the relative path are refused, including a final link. Writes and edits refuse a regular file with more than one hard link; read and search refuse it too, so a second name outside the root cannot be used as an alias for data. If link count or identity cannot be obtained reliably, refuse rather than assume one link.

The opened root is the anchor, not a textual prefix. For every call, walk from its live handle, inspecting each component before proceeding and retaining the directory handles to the operation. A missing final component is allowed only for create with `expected_absent`; its parent must already exist and pass the same checks. On Linux use `openat2` relative to the verified root with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` where available; otherwise a component-by-component `openat` walk using directory descriptors and `O_NOFOLLOW` is allowed only when it has the same checked semantics. Inspect type and link count by `fstat` on the opened object: `O_PATH | O_NOFOLLOW` can return a handle to a final symlink even with the resolve flags (V-L09). Never reopen a checked final object by an untrusted absolute name. Reject mount crossings for the operation if the opened object's device/mount identity differs from the registered root. On Windows open each component relative to its already-open parent using a native root-directory handle; open without following that component's reparse point, use directory semantics where appropriate, and check the returned handle's attributes, volume and file ID. `FILE_FLAG_OPEN_REPARSE_POINT` on one full path affects its final component and does not validate intermediate components; a final-path string alone is insufficient (V-W12). Retain directory handles without delete sharing where supported and fail closed on sharing violations. Use handle-relative creation and replacement/disposition with the verified parent and object; do not resolve the unchecked string again at effect time. Unsupported primitives, filesystems, IDs or checks return an explicit refusal rather than falling back to string-prefix checks. The Windows and Linux implementations, including actual traversal and reparse behaviour, must be proven on the native hosts (A-W06, A-L06).

For a live routed delivery, immediately before an effect recheck its link and signature expiry, permission, opened parent/object identities, type, link count and required hash. A durable approval that a local HUMAN decides later is a separate local decision under the captured original caller and command, not an assertion that the old channel signature remains live; it rechecks approval expiry, current policy and every filesystem precondition before executing. A detected replacement, change or ambiguous identity is a conflict before effect; a detected race after an effect starts is an uncertain outcome. Registered-root checks and no-follow resolution prevent a caller from choosing an out-of-root path or using a symlink/junction as a route out. They do **not** confine another process of the same OS user: Linux has no general atomic compare-inode-and-rename/unlink primitive, and a last `stat` does not lock a namespace against uncooperative same-user rename or direct file writes. The implementation serializes ArcForges operations on the same path, uses the strongest available handle/sharing primitives, detects observable swaps and fails closed or reports UNKNOWN as appropriate; it never claims all such external races are excluded or rolls back an unrelated replacement. The task tests both supported safety and this stated limit. A stale expected hash observed at the checked object before an effect must leave it unchanged.

## 3. Bounded operations and results

All limits are checked on decoded and serialized sizes at the node and at ingress. One operation gets at most 10 seconds of monotonic execution time; search has a 5-second work budget inside that deadline. The signed relay's existing maximum request payload is 253,952 bytes, result payload 1,040,384 bytes, and channel frame 1 MiB. Each new Fleet ingress and Worker route must admit the method's bounded serialized reply, with framing and metadata included, without widening unrelated routes. A file request's serialized node payload is at most 245,760 bytes, leaving at least 8,192 bytes below the channel-call payload maximum for later evolution; the outer ingress, response and framing limits still apply. Never silently split a mutation into multiple calls.

| Operation | Input and limits | Result and safety |
|---|---|---|
| Read | Existing regular file; byte `offset` ≥ 0 and requested `length` ≥ 1. Maximum returned content 65,536 bytes. | Raw bytes, actual byte count, SHA-256 of those returned bytes, next byte offset and EOF. Oversize requests return the bounded prefix and continuation, not a fabricated EOF. An offset at or past EOF returns zero bytes and EOF. The caller can request the next chunk; there is no claim of a consistent snapshot across separate calls while a file changes. |
| Write | Replace a whole file with at most 196,608 bytes. Exactly one precondition: 32-byte SHA-256 of the entire existing file, or `expected_absent` for create. Existing files larger than 4 MiB are refused before hashing or mutation. | Return resulting size and SHA-256. Absence uses exclusive creation; an existing target requires a matching whole-file hash. A stale hash returns `CONFLICT/file_changed`, DID_NOT_HAPPEN. It must never truncate before checking. |
| Edit | Existing strict UTF-8 file, at most 4 MiB. Exact, case-sensitive UTF-8 `old` and `new` strings, each at most 65,536 bytes; `old` is nonempty; expected non-overlapping occurrence count 1–1,000; resulting file at most 4 MiB. An expected whole-file SHA-256 is required. | Replace exactly the counted occurrences, without line-ending or Unicode normalization. Invalid UTF-8, a wrong count or stale hash is refused before a write. Return count, resulting size and SHA-256, never the replacement text. |
| Search | One existing regular file or one directory subtree under the root; literal or non-backtracking regular expression, case-sensitive on strict UTF-8, pattern 1–1,024 UTF-8 bytes. At most 10,000 visited entries, 8 MiB total content scanned, 1 MiB per file, 100 matches and 5 seconds. Reject unsupported regex constructs; use a bounded non-backtracking engine with a timeout. | Matches contain relative path and UTF-8 byte offset/length; no snippet is required. A zero-length regex match advances by one Unicode scalar before the next match, so it cannot loop at one offset. Return visited/scanned/skipped counts and an explicit truncation reason whenever a limit, oversized/binary file or deadline prevents full coverage. No recursive walk follows links or mounts; errors on individual entries are counted and surfaced. The serialized response is at most 131,072 bytes; stop before it is exceeded and mark truncated. |
| List | One directory only; page size 1–128, default 100. | Entry name, type and size when known, without following links. A 60-second opaque cursor is bound to the caller, workspace, directory identity and a bounded snapshot; at most 64 live snapshots and 16 MiB total are kept per node. A restart, expiry, changed directory, wrong caller or eviction returns `VALIDATION/invalid_cursor`, not a partial success. At most 10,000 entries are snapshotted; an additional entry is reported as truncation. |
| Remove | One exact workspace-relative file or directory, or the caller's own completed task temporary directory (§5). No wildcard and no unbounded recursion. | The restricted two-phase plan and execution of §5 apply. A directory may be removed only as one explicitly planned, bounded tree, with every descendant checked; root removal is forbidden. |

A successful operation and every refusal are audited at the node; cloud-originated calls are also audited at the center. The record identifies actor/origin, device, workspace and path, operation, outcome, byte count and SHA-256 of the actual content operated on where available: returned bytes for read, supplied/result bytes for write/edit, and matched/scanned bytes where computed for search. Unavailable hashes and sizes are explicitly absent, not invented. No file body, search pattern, match text or replacement appears in an audit, error, routing receipt or log. Paths are sensitive metadata under the existing privacy and retention rules. The center only forwards bounded content in memory; it persists neither content nor search results. A test inspects actual node and center stores and logs with seeded markers.

## 4. Permissions and conflict/error contract

The new fixed `workspace.register` and `workspace.unregister` rows are HUMAN A, SCRIPT D, AGENT D. `workspace.read` and `file.read` (read, search, list) default HUMAN A, SCRIPT A, AGENT A, subject to center-routed policy and narrower overrides. `file.write` (write and edit) defaults HUMAN A, SCRIPT P, AGENT D: a local HUMAN must explicitly set an AGENT permission override to ALLOW for that operation; an approval or account sign-in never changes its origin. `file.remove` defaults HUMAN A, SCRIPT P, AGENT D; an explicit AGENT ALLOW is necessary but does not bypass §5's ownership, cleanup policy, approval and plan checks. Planning uses the existing `cleanup.plan` permission, while execution also checks `cleanup.execute`. REMOTE overrides may only narrow. A missing, invalid, unreadable or uninterpretable policy fails closed. Permissions are re-evaluated before any effect, including after a HUMAN approval.

Malformed paths, arguments, invalid UTF-8 and unsupported regex are `VALIDATION/invalid_argument`; a missing path is `VALIDATION/path_not_found`; exceeding a write, edit, path or plan maximum is `RESOURCE/too_large` with the actual applicable limit; unauthorized operations are `AUTHORIZATION/permission_denied`. A hash, path identity or observable replacement mismatch is `CONFLICT/file_changed`; a wrong edit count is `CONFLICT/occurrence_mismatch`; both are NEVER/DID_NOT_HAPPEN when discovered before effect. A refusal caused by the OS before any effect is `STATE/file_access_denied` with a closed reason, NEVER/DID_NOT_HAPPEN. No body or secret appears in an error. A pending approval uses `AUTHORIZATION/approval_required` and its approval ID; it is not an auto-approval.

Before delivery, a read or any mutation returns DID_NOT_HAPPEN as specified by the existing routed error catalogue. A delivered read with no verified reply is DID_NOT_HAPPEN/AFTER_TIME. A delivered mutation with no verified reply is UNKNOWN/SAME_COMMAND: the caller may resend only the same command ID and bytes; §6's journal must ensure this does not apply the effect again. When recovery cannot determine the effect, the result is `EXECUTION/operation_failed`, UNKNOWN/NEVER with closed reason `file_outcome_unknown`; the user inspects the operation status, never receives a silent success. UNKNOWN is never paired with AFTER_TIME. Any transport failure, expiry or IO error after an effect may have begun must not be mislabeled DID_NOT_HAPPEN.

## 5. Ownership, approval and restricted cleanup

A newly created path is eligible for unattended agent removal only when creation succeeded through this API with `expected_absent`, and a durable ownership record binds its workspace, relative name, opened volume/file identity, last node-written content hash, creation evidence and the verified specific caller (agent grant identity when AF-CTR-07 exists, or verified relaying node plus local agent session in AF-CTR-06). To prevent a deleted and recreated name being treated as the same object after restart, the node records an unpredictable per-creation marker on the created object using a handle-relative platform metadata facility, such as an extended attribute on Linux or an NTFS alternate stream on Windows, together with the file identity in its protected store. The marker is written only on node-created objects; the file API does not expose arbitrary extended attributes or streams. On subsequent checks the record, file identity, marker and last node-written hash must all match. If the filesystem cannot persist or read the marker safely, the write can still succeed, but later unattended cleanup is unavailable and a HUMAN decision is required. The marker is an ownership guardrail, not a boundary against another process of the same OS user, which can access the same files. A successful controlled replacement transfers the ownership marker and record only when performed for that same owner; any other replacement or externally changed content invalidates unattended ownership. Merely overwriting an existing file never claims ownership. Paths created by another agent, an unknown principal, a HUMAN, or outside this API are not agent-owned. Verify the identity and ownership evidence again immediately before removal; a replaced or recreated same-name object loses ownership. A filesystem lacking enough durable identity evidence after restart is treated as unowned, never guessed. Another process of the same OS user can directly change filesystem objects and is outside an agent confinement claim (§2).

A task temporary directory qualifies only when the persisted task/attempt record binds it to that same specific caller, it is the exact node-managed temporary directory and it is no longer in use by a queued/running attempt, live session, pin or lease. This is a cleanup-only exception for that managed temp root, not permission for arbitrary file access outside registered workspaces.

This task implements the narrow form of 06 §7, not AF-STOR-01's analyzer: plan one explicitly named object, enumerate at most 1,000 descendants and 64 MiB, and bind the plan ID/digest, caller, target, every descendant's identity/type/fingerprint, aggregate size, chosen action and 60-minute expiry. There is no wildcard or recursive-delete argument. Planning causes no removal. Before executing, revalidate the plan, root, target, each child and in-use constraints; a changed, unowned or newly added descendant makes unattended execution fail. Classify an item as low risk for this restricted operation only when its caller ownership or eligible task-temp provenance is verified and all preconditions still hold; an unowned or ambiguous item is not low risk. Agent `file.remove=ALLOW` is insufficient by itself: unattended execution also requires `cleanup.agent_execute=LOW_RISK_ONLY`, every selected item to be low risk, and every item to be verifiably owned by that agent or within its own eligible task temp. When `file.remove` permits the request but the cleanup policy or risk requires approval, a real local HUMAN must decide the exact plan and digest; unowned items always need that decision regardless of low-risk policy. A HUMAN's decision cannot be manufactured by the requester, its account login or a test fixture.

As in 06 §7, removal first moves the exact planned object to a private same-volume quarantine, then keeps it for the existing default 24-hour purge/restore period. An agent may propose an unowned path inside the registered workspace for approval, but its proposal is not authority to act. When a planned tree is not wholly agent-owned, the approval shows the exact paths, sizes and risks; a local HUMAN must explicitly select that exact plan and separately confirm any path that 06 §7 treats as external. An agent cannot add external paths as though the HUMAN had selected or confirmed them. If there is no configured/confirmed same-volume quarantine root, do not quietly delete: an explicit HUMAN per-item delete-without-quarantine confirmation is required, and direct execution is limited to the exact revalidated planned set. The plan's digest and ownership are rechecked after approval. Quarantine does not authorize a changed object, mount crossing, link traversal or a user file hidden inside an agent-owned directory. General analysis, managed-worktree removal and their wider cleanup classes are not delivered here.

## 6. Mutation journal, restart and audit

The node serializes its own mutations per workspace/path and keys a durable journal by command ID, exact request digest and verified caller. A different payload or caller for the same ID is refused; an identical completed command returns its recorded metadata outcome without reapplying it. Register/unregister use SQLite's existing transactional receipt. Filesystem effects are not part of that transaction: before the first effect, durably record the command, root/parent/target identity, precondition and intended size/digest in a PREPARED journal entry. Stage new bytes in a private, access-restricted temporary file on the target volume, flush the staged bytes and journal before attempting replacement, and never place bytes in audit, the center, or an approval's captured request. After the effect and the required filesystem durability operations, commit the resulting metadata and receipt to SQLite before answering success. Preserve the existing file's owner, mode, ACL and non-content attributes, including extended attributes and alternate streams; if a safe bounded preservation cannot be established, refuse before effect. Never silently widen access.

If the node stops after PREPARED and before a durable completed receipt, recovery inspects only this operation's exact recorded identities and staged object. It must never overwrite or remove a different object, infer success solely from a matching pathname/hash, or automatically repeat an effect whose prior completion is uncertain. Where it cannot prove the outcome, durably mark UNKNOWN, retain the minimum owned recovery evidence, refuse further mutation of that target until a local HUMAN acknowledges the uncertainty, and expose a bounded `GetFileOperation(command_id)` status to the original caller and local HUMAN. A blocked mutation returns `STATE/invalid_state` with reason `file_recovery_pending`, NEVER/DID_NOT_HAPPEN, and points to the status; it never waits indefinitely. The HUMAN-only acknowledgment releases this hold without modifying user files or pretending the old operation succeeded. Keep unresolved metadata until acknowledgment; only an exactly identified node-owned staging file may be purged after 24 hours, with the loss of that staging evidence recorded in the status. A replaced or unidentifiable staging path is never deleted by cleanup. A duplicate of an UNKNOWN command returns the recorded uncertainty and never executes again; a different command ID cannot bypass the hold. The status/acknowledgment calls are additive v1 node/fleet interfaces, audited, and do not expose bodies.

Approval records carry a plan ID, digest, identities and decision details only, not write/edit bodies or search content. If policy requires approval for a write/edit, keep its bounded staged bytes in the private journal, referenced by the approval; recheck policy, identity, expiry and hash after approval and before effect. Secure disposal and its limits follow existing node-data retention and OS permissions; no physical-erasure guarantee is invented.

### Expand-only delivery and command identity

The shipped SQLite schema step 2 is immutable: its `routed_call_log.method` accepts only 1–6 and verified rows require a method. New file/workspace calls therefore use a new step and an append-only `routed_file_call_log`, never a fake old method or a change to that checksum. Add a shared verified-call-ID registry and a trigger or equivalent single-writer transaction that enforces uniqueness across the old and new logs, backfilled with still-live old verified IDs; forged frames cannot reserve IDs. Preserve the old rows and their retention. Add workspace root identity, created-object ownership, restricted cleanup-plan and file-journal records as new, versioned schema objects; their contents and retention are in [node-store](../data/node-store.md). Older binaries must not receive a new method; advertise and check capability before routing it.

The delivered PostgreSQL `fleet.routed_call` in migration 0010 accepts method 1 or 6 only. Preserve that migration and its records; add a separate file/workspace routing receipt and a shared `(account_id, command_id)` registry. Backfill existing IDs and install transactional insert enforcement for both old and new receipt paths under a migration lock that excludes concurrent receipt writes. This includes older still-running center binaries, so neither concurrent deployment nor rollback can reuse one command ID across the two tables. A repeat within the same table reaches that table's existing digest/caller deduplication; a different method, caller or digest is refused `CONFLICT/command_id_reused`. Neither store contains file bytes or response bodies. The migration must be tested with old rows, concurrent same-ID writers, restart and the supported rollback path; no changed or missing historical checksum is accepted.

## 7. Required evidence

The author runs actual native Windows and Linux tests, and each real native node separately makes file/workspace calls through a real center. Record head/tree, actual binary hashes, call path, synthetic identity, command, result, logs and cleanup for each row. Cover safe Git metadata with hostile fsmonitor and filter helpers, root traversal, absolute and reserved names, case variants, symlink/junction and intermediate-component swaps, hard links, root/object replacement, ordinary and observable competing rename/write races, read continuation, limits, stale hash preserving bytes, exact-count failure, regex time/count bounds, list cursor invalidation, persistence/restart, caller-scoped ownership, policy denial/allow, real HUMAN approval, other-agent and unowned descendants, quarantine and in-use refusal, crash at every journal/effect/receipt boundary, same-ID replay and no audit body. Verify both the successful path and refusal; fault injection does not substitute for real filesystem operations.

The explicit user exception of 2026-11-09 permits only unavailable owner-only external credentials, hardware, persistent key custody or hosted/proof venue substitutes. Isolated real centers and native nodes plus the named protocol harness may supplement those venues; report each component separately as REAL, MOCKED or NOT PROVEN. These substitutes never prove AR-25's hosted H5, Windows-to-proof or Windows-to-Linux route, never replace a native gate or independent review, and never turn unperformed owner actions into completed actions.
