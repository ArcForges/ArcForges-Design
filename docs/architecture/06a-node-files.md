# 06a — Center-routed node files and registered workspaces

**Target, 2026-11-09: AF-CTR-06.** This is the delivery design, not a claim that the APIs or either native leg have shipped. It amends [06](06-storage-workspaces.md) §§3 and 7, [11](11-security-privacy.md) §1 and [AD-0021](../decisions/AD-0021-central-access-go-center.md) §§7, 10 and 11. The [Contracts repository](../contracts/README.md) is the v1 wire authority; its additive node, fleet and relay changes, generated bindings and admission are part of this task. The limits below are product defaults and hard maxima for this first version, not claims about the maximum sizes of the transports. Managed worktrees and general storage analysis remain AF-WS-01 and AF-STOR-01.

## 1. Routing, authority and workspace identity

Ordinary operations use the configured center and an explicitly selected device; CLI workspace commands use the node's authenticated Fleet relay, defaulting to this installation's node. The node, not the center, resolves paths and performs I/O. Center authentication, account ownership and the `center.execute` entitlement precede routing; the target's center-routed and per-origin permissions decide last. The node credential relays these new methods only with the existing valid relay assertion, one-use channel nonce, request digest, target, method, caller and command ID binding; its bearer token alone is insufficient. AD-0021 §7's existing own-node default, cross-node local-HUMAN opt-in, narrowing of cross-node HUMAN to SCRIPT, and own-node-only relayed AGENT rule until AF-CTR-07 remain. Calls, results and refusals use the existing signed channel, expiry and before-effect recheck. An account session is still REMOTE at the target; the center's HUMAN authentication does not by itself turn an agent into HUMAN.

Registration and unregistration are fixed HUMAN-only operations, locally or through the center. An account-session HUMAN can register or unregister through the center only under a new explicit routed row: an account session needs the current high-risk step-up bound to that method and target; `mobile.limited` must upgrade; the target applies the center-routed policy. A node-relayed HUMAN may do so only when its verified relay is the target itself and the local origin is HUMAN; a cross-node claimed HUMAN is narrowed to SCRIPT and cannot register or unregister. AGENT and SCRIPT cannot override these fixed rows, even by approval. List and Get are read operations available to AGENT subject to the center and node policies; no caller can enumerate another account's device. A routed caller never decides an approval; a local HUMAN does. AF-CTR-07 adds agent grants later; until then a relayed AGENT can address only its own node.

For workspace kind REGISTERED, registration opens an existing absolute directory, records its canonical opened identity and path, a node-generated workspace ID, name (1–100 characters; default directory name), kind REGISTERED and timestamps in the node's SQLite workspace table. A duplicate of the same opened root returns the existing workspace. Windows equivalence is based on the filesystem and opened identity, not merely a case-folded SQL string. A registration survives restart. Every operation that accesses that root, including `GetWorkspace` and any fresh Git lookup, safely reopens it and compares its volume and file identity with the registration. A moved, replaced, missing, wrong-type or unverifiable registered root is refused for those uses until a HUMAN corrects the registration. `GetWorkspace` resolves the ID against the complete workspace catalogue and uses `STATE/not_found` only when no workspace of any supported kind has that ID. A known MANAGED_WORKTREE or REMOTE record is not missing merely because it has no REGISTERED root identity; retain its existing kind-specific metadata and Get behavior. The native registration-root checks here apply to the REGISTERED subset. Registration/unregistration retain their registered-workspace semantics; this clarification adds no managed-worktree or remote-workspace capability. For `GetWorkspace`, an observed missing, replaced or wrong-type previously registered root uses `CONFLICT/file_changed` with `workspace_root_changed`; an OS access failure or inability to obtain reliable identity uses its allowed `STATE/file_access_denied` with the applicable closed reason. Do not report a missing or changed root as a permission denial. `UnregisterWorkspace` changes registration metadata only and does not require the root to remain available; it never changes files and is refused while an in-flight operation or pending cleanup/approval uses that workspace. `ListWorkspaces` uses the existing `PageRequest` limit 1–500 but caps its serialized response at 131,072 bytes, returning a continuation without omitting entries when the byte bound cuts a page; `GetWorkspace` returns that record and a bounded fresh git summary as its existing contract says. Any git metadata lookup used during registration follows the same safe execution rules. The summary has a 2-second deadline and 16 KiB output cap. A proven non-git root has no git summary; a timeout or unavailable git returns quality UNKNOWN, and output beyond the cap returns TRUNCATED. Register/Get/List results with a summary explicitly carry quality COMPLETE, UNKNOWN or TRUNCATED; legacy summaries without quality remain wire-compatible but never mean COMPLETE. COMPLETE requires present dirty, modified-files, untracked-files and locked fields; branch, head, ahead, behind, merged-into-base and upstream-deleted remain conditional. UNKNOWN/TRUNCATED omit every prior boolean and count field and may retain independently established branch/head, never partial counts presented as complete. A shape check cannot itself prove a root is non-git or run the bounded Git query. The implementation either computes this without launching git or runs a trusted fixed git executable by argument vector in an OS-enforced one-process guard: a Windows job with active-process limit 1 and no breakaway, or a Linux delegated cgroup with pids limit 1. Disable optional locks, hooks, external diff, text conversion, filters, submodule recursion and fsmonitor, and prohibit network and credential helpers; in particular override repository `core.fsmonitor`. The process guard is required even when configuration is hostile or changes after inspection; failure to set it, a forbidden helper or a timeout yields an explicitly unknown git summary. An untrusted repository cannot turn a read into arbitrary helper execution. Prove the guard on both hosts with repository-configured fsmonitor and clean-filter helpers that would create a marker if executed.

`ListWorkspaces` enumerates the complete persistent workspace catalogue, honors its `kinds` filter (empty means all), and retains MANAGED_WORKTREE and REMOTE records with their existing kind-specific semantics. It must not restrict the page to REGISTERED records or convert another kind into a registration. For the REGISTERED subset, enumeration does not promise that every recorded root is currently usable. Return a missing, replaced or inaccessible root's registration metadata so the HUMAN can identify and unregister it. Do not omit it, read the replacement root, or fail the whole metadata page with a native root error. Before any optional fresh Git lookup, verify the recorded root as above. If that cannot be established, return a present `GitStatusSummary` with quality UNKNOWN, no unverified branch/head and no dirty/modified/untracked/locked/ahead/behind or other prior boolean/count fields. An absent Git summary means only a safely established non-Git root. Neither persisted Git data nor a previously observed non-Git classification proves the current root. Pagination follows that full filtered workspace inventory across kinds, includes unavailable REGISTERED roots without omissions or duplicates, preserves the existing count and serialized-byte limits and lossless continuation, and reports an invalidated inventory cursor as `VALIDATION/invalid_cursor`. Root availability alone does not erase a record or invalidate its metadata identity. Native acceptance must cover replaced, missing and inaccessible roots, recovery/unregistration and continuation pages.

The older `storage.auto_register_workspaces=true` direction in 06 §3 does not grant registration to a task's origin. AF-CTR-06 performs no implicit registration for AGENT or SCRIPT, including an agent-submitted task; neither can obtain a new root by causing a task to run. A future automatic registration may only result from a HUMAN-origin request under the fixed registration rule and is not needed for this task. Neither an accepted task nor a policy default silently widens the registered roots.

### Routed method set

Add node `FileService.ReadFile`, `WriteFile`, `EditFile`, `SearchFiles`, `ListDirectory`, `PlanRemoval`, `ExecuteRemoval`, `GetFileOperation` and `AcknowledgeFileOperation`, alongside the existing four `WorkspaceService` methods. Add explicit Fleet counterparts `ReadNodeFile`, `WriteNodeFile`, `EditNodeFile`, `SearchNodeFiles`, `ListNodeDirectory`, `PlanNodeRemoval`, `ExecuteNodeRemoval`, `GetNodeFileOperation`, `RegisterNodeWorkspace`, `UnregisterNodeWorkspace`, `ListNodeWorkspaces` and `GetNodeWorkspace`. The acknowledgment is local HUMAN-only and has no Fleet route. The bounded recovery commands `arcforges file-operation show <command-id>` and `arcforges file-operation acknowledge <command-id> --digest <request-sha256>` use the node's local management endpoint, not Fleet. Show names the command, target, original request digest, journal phase, possible effect, any held capture and safe recovery actions without file contents. Acknowledge requires the exact 32-byte request digest from show and an explicit interactive confirmation naming that command and target; the node compares the digest with its persisted intent and records the HUMAN decision. A stale or wrong digest returns `CONFLICT/digest_mismatch` before changing the hold. It only releases the hold; it does not submit a file operation or declare the earlier effect successful. The node independently classifies the local connection through the existing Hello/peer and ancestry checks: AGENT, SCRIPT, noninteractive and unrelated callers cannot acknowledge, and cannot self-assert HUMAN. Show is available to a local HUMAN; a routed original caller may use the separately authorized `GetNodeFileOperation`. Existing local node service entry points otherwise remain for internal dispatch and tests; ordinary CLI or AI operations cannot bypass the center through them. The request metadata of every mutation, including planning a persistent removal, carries a command ID; read/status/list calls do not.

For an account session, file and workspace reads, searches, lists, plan creation and own-operation status are low risk (no step-up; `mobile.limited` may reach them). File write/edit/removal and workspace registration/unregistration are high risk: each delivery needs target- and operation-bound step-up; `mobile.limited` must upgrade. A node-relayed caller cannot step up, so the existing signed relay and target-local policy rule applies instead. The center checks ownership, session, method and current entitlement on every delivery and never uses the client credential as a node credential. The node returns a signed result; it remains authoritative for root, permission, caller ownership and filesystem checks.

The center binds each admitted write, edit or removal execution to its account, active node enrollment, verified caller, mutation kind and SHA-256 of the exact transmitted inner request bytes. This raw digest is separate from the domain-separated routing-record digest; the legacy removal of a correlation field from a request digest does not apply to these new methods. Persist only bounded target metadata. A verified successful removal plan binds its signed plan ID to the known workspace/path or exact attempt target. Target and status lookups are scoped by account, enrollment and caller: an account caller may use another currently valid session of the same account; a relay remains bound to its verified relaying node, origin and local session. A signed operation status must match the admitted operation, mutation kind and raw digest, and agree with its known target. If an existing center-admitted receipt proves that caller and request but its target was not previously known, a valid signed status may establish the target. A signature alone is not caller authorization: foreign or unknown status is never adopted or returned as success. Retain these associations for refusal, offline and restart audits; the original local HUMAN keeps the separate local show path. The center never claims to have inspected the node's files.

## 2. Path contract and native resolution

Every ordinary read, write, edit, search and list request names a workspace ID and a UTF-8 workspace-relative path. A removal plan instead has exactly one of two targets: `workspace_path` (workspace ID plus relative path), or `attempt_id` (one existing attempt's exact managed temporary root). The second form never accepts a caller-supplied filesystem path or task root: the node resolves it exclusively from its trusted persisted task/attempt and managed-directory records, verifies that this specific caller owns the task, and confirms the attempt is terminal and the directory is not referenced, live, pinned or leased. Execution names only the issued plan ID and digest and rechecks the derived target and ownership. Unknown, forged, foreign, active or no-longer-matching attempt IDs are refused before effect; a caller cannot turn this exception into a general out-of-workspace file API. Components of a workspace path are separated by `/`; a backslash is refused on both platforms so a name has the same interpretation at every boundary. Registration walks its absolute path from the native filesystem root with the same no-follow component checks before recording the resulting root identity. The root itself is represented by the empty path only for list/search; it can never be written, edited or removed. Reject NUL, invalid UTF-8, absolute/drive/UNC/device paths, empty components, `.`, `..`, embedded separators in a component and more than 4,096 UTF-8 bytes in the full path. Windows additionally refuses colon/alternate-data-stream names, trailing spaces or dots, reserved device names including their extensions, and names Windows normalizes ambiguously; use native case semantics per directory, never string-prefix containment. A rejected path has no effect. Only regular files and directories are served; links, junctions, mount/reparse points and special files encountered in the relative path are refused, including a final link. Writes and edits refuse a regular file with more than one hard link; read and search refuse it too, so a second name outside the root cannot be used as an alias for data. If link count or identity cannot be obtained reliably, refuse rather than assume one link.

The opened root is the anchor, not a textual prefix. For every call, walk from its live handle, inspecting each component before proceeding and retaining the directory handles to the operation. A missing final component is allowed only for create with `expected_absent`; its parent must already exist and pass the same checks. On Linux use `openat2` relative to the verified root with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` where available; otherwise a component-by-component `openat` walk using directory descriptors and `O_NOFOLLOW` is allowed only when it has the same checked semantics. Inspect type and link count by `fstat` on the opened object: `O_PATH | O_NOFOLLOW` can return a handle to a final symlink even with the resolve flags (V-L09). Never reopen a checked final object by an untrusted absolute name. Reject mount crossings for the operation if the opened object's device/mount identity differs from the registered root. On Windows open each component relative to its already-open parent using a native root-directory handle; open without following that component's reparse point, use directory semantics where appropriate, and check the returned handle's attributes, volume and file ID. `FILE_FLAG_OPEN_REPARSE_POINT` on one full path affects its final component and does not validate intermediate components; a final-path string alone is insufficient (V-W12). Retain directory handles without delete sharing where supported and fail closed on sharing violations. Use handle-relative creation and replacement/disposition with the verified parent and object; do not resolve the unchecked string again at effect time. Unsupported primitives, filesystems, IDs or checks return an explicit refusal rather than falling back to string-prefix checks. The Windows and Linux implementations, including actual traversal and reparse behaviour, must be proven on the native hosts (A-W06, A-L06).

For a live routed delivery, immediately before an effect recheck its link and signature expiry, permission, opened parent/object identities, type, link count and required hash. A durable approval that a local HUMAN decides later is a separate local decision under the captured original caller and command, not an assertion that the old channel signature remains live; it rechecks approval expiry, current policy and every filesystem precondition before executing. A detected replacement, change or ambiguous identity before any effect is a conflict. A detected race after an effect starts is not solved merely by returning UNKNOWN: the exact object affected and any captured object must be protected by the protocols in §§2a and 5. Registered-root checks and no-follow resolution prevent a caller from choosing an out-of-root path or using a symlink/junction as a route out. They do **not** confine another process of the same OS user: Linux has no general atomic compare-inode-and-rename/unlink primitive, and a last `stat` does not lock a namespace against uncooperative same-user rename or direct file writes. A same-user process can independently move the already-open object or a directory after validation, or create an alias or change objects outside the product API; this release does not claim to prevent such activity. The implementation serializes ArcForges operations, rechecks observable changes and uses effects on the verified object handle where supported. During cleanup it never moves, overwrites, deletes or purges a newly substituted or unplanned object under the guise of an uncertain outcome. Tests inject a real-object swap after the last validation and before each name-based effect on both hosts. A stale expected hash observed at the checked object before an effect leaves it unchanged.

### 2a. Writing the verified object, not a later name

For an existing file, open it once relative to the verified parent with read/write access, no link following, a single-link check and a stable object identity. Acquire a real exclusive write guard **before** reading the expected whole-file hash and keep the same open file description/handle and guard through the effect and result hash. On Windows use a verified file handle opened with no read/write/delete sharing, and do the write and final length change through that handle; a conflicting existing handle or sharing violation fails before effect. On Linux use an exclusive `F_SETLEASE/F_WRLCK` lease on that opened regular file; it is available to an unprivileged process only for a file it owns, and only when no other open file descriptor conflicts. Configure and safely handle lease-break notifications without terminating the node, and check for a pending or broken lease before effects and during the bounded write. A break before effect is a refusal; after any bytes may have changed, stop and report UNKNOWN, not a clean rollback. Linux can forcibly break a lease after its configured interval, so first verify the existing `/proc/sys/fs/lease-break-time` is greater than the 10-second operation bound plus a 2-second margin; a missing, unsuitable or unsupported lease/guard is `RESOURCE/enforcement_unavailable`, NEVER/DID_NOT_HAPPEN before effect, with a closed reason; it is never a reason to alter host settings. A dedicated native helper may own the lease and signal handling; any helper must keep the exact verified descriptor and return bounded results. These guards protect their documented open/truncate conflicts (V-L10); they are not namespace locks or a claim against every action by the same OS user.

After the guard and expected-hash check, use `pwrite`/`ftruncate` on Linux or the equivalent write and end-of-file operations on Windows **through that same handle**, not a rename over a checked filename. New files use atomic exclusive creation of the final name relative to the checked parent (`O_CREAT|O_EXCL|O_NOFOLLOW` or Windows `CREATE_NEW`); then write only through the newly created handle. If a different object occupies the name, creation fails and does not overwrite it. A parent/object identity change detected before effect fails closed. Revalidate the name and opened identities after the operation and before claiming success; a detected move/change reports the actual uncertain state, never touches the new name and leaves recovery evidence. The guarded in-place update is not an atomic replacement: readers may observe an intermediate state and a crash or I/O failure after the first effect can leave a partial original object. Before effect, the PREPARED journal records the original and intended lengths and digests, with their bounded bytes in private staging while that staging remains available (§6). An anonymous stage vanishes on a process crash, which is reported honestly; no preimage is invented. Where retained bytes are available a HUMAN can inspect/recover them; the node never automatically writes back over a possibly changed object. Before the first effect, a stale hash or failed guard leaves the file unchanged. After effect, failure or a lost guard is UNKNOWN unless its outcome is proven, and SAME_COMMAND never repeats the write. Success needs the required flush, an unchanged held identity and a rehash of the final bytes on the held handle. Cleanup effects on either platform must meet §5, not this in-place-write protocol.

### 2b. Measured native guard limits (2026-11-09)

This records the local, unshipped AF-CTR-06 guard candidate, not delivery of a file API or an accepted change to §5. The native author tests and independent review used separate processes and test-owned files. Earlier fixture results and later counterexamples are retained separately.

- On the tested native Linux host and files, acquiring a write lease was refused when the tested independent read/write data descriptors or the mappings below already existed. An independent mapping-only probe used Python mmap with trackfd=False, closed its source descriptor and checked /proc/self/fd; read-shared, write-shared and private-write mappings each prevented the competing lease, while the no-mapping positive case succeeded. Python's default trackfd=True keeps a duplicated descriptor after the visible file is closed, so the earlier default-mmap fixture did not independently establish mapping-only coverage. A native guard test must remove that hidden descriptor and verify the actual component.
- In the tested Linux cases, thread-targeted lease-break signals were consumed without terminating the node, and one guard paused at a coordinated check did not prevent another guard from processing its break. These observations do not establish a scheduling guarantee. F_GETLEASE and a future pwrite are separate operations. The observed 45-second lease-break interval exceeds the configured operation bound; that observation, a timer or a thread-pool callback does not prove exclusion under process suspension, scheduling exhaustion or blocked I/O. A future effect needs its actual guard/lifetime and journal proof. No file-effect API has been exposed by this candidate, and a Host AOT publish that may trim it is not native execution of the guard.
- On the checked native Windows host, a real read-only mapped view survives after **both** the explicit file and section handles are closed. An independent process can then obtain the candidate's metadata-handle plus ReOpenFile read/write handle with share mode zero. A real write through that latter handle was observed immediately through the surviving read-only view. Retaining an ordinary read handle instead causes the expected sharing violation; a shared writable view without the explicit handles also caused a sharing violation in this probe. These are distinct cases, not evidence that a read-only view itself is writable.
- The corrected Windows component fixture creates the view with CreateFileMappingW/MapViewOfFile, closes both handles, confirms ERROR_INVALID_HANDLE for them, and retains the live view. The actual C# guard test then fails its required file_in_use assertion because the guard is accepted (three other guard cases pass, seven Linux-only cases skip). The earlier default-Python-mmap pass cannot replace this failure. Share-zero opening alone therefore does not supply §5's required mapping conflict check.

These observations preserve the target: mapped-content conflicts must be refused before cleanup, and the strict source/ancestor/whole-tree exclusion in §5 is separately mandatory. A Linux lease is not a namespace lock; a Windows share check is not a general mapped-view detector. The checked interfaces still supply no demonstrated strict Linux source-and-tree stabilization. An unsupported capability must be reported before effect, and that refusal never counts as the required successful quarantine. Internal component source/tests, a source-equivalent build or an approved contract package do not close these implementation and native-acceptance prerequisites. The candidate remains unmerged while the independent blocking findings are unresolved.

## 3. Bounded operations and results

All limits are checked on decoded and serialized sizes at the node and at ingress. One operation gets at most 10 seconds of monotonic execution time; search has a 5-second work budget inside that deadline. The signed relay's existing maximum request payload is 253,952 bytes, result payload 1,040,384 bytes, and channel frame 1 MiB. Each new Fleet ingress and Worker route must admit the method's bounded serialized reply, with framing and metadata included, without widening unrelated routes. A file request's serialized node payload is at most 245,760 bytes, leaving at least 8,192 bytes below the channel-call payload maximum for later evolution; the outer ingress, response and framing limits still apply. Never silently split a mutation into multiple calls. A complete `PlanRemoval` node success response must fit the existing 1,040,384-byte result-payload bound, including its metadata and every planned item. A plan that cannot fit is refused under §4 before a successful plan is committed; it is never returned as a truncated plan.

| Operation | Input and limits | Result and safety |
|---|---|---|
| Read | Existing regular file; byte `offset` ≥ 0 and requested `length` ≥ 1. Maximum returned content 65,536 bytes. | Raw bytes, actual byte count, SHA-256 of those returned bytes, next byte offset and EOF. Oversize requests return the bounded prefix and continuation, not a fabricated EOF. An offset at or past EOF returns zero bytes and EOF. The caller can request the next chunk; there is no claim of a consistent snapshot across separate calls while a file changes. |
| Write | Write a whole file with at most 196,608 bytes through the checked handle (§2a). Exactly one precondition: 32-byte SHA-256 of the entire existing file, or `expected_absent` for create. Existing files larger than 4 MiB are refused before hashing or mutation. | Return resulting size and SHA-256. Absence uses exclusive creation; an existing target requires a matching whole-file hash. A stale hash returns `CONFLICT/file_changed`, DID_NOT_HAPPEN. It must never truncate before checking. |
| Edit | Existing strict UTF-8 file, at most 4 MiB. Exact, case-sensitive UTF-8 `old` and `new` strings, each at most 65,536 bytes; `old` is nonempty; expected non-overlapping occurrence count 1–1,000; resulting file at most 4 MiB. An expected whole-file SHA-256 is required. | Replace exactly the counted occurrences, without line-ending or Unicode normalization. Invalid UTF-8, a wrong count or stale hash is refused before a write. Return count, resulting size and SHA-256, never the replacement text. |
| Search | One existing regular file or one directory subtree under the root; literal or non-backtracking regular expression, case-sensitive on strict UTF-8, pattern 1–1,024 UTF-8 bytes. At most 10,000 visited entries, 8 MiB total content scanned, 1 MiB per file, 100 matches and 5 seconds. Reject unsupported regex constructs; use a bounded non-backtracking engine with a timeout. | Matches contain relative path and UTF-8 byte offset/length; no snippet is required. Every start and end must lie on a Unicode scalar boundary. A .NET regex engine reports UTF-16 indices and can match half of a surrogate pair (for example `.` over a supplementary-plane scalar); when any match bisects a pair, refuse that search `VALIDATION/invalid_argument` with `state.reason` `pattern: regex_scalar_boundary`, and do not return fabricated offsets or partial matches. Otherwise translate indices through the exact strict UTF-8 scalar-to-byte mapping, never a replacement encoder. A zero-length match advances one whole Unicode scalar, or terminates at EOF. A scan cut by its byte limit processes only a complete UTF-8 prefix: retain at most the three trailing bytes of an incomplete scalar as unprocessed, report truncation and never treat that boundary as invalid UTF-8. Invalid sequences wholly inside the scanned prefix are reported as skipped/invalid, never decoded with replacement. Return visited/scanned/skipped counts and an explicit truncation reason whenever a limit, oversized/binary file or deadline prevents full coverage. No recursive walk follows links or mounts; errors on individual entries are counted and surfaced. The serialized response is at most 131,072 bytes; stop before it is exceeded and mark truncated. |
| List | One directory only; page size 1–128, default 100. | Entry name, type and size when known, without following links. A 60-second opaque cursor is bound to the caller, workspace, directory identity and a bounded snapshot; at most 64 live snapshots and 16 MiB total are kept per node. A restart, expiry, changed directory, wrong caller or eviction returns `VALIDATION/invalid_cursor`, not a partial success. At most 10,000 entries are snapshotted; an additional entry is reported as truncation. |
| Remove | `PlanRemoval` selects exactly one `workspace_path` or `attempt_id` target as defined in §2; `ExecuteRemoval` names the resulting plan ID and digest (§5). No arbitrary absolute path, wildcard or unbounded recursion. | The restricted two-phase plan and execution of §5 apply. A directory may be removed only as one explicitly planned, bounded tree, with every descendant checked; root removal is forbidden. |

A successful operation and every refusal are audited at the node; cloud-originated calls are also audited at the center. The record identifies actor/origin, device, workspace or attempt target, path, operation, outcome, byte count and SHA-256 of the bytes actually operated on. A successful read hashes the exact returned bytes; a successful write/edit records the resulting file size and whole resulting-content SHA-256. For every successful search, including a truncated search and a search with zero scanned bytes, compute and record the total number of regular-file bytes actually read by the scanner and a mandatory `scan_sha256` as follows: start SHA-256 with UTF-8 bytes `ArcForges search-scan v1` followed by one zero byte; in the actual scan order, for each file from which any bytes were read append the unsigned 32-bit big-endian UTF-8 byte length of its workspace-relative path, those exact path bytes, the unsigned 64-bit big-endian number of bytes read from that file, and exactly those bytes. Hash file prefixes read for UTF-8/binary detection too, including bytes subsequently skipped as invalid or truncated; never hash unread file content. Buffer each bounded per-file prefix as needed so length precedes bytes. A scan with no bytes hashes only the domain. The signed node response carries scan count and digest in bounded audit metadata outside the value/error outcome, so the center can persist that metadata for either a successful/truncated result or a refusal after bytes were scanned; the center does not claim it independently read the scanned file bytes. Node audit includes a scanned-byte digest even on a refusal after scanning, including `regex_scalar_boundary`. If the center never receives a verified result, its audit marks that node-derived size/digest unavailable instead of inventing one. Refusals before any file data is available, and operations with no applicable bytes, explicitly omit rather than invent a content hash. Directory and workspace operations have no file-content bytes to hash. For a successful directory page, the node reports an entry count, metadata-transcript byte count and SHA-256 over UTF-8 `ArcForges directory-list v1` plus a zero byte, followed in returned entry order by each name's unsigned 32-bit big-endian UTF-8 byte length and bytes, its kind as unsigned 32-bit big-endian enum number, and one byte for size presence (0 absent, 1 present), followed by unsigned 64-bit big-endian size only when present. For a successful workspace list or get, hash UTF-8 `ArcForges workspace-metadata v1` plus a zero byte, followed in returned-record order by each 16-byte workspace ID, unsigned 32-bit big-endian root-path UTF-8 byte length and bytes, unsigned 32-bit big-endian kind, unsigned 32-bit big-endian state, and unsigned 32-bit big-endian name UTF-8 byte length and bytes. Empty lists hash only the applicable domain. Metadata byte count includes the domain, terminator and frames; these hashes identify the specified metadata subset and do not claim a hash of the directory's contents or every workspace field. The node supplies these counts and digests as signed metadata to the center. No file body, search pattern, match text or replacement appears in an audit, error, routing receipt or log. Paths are sensitive metadata under the existing privacy and retention rules. The center only forwards bounded content in memory; it persists neither content nor search results. Tests inspect actual node and center stores and logs using seeded markers, and independently recompute the digest for complete, partial, binary and zero-byte searches.

## 4. Permissions and conflict/error contract

The new fixed `workspace.register` and `workspace.unregister` rows are HUMAN A, SCRIPT D, AGENT D. `workspace.read` and `file.read` (read, search, list) default HUMAN A, SCRIPT A, AGENT A, subject to center-routed policy and narrower overrides. `file.write` (write and edit) defaults HUMAN A, SCRIPT P, AGENT D: a local HUMAN must explicitly set an AGENT permission override to ALLOW for that operation; an approval or account sign-in never changes its origin. `file.remove` defaults HUMAN A, SCRIPT P, AGENT D; an explicit AGENT ALLOW is necessary but does not bypass §5's ownership, cleanup policy, approval and plan checks. Planning uses the existing `cleanup.plan` permission, while execution also checks `cleanup.execute`. REMOTE overrides may only narrow. A missing, invalid, unreadable or uninterpretable policy fails closed. Permissions are re-evaluated before any effect, including after a HUMAN approval.

Malformed paths, arguments, invalid UTF-8 and unsupported regex are `VALIDATION/invalid_argument`. An initially requested file/directory path that is missing or has the wrong required type uses `VALIDATION/path_not_found` only on a method that allows that code; it is not a generic error for a stored workspace, plan or operation ID. The registered-root rules in §1 apply to `GetWorkspace`. `PlanRemoval` uses its allowed `STATE/not_found` for an unknown workspace or attempt; `ExecuteRemoval` uses it for an unknown plan, and the operation status/acknowledgment methods for an unknown operation. A path-based `ReadFile`, `WriteFile`, `EditFile`, `SearchFiles` or `ListDirectory` selection of an unregistered workspace instead violates that method's required registered-root argument and uses its allowed `VALIDATION/invalid_argument` with `workspace_id.registered`; it is not an observed native path change or permission failure. In `ExecuteRemoval`, a known plan's target that disappeared or changed type before execution uses `CONFLICT/file_changed` with `planned_tree_changed`, before any effect. Exceeding a write, edit, path or plan maximum is `RESOURCE/too_large` with the actual applicable limit; unauthorized operations are `AUTHORIZATION/permission_denied`. A hash, path identity or observable replacement mismatch is `CONFLICT/file_changed`; a wrong edit count is `CONFLICT/occurrence_mismatch`; both are NEVER/DID_NOT_HAPPEN when discovered before effect. A refusal caused by the OS before any effect is `STATE/file_access_denied` with a closed reason, NEVER/DID_NOT_HAPPEN. No body or secret appears in an error. A pending approval uses `AUTHORIZATION/approval_required` and its approval ID; it is not an auto-approval.

**Error-layer clarification, 2026-11-10 (AF-CTR-06 target).** The write, edit, path and plan resource maxima above are checked as resource bounds on an otherwise decodable request: exceeding one returns `RESOURCE/too_large`, NEVER/DID_NOT_HAPPEN, with `details.limit.limit_name` identifying that bound and `maximum` giving its actual configured maximum in the bound's units. This applies to the node method and its Fleet counterpart. Malformed encoding, invalid identifiers, path syntax and other field-rule violations remain `VALIDATION/invalid_argument`. A center refusal made before delivery is an outer Fleet `ArcError`; it is not a fabricated signed node outcome. The target node independently checks the same bounds and returns its own error when it makes the decision. An unavailable result or audit measurement is not invented.

### Replay admission, signed time and transport

For a routing record created at center time `C`, keep its configured replay window `W` and exclusive cutoff `R = C + W` fixed. A new file/workspace call has a Fleet deadline at most 15 seconds and a signed expiry at most 30 seconds after that deadline, hence at most 45 seconds after signing. Pass the original `C` into signing and refuse an observed signing time earlier than `C`; do not invent a timestamp to conceal a clock regression. For an attempt that may already have been delivered, authorize and observe the send only while center time is before `R`, and fix the signed expiry before any queue or write wait, no later than `R + 45 seconds`. Never re-sign or extend that header after a pause. A genuinely proven NOT_DELIVERED attempt follows the existing separate rule; this paragraph does not silently turn it into a potentially delivered attempt or restart an existing command's identity.

Recheck the exclusive cutoff after queue waits and at the final send observation, and bound the write wait by the previously fixed remaining duration on the monotonic clock. A context timeout, `SetWriteDeadline`, last time check or queue-state transition is not an atomic wall-clock condition on every eventual network byte: scheduling and transport buffering may intervene. Once a write may have begun, its mutation is potentially delivered and failures remain UNKNOWN; never claim DID_NOT_HAPPEN merely because the timeout fired. No deferred write may acquire a new signature or later expiry. The target's actual expiry recheck and durable deduplication are required for the safety of delayed frames; a best-effort transport deadline alone is not that proof.

The conservative bound must be established in the real implementation. If the first node receipt time `E` is at least `C - 120 seconds`, its minimum expiry is `E + 24 hours`. With the node's extra 120-second expiry tolerance, a valid new-method signature permits an effect only while node validation time `N < C + W + 45 seconds + 120 seconds`. At the maximum `W = 23 hours 52 minutes`, this remains 195 seconds before the earliest node receipt expiry, leaving 135 seconds beyond the required 60-second margin. The initial `E` bound must be checked against the actual signing and node transaction clocks, not assumed from a field shape. The node must use a coherent time/retention model for both comparisons, including the persistent clock rules in §6; a forward deletion followed by a backward clock step invalidates the argument if old signatures can become valid again. These conditions are implementation and native acceptance requirements, not evidence that the current WIP meets them.

Tests distinguish the final send observation from a physical packet deadline: pause after the delivered transition, wait inside the WebSocket writer, block an actual write, and delay an already signed frame past its permitted lifetime. Prove fixed signature identity/expiry, truthful delivery classification and no new node effect beyond the protected deduplication horizon. Retain successful retries immediately inside both configured window bounds and refusal at the exclusive cutoff; an earlier blanket refusal does not substitute for those positive cases. Use the real node expiry and journal code in the final native paths; synthetic handlers establish only their named center component.

## 5. Ownership, approval and restricted cleanup

A newly created path is eligible for unattended agent removal only when creation succeeded through this API with `expected_absent`, and a durable ownership record binds its workspace, relative name, opened volume/file identity, last node-written content hash, creation evidence and the verified specific caller (agent grant identity when AF-CTR-07 exists, or verified relaying node plus local agent session in AF-CTR-06). To prevent a deleted and recreated name being treated as the same object after restart, the node records an unpredictable per-creation marker on the created object using a handle-relative platform metadata facility, such as an extended attribute on Linux or an NTFS alternate stream on Windows, together with the file identity in its protected store. The marker is written only on node-created objects; the file API does not expose arbitrary extended attributes or streams. On subsequent checks the record, file identity, marker and last node-written hash must all match. If the filesystem cannot persist or read the marker safely, the write can still succeed, but later unattended cleanup is unavailable and a HUMAN decision is required. The marker is an ownership guardrail, not a boundary against another process of the same OS user, which can access the same files. A successful controlled replacement transfers the ownership marker and record only when performed for that same owner; any other replacement or externally changed content invalidates unattended ownership. Merely overwriting an existing file never claims ownership. Paths created by another agent, an unknown principal, a HUMAN, or outside this API are not agent-owned. Verify the identity and ownership evidence again immediately before removal; a replaced or recreated same-name object loses ownership. A filesystem lacking enough durable identity evidence after restart is treated as unowned, never guessed. Another process of the same OS user can directly change filesystem objects and is outside an agent confinement claim (§2).

A task temporary directory qualifies only when the persisted task/attempt and managed-directory records bind the exact `attempt_id` and its directory to that same specific caller, the attempt is terminal, and it is no longer in use by a queued/running attempt, live session, pin or lease. No absolute path is accepted from the caller. Re-derive and recheck the node-owned root, attempt, caller and directory identity at execution, including after approval or restart. This is a cleanup-only exception for that exact managed temp root, not permission for arbitrary file access outside registered workspaces.

This task targets the narrow form of 06 §7, not AF-STOR-01's analyzer: plan one explicitly named object, enumerate at most 1,000 descendants and 64 MiB, and bind the plan ID/digest, caller, target, every descendant's identity/type/fingerprint, aggregate size, chosen action and 60-minute expiry. There is no wildcard or recursive-delete argument. Planning causes no removal. Before executing, revalidate the plan, root, target, each child and in-use constraints; a changed, newly unowned or newly added descendant invalidates the earlier plan and its approval; an explicitly listed unowned item requires the HUMAN decision below. Classify an item as low risk for this restricted operation only when its caller ownership or eligible task-temp provenance is verified and all preconditions still hold; an unowned or ambiguous item is not low risk. Agent `file.remove=ALLOW` is insufficient by itself: unattended execution also requires `cleanup.agent_execute=LOW_RISK_ONLY`, every selected item to be low risk, and every item to be verifiably owned by that agent or within its own eligible task temp. When `file.remove` permits the request but the cleanup policy or risk requires approval, a real local HUMAN must decide the exact plan and digest; unowned items always need that decision regardless of low-risk policy. For production or user-owned files, the requester's agent, its account login and an automated fixture cannot manufacture the decision: it must be an independently authorized local HUMAN. An isolated test may use a synthetic HUMAN/process to invoke the real approval, origin classification and policy code against exclusively test-owned data; record the actor as MOCKED and the actual code and native filesystem as REAL, and never claim that the owner approved anything.

As in 06 §7, the intended successful removal moves the exact verified planned object to private same-volume quarantine, records `QUARANTINED` only after that actual authorized effect, and retains it for at least the existing 24-hour recovery window. This success remains required for AF-CTR-06 and is not yet established on the Linux host. The general retention purge, restore and storage-analysis services remain AF-STOR-01; CTR06 does not claim they are delivered or silently purge by an unsafe pathname. An agent may request removal; the result is the actual quarantine move, not a claim that bytes or evidence were destroyed. An agent may propose an unowned path inside the registered workspace for approval, but its proposal is not authority to act. When a planned tree is not wholly agent-owned, the approval shows the exact paths, sizes and risks; a local HUMAN must explicitly select that exact plan and separately confirm any path that 06 §7 treats as external. An agent cannot add external paths as though the HUMAN had selected or confirmed them. If there is no configured/confirmed same-volume quarantine root, do not quietly delete: an explicit HUMAN per-item delete-without-quarantine confirmation is necessary. Direct deletion additionally requires an OS operation that acts on the held verified object without replacing or deleting a different name. Where that cannot be established, including the generic Linux `unlinkat` name race, return `RESOURCE/enforcement_unavailable`, NEVER/DID_NOT_HAPPEN before effect; confirmation does not manufacture such a primitive. The plan's digest and ownership are rechecked after approval. Quarantine does not authorize a changed object, mount crossing, link traversal or a user file hidden inside an agent-owned directory. General analysis, managed-worktree removal and their wider cleanup classes are not delivered here.

**Open-object guard before capture (AF-CTR-06 target; scope pending review).** The existing 06 §7 rule says open files are `IN_USE`; its ordinary-user protection and the checks for queued/running attempts, live sessions, pins and maintenance leases remain. One proposed clarification is to treat external data/read/write/execute/delete use and mapped content as conflicts, without counting the node's own verification handles or metadata-only references that cannot themselves perform such access. That narrower interpretation of “open” has **not** been independently reviewed or accepted as a replacement for 06 §7. In particular, a successful Linux write lease does not prove the absence of every external descriptor: a separate process's `O_PATH` descriptor coexisted with it in L-32. Independent review must resolve this scope before the proposed interpretation can be used for acceptance; a lease or a rename must never be represented as proof that no file is open.

After plan and approval revalidation and before any cleanup namespace effect, acquire and retain the applicable native exclusion guard for the exact checked regular file and **every** regular file in a planned directory tree. Hold no-follow object and directory handles and compare their identities to the plan. An external data reader, writer, executor, delete-capable handle or mapped-content conflict must at least result in `STATE/in_use` with retry advice and `retry_at`, before effect. If a guard, object identity or type, complete bounded enumeration, descriptor capacity or required capability cannot be established, return `RESOURCE/enforcement_unavailable` before effect. A HUMAN approval cannot waive either check. The guard set is bounded by the 1,000-descendant plan limit and is acquired deterministically. Even a complete guard set for the previously enumerated files is **not** the namespace-stability proof required below.

On Linux, an exclusive `F_SETLEASE/F_WRLCK` on each verified regular-file open description is a candidate guard for the conflicting data opens and mappings it actually covers. A conflicting lease `EAGAIN` or an active executable's `ETXTBSY` while opening the guard maps to `STATE/in_use`; unsupported filesystem, privilege, ownership or signaling capability maps to `RESOURCE/enforcement_unavailable`. Do not alter host settings or substitute advisory locks. Handle lease-break notifications safely and inspect all leases before an effect; a pending or broken guard refuses before effect. If a guard is lost after an independently authorized effect, stop and record the actual outcome, preserving recovery evidence; UNKNOWN is not a license for an unapproved namespace effect. A later data open through a pre-existing `O_PATH` handle triggered the tested lease (L-32), but the `O_PATH` itself did not prevent granting it. Guard descriptions stay private; a mapping or duplicate of the guard's own open description is not an independent-open test. Unobservable or unsupported conflicts fail closed. A Linux file lease is neither a directory lease nor a namespace lock: L-33 shows a leased file can be renamed without a lease break and a newly added, open descendant can be moved with its parent.

On Windows, a candidate open-object guard retains each checked regular-file handle under no-sharing rules, with the access needed for identity and the intended effect, and relies on the OS's two-way share checks for the access modes they cover. A sharing conflict returns `STATE/in_use` before effect. Retain the checked directory handles too; if a needed guard, mapping check or guarded operation cannot be established, refuse rather than release a guard and continue. ## 6. Mutation journal, restart and audit

The node serializes its file effects per workspace/path. `WriteFile`, `EditFile` and `ExecuteRemoval` use a durable filesystem journal keyed by command ID, exact request digest and verified caller. A different payload or caller for the same ID is refused; an identical completed command returns its recorded metadata outcome without reapplying it. `RegisterWorkspace`, `UnregisterWorkspace` and `PlanRemoval` atomically commit their registration/plan metadata and command receipt in SQLite, without a filesystem-effect journal or file-operation status. Their uncertain-commit and receipt recovery rules are in §4. Filesystem effects are not part of that metadata transaction: before the first effect, durably record the command, root/parent/target identity, precondition and intended size/digest in a PREPARED journal entry. Stage the bounded intended bytes and, for an existing file, the bounded original bytes in private, access-restricted storage on the target volume; flush the staged bytes and journal before the first effect. A synchronous non-approval operation may use anonymous temporary objects (`O_TMPFILE` on a supporting Linux filesystem, or Windows delete-by-handle/delete-on-close) so successful operations release them without a name-based deletion. An anonymous stage disappears when its last handle is lost, including on a crash: the durable journal still returns UNKNOWN and must report that the staged preimage is unavailable; it never promises restoration from missing bytes. A delayed approval needs a named, durably flushed stage that survives restart and is bound and rehashed as below. Where anonymous staging is unavailable, an access-restricted named stage is permitted only with the explicit bounded retention and safe-disposition rules below. Do not put bytes in audit, the center, or an approval's captured request. The operation on an existing file uses the checked handle protocol in §2a, not a name-based replacement. After the effect and the required filesystem durability operations, commit the resulting metadata and receipt to SQLite before answering success. Preserve the existing file's owner, mode, ACL and non-content attributes, including extended attributes and alternate streams; if a safe bounded preservation cannot be established, refuse before effect. Never silently widen access.

If the node stops after PREPARED and before a durable completed receipt, recovery inspects only this operation's exact recorded identities and staged object. It must never overwrite or remove a different object, infer success solely from a matching pathname/hash, or automatically repeat an effect whose prior completion is uncertain. Where it cannot prove the outcome, durably mark UNKNOWN, retain the minimum owned recovery evidence, refuse further mutation of that target until a local HUMAN acknowledges the uncertainty, and expose a bounded `GetFileOperation(command_id)` status to the original caller and local HUMAN. A blocked mutation returns `STATE/invalid_state` with reason `file_recovery_pending`, NEVER/DID_NOT_HAPPEN, and points to the status; it never waits indefinitely. The HUMAN-only acknowledgment, with the original request digest, releases this hold without modifying user files or pretending the old operation succeeded. Keep unresolved metadata until acknowledgment. Named durable staging bytes are retained for at least 24 hours and may be removed only with an OS effect tied to the verified held object; a last name check followed by Linux `unlinkat` is not such a primitive. If safe disposal cannot be established, retain the staged object and surface its exact location to a local HUMAN for inspection and disposition; never delete a replaced or unidentifiable staging path or claim it was disposed. Bound total private staging to 256 MiB and 64 active file mutations; refuse new mutations with an explicit resource error when the bound is exhausted rather than silently delete evidence or wait forever. A duplicate of an UNKNOWN command returns the recorded uncertainty and never executes again; a different command ID cannot bypass the hold. Completed operation status and dedup metadata remain readable for at least 24 hours from the first execution; unresolved UNKNOWN and its hold remain until a local HUMAN acknowledges, even beyond that period. After acknowledgment, retain its terminal metadata at least until the original 24-hour window has elapsed. After a completed status ages out, report it unavailable, not DID_NOT_HAPPEN or success; the center's shorter replay fence still forbids delivery. The original caller's status is read-only and never extends the replay window. Status has additive v1 node and Fleet interfaces; acknowledgment is an additive local node management interface only. Both are audited and expose no file bodies.

Approval records carry metadata only, not write/edit bodies or search content. An approval binds the original command ID, exact request digest, verified requester, operation and target, root/parent/target identities, expected target hash or expected absence, plan ID/digest when applicable, staged object identity, and intended staged byte length and SHA-256. If policy requires approval for a write/edit, keep its bounded staged bytes in the private journal, referenced by that approval. After approval and after any restart, safely reopen or retain the staged object by its recorded identity; acquire the platform's write-exclusion guard, hash its complete exact byte sequence again and compare its length and SHA-256 to the approved intent. Revalidate caller, current policy, approval expiry, target identity and precondition immediately before effect. The exact staged handle whose bytes were rehashed remains guarded and is the source used for the effect. If its identity, bytes, size or any binding differs, fail before changing the target; an in-place stage modification is not excused by matching file ID. If guarding or rereading cannot be established, fail closed. An isolated test tampers with the staged bytes during pending approval and across restart and proves neither target nor unauthorized object changes. Secure disposal and its limits follow existing node-data retention and OS permissions; no physical-erasure guarantee is invented.

### Durable time and replay retention

The file/workspace expiry checks and receipt/journal retention must remain safe across restart and wall-clock steps. A forward wall-clock jump must not permit premature deletion of a completed command, followed by a backward jump that makes an old signed request valid again. Use a persisted nondecreasing validation-time boundary and establish at least 24 hours of elapsed retention independently of a wall-clock jump; conservatively retaining existing completed receipts for another 24 hours after a restart is permitted. Expiry checks immediately before an effect and pruning must share this safety model. If time continuity, the durable boundary or retention evidence cannot be established, refuse a new effect and keep recovery metadata rather than delete it, guess success or repeat an effect. Do not silently disable signature expiry. The implementation must also handle a frozen clock or a material disagreement with monotonic elapsed time explicitly. The exact algorithm and appropriate existing refusal code remain implementation/review work, not a new wire field or an owner-only mock exception.

Test forward-jump pruning followed by rollback, restart between those steps, a delayed previously signed request and receipt/status reuse through the real node code. Neither a center-only expiry calculation nor an unchanging fake clock establishes these properties. These requirements do not change unresolved UNKNOWN holds, HUMAN acknowledgment or the strict filesystem rules.
