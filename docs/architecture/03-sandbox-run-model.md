# 03 — Sandbox and Run model

## Sandbox aggregate

`SandboxId` is an opaque 128-bit ID allocated once. A display name is 1–80 Unicode characters, unique per owner after normalized comparison, never used as a filesystem path. `revision` is a positive monotonic integer. A Sandbox contains owner principal, creation timestamp, current configuration, data-root-relative directory identity, lifecycle state, and an optional local remote grant. Renaming never moves data.

Configuration is versioned as a whole: backend profile; environment allowlist; default work directory; read-only/writable host grants; network policy; max concurrent runs; resource weight/priority/ceilings and pressure action; terminal/output retention. Store a canonical digest, not credentials or raw inherited host environment. Secrets are explicit user injections from protected local storage and are redacted from stored snapshots and logs.

`Create` validates the complete profile, transactionally reserves ID and path, creates owner-only directories with a manifest, then commits READY. Partial creation becomes ERROR with an owned cleanup record; never recursively delete an unverified path. `Configure(expected_rev)` validates the full replacement and optional display name; name-only edits supply the unchanged config and never move data. Explicit local `repair_error=true` repairs ERROR only after exact ownership, no-use and no-unresolved-effect checks; it is not a general RECOVERY_REQUIRED override. Path/network/identity changes require no nonterminal Run, preventing an existing process from retaining revoked host grants. Live resource changes use `ResourceService.SetPolicy` and commit requested versus applied/read-back state separately. A failed OS apply is not advertised as enforcement.

`List` is owner-filtered and cursor-paginated. `Inspect` returns current revision, capabilities and limitations, active Run IDs, private usage and excluded host mounts. Remote callers see only grant-visible fields. `PlanDelete` gives a short-lived revision-bound plan, active-run refusal and exact owned subtree/bytes; `Delete` consumes that plan only if identity, revision and no-use guards still hold. External grants are never deletion targets. Quarantine/journal cleanup is recoverable; concurrent Run starts are blocked under the same ownership lock. A preview may be abandoned before Delete. Accepted deletion is not cancellable; a local Delete with resume_command_id is a fresh, journal-linked authorization for the same original intent under the exact guards in the API conventions.

## Run aggregate and launch

A Run has opaque RunId, SandboxId, monotonically increasing revision, Run epoch, supervisor instance identity, boot ID, native process creation identity, platform resource identity, canonical launch digest, immutable config snapshot, state, timestamps, output sequence range, resource observations and optional authoritative exit result. A Run is never reused for an automatic retry. Its wire projection includes a redacted safe command display, immutable sandbox_revision and profile_version; historical records never read these from the Sandbox's later current config.

`Start` supplies SandboxId, explicit argv array, root-relative work directory, explicit environment additions, `interactive` or `pipes` terminal mode, initial rows/columns when interactive, and desired resource policy bounded by the Sandbox ceiling. User-requested shell execution is explicit (`shell -c` or `cmd /c` in argv). The trusted adapter uses the tested Windows/POSIX serializer required by the official backend; it never interpolates raw arguments into shell syntax or evaluates them on the host. Resolve executable paths under the profile, reject missing capabilities and bind canonical path/file identity where supported.

Admission is synchronous and finite: validate/authenticate; reserve command ID; lock Sandbox; check revision and no-delete state; reserve resource grant; create STARTING record and supervisor; install OS resource/confinement settings before user code; read back required controls; then mark RUNNING when the supervised execution is active. This does not assert that the payload reached its entry point; `payload_started` remains UNKNOWN until independently proved. Lack of capacity returns `RESOURCE/budget_unavailable` with no queued task. A caller may retry later as a new explicit action only after knowing the previous effect. There are no DAGs, retries, task result caches or compiler adapters.

A lost reply after admission is `UNKNOWN` and resolved using `GetOperation(owner_epoch, command_id)` plus `Run.Inspect`. Reusing the same ID and identical canonical payload returns the original record; changing the payload conflicts. Never automatically invent a new command ID after timeout.

## Execution and terminal behavior

Interactive mode means real PTY/ConPTY with terminal size, UTF-8 byte streams, TUI escape sequences, foreground input and signals; it is a negotiated capability. Pipe mode is explicit and remains useful for redirected batch output; it is not represented as an interactive terminal. Only one attachment owns the writer lease, with a short renewable expiry and epoch. Read-only output watchers do not obtain input permission. Lease expiry or CLI disconnect stops writes and detaches, while the supervisor retains the Run.

The byte stream uses Run epoch and increasing byte offsets. A bounded spool reports a gap when a client asks before the retained beginning; it does not manufacture old output. Resize and input commands must carry the current lease ID/generation; stale writes are rejected. Local detach releases only the lease. Local attach may take a lease only with the same OS owner authorization; forced takeover is an explicit action shown to the user. The Web V2 dashboard watches logs and controls runs; a remote browser terminal is not a V2 delivery requirement.

`Stop(grace_ms)` is an explicit group-level operation: request the platform's tested graceful interrupt, wait within a bounded timeout, terminate the verified whole owned group, and confirm emptiness. The returned receipt says requested or complete; `STOPPING` persists until authoritative completion. Do not equate request cancellation or SDK object disposal with confirmed process termination. Unknown ownership becomes RECOVERY_REQUIRED; never kill a bare reused PID.

## States and output truth

Sandbox: CREATING → READY → DELETING → DELETED, with ERROR and RECOVERY_REQUIRED when construction/deletion/ownership is unresolved. Run: STARTING → RUNNING → STOPPING/DRAINING → EXITED, with FAILED for definite pre-start/launch failure and RECOVERY_REQUIRED for unresolved ownership. Exit codes are present only when observed from the authoritative supervisor/backend; an OS-killed or lost run records a reason even if no numeric exit code is available. A normal parent/executor exit enters DRAINING and cannot make a Run EXITED while managed descendants remain. The stable one-shot backend cleans up descendants when the root exits: long-lived services keep a foreground root, and daemon children are not promised to survive root exit. Record `exit_source` separately as payload, official_executor, supervisor or unknown; never parse terminal output as a trusted completion message.

Node startup reconciles records with authenticated supervisors before admitting conflicting work. Host reboot ends prior Runs and records an interrupted/reboot reason. Reconnecting a still-alive supervisor is recovery, not replay of Start. Exact transition guards/effects are normative in [machines.json](../state-machines/machines.json).
