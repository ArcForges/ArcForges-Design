# Architecture

This directory defines system architecture, runtime topology, component boundaries, data ownership, communication protocols, and security models for ArcForges.

All content here is **authoritative**. Later explicit user amendments apply, including the C#-first implementation decision [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021), which supersedes [P2-008](../decisions/phase-2-specification-decisions.md#rule-p2-008) in part (items 1, 2 and 4; item 3 narrowed; items 5 and 6 in force) and amends the Kotlin, npm and Maven parts of [P2-009](../decisions/phase-2-specification-decisions.md#rule-p2-009) and [P2-010](../decisions/phase-2-specification-decisions.md#rule-p2-010), together with the scope decisions [P2-022](../decisions/phase-2-specification-decisions.md#rule-p2-022) (PDF preview retirement), [P2-023](../decisions/phase-2-specification-decisions.md#rule-p2-023) (macOS out of scope), [P2-024](../decisions/phase-2-specification-decisions.md#rule-p2-024) (WSL2 Linux validation) and [P2-025](../decisions/phase-2-specification-decisions.md#rule-p2-025) (blocked-external inputs). It is governed by the frozen Phase 1 decisions in [`../decisions/phase-1-foundation-decisions.md`](../decisions/phase-1-foundation-decisions.md) ([D-001](../decisions/phase-1-foundation-decisions.md#rule-d-001) … [D-023](../decisions/phase-1-foundation-decisions.md#rule-d-023)) and by the verification record in [`../assurance/phase-1-official-verification.md`](../assurance/phase-1-official-verification.md) ([V-01](../assurance/phase-1-official-verification.md#rule-v-01) … [V-09](../assurance/phase-1-official-verification.md#rule-v-09)). Architecture realises the requirements in [`../requirements/`](../requirements/README.md); where the two appear to disagree, the requirement states *what* must be true and the architecture states *how*, and any genuine conflict is a defect to be resolved, not a choice to be made at implementation time.

## Reading order

Read [`00-architecture-overview.md`](00-architecture-overview.md) first — it establishes the five controlling constraints, the runtime topology, the layering rules and the single write path that every other document assumes. Then read [`01-solution-and-project-layout.md`](01-solution-and-project-layout.md) and [`02-contracts-and-protocols.md`](02-contracts-and-protocols.md), which fix where code lives and how components speak to each other.

Documents `00`–`25` state architecture: boundaries, ownership and rules. The [`contracts/`](contracts/00-operation-catalogue.md) and [`data-model/`](data-model/00-data-model-overview.md) subdirectories state the **concrete design those rules produce** — the actual operations, signatures, events and schemas. A rule without its concrete counterpart is not yet implementable, which is why they are held to the same authority.

## Conventions

- Every architectural rule carries a stable identifier (`AB-nn`) scoped to its document, so requirements, assurance and work packages can cite it precisely.
- A rule states an obligation that a reviewer or a test can check. Where a rule is machine-checkable, the corresponding architecture or repository-policy test is named in [`01-solution-and-project-layout.md`](01-solution-and-project-layout.md) or in the document's own testing section.
- Citations to Phase 1 decisions use **D-nnn**, verification findings use **V-nn**, and deferred gates use **F-nnn**.
- Historical input provenance is retained in the completed foundation records and [deprecated archive](../deprecated-inputs/README.md), outside the active design dependency chain. Current design rules and their concrete definitions must be stated in the formal layers; the archive cannot supply a missing normative answer.
- Superseded product names (`ArcCanvas`, `ArcMusic`, `ArcImage`, `ArcVideo`) and the superseded payment provider never appear as current, per **[D-002](../decisions/phase-1-foundation-decisions.md#rule-d-002)** and **[D-005](../decisions/phase-1-foundation-decisions.md#rule-d-005)**.

The [content and extension isolation design](24-content-and-extension-isolation.md) specifies [P2-007](../decisions/phase-2-specification-decisions.md#rule-p2-007)’s C# helper, OS profiles, broker limits and packaged-RID evidence.


**Rewrite status (2026-10-08, P2-021 to P2-025).** The decision records are authoritative for every stack, PDF, macOS and WSL statement in this directory. The stack clauses of [01](01-solution-and-project-layout.md) are rewritten in place by the pending rows of [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021), and its historical Android block is marked superseded. The bodies that are not yet rewritten in place are [10-web-architecture](10-web-architecture.md), [11-mobile-architecture](11-mobile-architecture.md), [25-web-toolchain-and-sdk](25-web-toolchain-and-sdk.md), [14-build-packaging-and-release](14-build-packaging-and-release.md) and [contracts-publication-channels](contracts-publication-channels.md), together with the other bodies named in the pending table of P2-021. Under the pending-row rule of P2-021, each old-stack sentence in those bodies is superseded by P2-021 to P2-025 and is not current until its row merges. Where a body states a rule that stays in force until its row merges, that rule governs; CS-01 in [architecture 10](10-web-architecture.md) line 115 is one example.

The [Web toolchain and generated SDK contract](25-web-toolchain-and-sdk.md) defines handwritten proto → generated packages, exact values, browser/realtime adapters and release gates. [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021) replaces its React/TypeScript/Node workspace, esproj and npm entry points with a C#/.NET Blazor WebAssembly toolchain and generated C# NuGet SDKs. [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021) supersedes [P2-008](../decisions/phase-2-specification-decisions.md#rule-p2-008) items 1, 2 (its TypeScript and OpenAPI-to-TS SDK parts) and 4, narrows item 3 (Node is build and deploy tooling only; the Harness host is C#), and leaves items 5 and 6 in force.


[P2-009](../decisions/phase-2-specification-decisions.md#rule-p2-009) together with [P2-010](../decisions/phase-2-specification-decisions.md#rule-p2-010) is the current repository/runtime/protocol authority. The [numbered protobuf wire registry](contracts/04-protobuf-wire-registry.md) supplies exact request/result/shared schemas; the [Cloudflare integration contract](contracts/05-cloudflare-integration.md) supplies execution, model, object and recovery state/ports. Their selected contracts are implementation inputs, including for local RPC, MAUI Android and Blazor Web. The Kotlin Android wording of [P2-010](../decisions/phase-2-specification-decisions.md#rule-p2-010) is superseded by [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021).

[P2-010](../decisions/phase-2-specification-decisions.md#rule-p2-010) initial implementation authorities: [native functional ABI](contracts/06-native-functional-abi.md), [client journeys and ports](contracts/07-client-journeys-and-ports.md), [extension/policy/configuration schemas](contracts/08-extension-and-policy-profiles.md), [product behavior profiles](26-product-behavior-profiles.md) and [producer stages](../planning/producer-artifacts-and-integration.md).
