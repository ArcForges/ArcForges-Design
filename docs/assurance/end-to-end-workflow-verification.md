# End-to-End Workflow Verification

> Status: **Authoritative** — Phase 2; reconciled under [P2-007](../decisions/phase-2-specification-decisions.md#rule-p2-007) against the fourteen repair groups.
> Scope: executable **design traces**, not claims that product code, packaged sandboxes, databases or provider integration already passed.

This document follows authority, commit boundaries, failure recovery and delivery ownership through the commercial product. Current rules replace the older traces at baseline c5b95a7; Git preserves that history. [Design closure evidence](phase-2-design-closure-review.md) records the counterexamples and document checks. ## 1. How a trace closes

Each trace names an authoritative operation/store, its commit unit, the uncertain interval, the recovery path and the work package that proves it with real code. A requirement alone is insufficient. A future runtime gate cannot excuse an undefined schema, contradictory algorithm or missing dependency in the current design.

## 6. Cloud tool, native Product Job and automation

The [durable bridge](../architecture/contracts/03-realtime-and-bridge.md) creates a ToolRequest, which Desktop pulls and re-authorises. Native render/analysis returns ProductJobRef, not an Agent Task. The product owns job checkpoints, progress and cancellation; Cloud owns the calling Step and records its result idempotently. No Cloud connection to local IPC and no local Harness is introduced. The command log resolves local effects; effects across a further external network still follow their own status/idempotency/unknown protocol. [WP-26](../planning/work-packages/26-remote-action-and-tool-bridge.md#rule-wp-26) and [WP-52.05](../planning/work-packages/52-cloud-harness.md#rule-wp-52.05) prove this with a real product process.

Cloud automation stores immutable definition versions and unique trigger occurrences, creates each linked Task once and uses the same Harness/admission. Two replicas, catch-up, clock rollback, disable/revoke and storm limits cannot create duplicate or unbounded work. [WP-17.04](../planning/work-packages/17-arcchat-independent-core.md#rule-wp-17.04) is the client half; [WP-52.06](../planning/work-packages/52-cloud-harness.md#rule-wp-52.06) supplies and verifies the scheduler. Desktop displays automation rather than scheduling AI locally.

### 6.1 First ArcChat–ArcNotes workflow acceptance

This is the canonical first cross-product scenario. [WP-20](../planning/work-packages/20-first-cross-product-workflow.md#rule-wp-20) proves the native capability portion by direct invocation. [WP-52.05](../planning/work-packages/52-cloud-harness.md#rule-wp-52.05) proves the complete agent-driven path with real Cloud admission, a real provider and the signed device bridge. A native capability test does not claim that the Cloud workflow has passed.

**Inputs.** Use an authenticated single-owner workspace with an active service term, available included capacity or authorized extra credits, an allowed model and a registered desktop device. ArcNotes is installed on that device and exposes its typed document capabilities. The user requests a report using an explicitly selected, permission-readable note at an acknowledged Cloud revision. Fix the source, requested output structure and effective policy for the test; use an isolated test workspace. Exact model prose is not an oracle: required structure, authorized source provenance, ownership, revisions and durable outcomes are.

| Step | Required behavior and observable result |
|---|---|
| Accept the request | Chat acceptance and its Cloud Task commit through the existing receipt transaction. Retrying the same request returns the same accepted work. The Run records the effective model, policy and commercial authority. |
| Prepare the report | The single Cloud Harness retrieves only the selected authorized context, invokes the provider under a reservation and persists the delivered iteration and usage. The desktop runs no model loop. |
| Authorize document changes | Cloud creates durable typed tool requests. ArcChat Desktop pulls them, validates the signed request, and re-authorizes at the resource owner. Any approval required for creation or content insertion is obtained **before that mutation**, bound to its actual parameters and current resource revision. A displayed proposal is not a write. |
| Create and populate | ArcNotes creates the document and inserts the structured report through its typed application commands. Each distinct write has a stable command identity, one durable command receipt and one resulting revision. Retrying after a lost acknowledgement reuses that command identity and returns the existing outcome. Content never travels through the Hub as an unbounded inline body. |
| Save and synchronize | The native commit survives process restart. Keep the tool's declared commit boundary; the acceptance run additionally waits for and checks the acknowledged Cloud revision through the declared sync path. A pending native edit is never displayed or counted as an acknowledged Cloud save. |
| Return the result | ArcNotes returns an artifact reference owned by ArcNotes. ArcChat presents its bounded preview and opens the owning editor on handoff. Resolving the reference re-checks permission and reports changed or deleted content. The Cloud Task reaches its documented terminal outcome only after its required tool results and final-message receipt commit. |
| Prove undo and recovery | In an isolated repetition, undo and redo the accepted content edit through ArcNotes, verify the resulting document and revisions, then kill and restart during an unacknowledged write. Recover to the last durable commit; reconcile the command receipt before retry. Neither undo nor a client restart reverses already settled provider usage. |

| Failure injection | Required outcome |
|---|---|
| Target device offline before dispatch | Cloud records the declared waiting-for-device outcome and the client shows the unavailable device. No local agent substitute or unapproved document write appears; resume follows re-authorization and existing command identities. |
| Approval rejected or expired | The affected mutation does not execute. Expiry cannot be treated as approval; any subsequent attempt requires fresh authorization. Earlier committed document changes, if any, remain visible and are not silently rolled back. |
| Capacity exhausted before a later provider call | No additional provider dispatch occurs until the existing admission policy permits it. The client shows the precise capacity refusal/waiting outcome and recovery information; completed invocations remain settled once. |
| Paid term expires during the Run | Subsequent provider calls fail the service-term check even if purchased credit remains. Any already dispatched invocation is resolved and settled under its original snapshot; expiry does not delete the document. |
| Crash after tool dispatch but before a recorded outcome | Effect certainty remains unknown until the existing command receipt/status path resolves it. A timeout is not proof of no effect. A retry creates neither a second document nor duplicate blocks. |
| Concurrent edit or permission revocation | Revision/permission validation refuses the stale or unauthorized mutation with the defined conflict/refusal outcome. No silent overwrite and no stale approval reuse occur. |
| Restart after native commit but before Cloud acknowledgement | The native write and outbox recover; receipt-based sync converges to one Cloud result. Pending state remains explicit until acknowledgement. |

The operation envelopes and error classifications come from the [operation catalogue](../architecture/contracts/00-operation-catalogue.md), local commands from the [typed local interfaces](../architecture/contracts/02-local-rpc-operations.md), and dispatch/recovery from the [bridge contract](../architecture/contracts/03-realtime-and-bridge.md) and [Harness](../architecture/17-agent-harness.md). Test evidence records command receipts, native/Cloud revisions, Task/Run outcomes and metering entries through the existing privacy-safe test interfaces. A waiting outcome is an asserted result, not a falsely reported terminal completion.

## 7. Deterministic simulator

Scenario validation, seed/execution-profile pinning and bounded duration/sample/byte/egress reservations precede work. The single Cloud host executes bounded leased slices. Every segment publication checks the current fence and atomically commits verified Resource references, quota consumption, manifest range and checkpoint. After a killed host, a new holder continues the same logical range; a stale holder cannot publish. Realtime is optional; polling the retained manifest recovers all committed segments. Cancel/term expiry records a partial or cancelled result, never success for incomplete output. Native ingestion/replay keeps synthetic provenance through analysis, report, copy and export. All of these belong to [WP-51](../planning/work-packages/51-arcscope-cloud-simulator.md#rule-wp-51); desktop capture [WP-33.06](../planning/work-packages/33-arcscope-acquisition-and-session.md#rule-wp-33.06) is not simulator evidence.

## 9. Configuration, migration and release order

Configuration activation enlists the exact Config/Entitlement/Commerce/Agent/Policy write sets under the shared unit of work. Snapshot/head/offer-policy period changes commit together; private parameters never enter the client projection. Workspace-specific term/plan changes advance old capacity before recording new boundaries. Restart preserves balances and reservations. [WP-44.01](../planning/work-packages/44-dynamic-policy-and-configuration.md#rule-wp-44.01) and [WP-42.11](../planning/work-packages/42-commerce-entitlement-and-credits.md#rule-wp-42.11) test the actual implementation.

[Migration cutover](../architecture/22-deployment-and-release-execution.md#25-versioned-capture-backfill-and-cutover) uses per-key source versions and tombstones, guarded backfill/capture writes, a completed range manifest and an exclusive writer fence. The fence drains prior writers and all committed capture, verifies dirty ranges and changes epoch/authority atomically. A/B retain a lossless old authority through the horizon; C closes data rollback at its switch. Neither two timestamps nor an unfenced empty queue proves convergence. [WP-21.03](../planning/work-packages/21-cloud-host-and-persistence.md#rule-wp-21.03) and [WP-50.04](../planning/work-packages/50-full-platform-production-release.md#rule-wp-50.04) own the real PostgreSQL/mixed-version rehearsal.

The [serial work-package order](../planning/work-packages/README.md) places real exports at [WP-25.08](../planning/work-packages/25-sync-engine-and-blob-lifecycle.md#rule-wp-25.08), commercial/policy prerequisites before provider/retrieval/simulator use, the Harness after its bridge/context/MCP/workflow dependencies, Android acceptance after [WP-52](../planning/work-packages/52-cloud-harness.md#rule-wp-52) and the Web companion after the real Harness. Early fixture endpoints exercise only client behaviour and are deleted by their named producer package. No fixture crosses a real integration gate.

## 10. Design closure versus implementation evidence

The traces specify mechanisms and owners now. They do not close runtime gates by assertion. SQL concurrency, actual provider usage/payment reconciliation, signed RID isolation, Android/device operation, long media/simulator soaks, restore drills and production release remain explicit implementation evidence in the gate register. Current citation/graph/schema contradictions are repaired in this design step rather than deferred to those gates.
