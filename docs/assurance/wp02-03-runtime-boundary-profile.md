## Collected facts and decisions

Research on 2026-09-21 uses Design `929e5f055ef2ff42ea611a12124df22375999d87` and Web `84939ca1fde0f0653d2cb4d8b8f9e5dd1057abb5`. Six managed owners have 43 projects, 31 with effective AOT analysis. Desktop products and the Cloud host already declare Native AOT. Cloud's solution contains only its own service and managed tests; it does not dispatch Web, Mobile or native builds. DesktopPlatform alone owns native production. Product solutions reference only owner-local managed projects and pinned public packages. Android remains Kotlin/Gradle; AI and Web use their own TypeScript/npm commands. No new Cloud property filename, copied shared build root or .NET mobile/Web runtime is needed merely to match an illustrative file table.

Each existing producer already owns candidate identities and dependency pins. WP06 owns the first foundation integration-manifest composition; this step preserves the existing exact artifact consumers and cannot require unproduced business capabilities or invent a consolidated family manifest.

Web's direct esproj build works, but both the installed Visual Studio MSBuild and CLI solution build report success while skipping the sole project. The actual log says the project is not selected for the solution configuration. Microsoft's solution persistence implementation assigns JavaScript projects a no-build default. An untracked research solution with an explicit Build rule ran the real npm production command and verified the candidate through MSBuild and Visual Studio 18.10.1.

The existing esproj disables implicit npm install correctly, but its standard Restore does not invoke the required root `npm ci --ignore-scripts`. The pinned SDK's `NPMRestore` target is reached by both project and solution restore; a diagnostic-only hook confirmed this actual dispatch. Add a narrowly scoped explicit restore target there, without installing during Build or design-time evaluation.

Actual Visual Studio Run with a local Deploy mapping reached the JavaScript launch provider but failed because the repository has no `.vscode/launch.json`. Define an Edge browser launch against the same loopback development server as portable `npm run dev`. Fix that server at port 5173 with strict-port failure, so the IDE cannot silently attach to an unrelated port after a collision. This development profile starts no C# host, authenticates no session and introduces no production proxy or server. The existing server-connection page remains an explicit Hello example and does not establish future Account/Chat development profiles.

## Execution finding: installed browser

Actual IDE startup during execution exposed a missing local prerequisite: Edge is not installed on the verification machine. Chrome is already installed. The implementation uses the supported Chrome launch type with normal installed-browser discovery, and the development guide names that prerequisite. No browser or native dependency was installed. This replaces the Edge choice above without changing the loopback URL, strict-port behavior, runtime boundary or acceptance sequence. Actual Visual Studio Run reached debug mode 3 and the IDE-started page passed browser interaction after this correction; the initial missing-browser error is not counted as successful startup.
