All owners have working foundation candidates and real runtime evidence; no nonexistent producer is an input to this step.

Existing product smoke reports and Cloud health expose source revision, and Web/AI report a release version plus source. Contracts package resources retain schema/descriptor and source identity. DesktopPlatform's native ABI1.0 probes report library/dependency versions. Android already stamps versionName/versionCode and a Contracts package version. These are useful but do not form a nine-axis report, do not prove independence and do not stamp a complete build/run identity into every owner-authored assembly or runtime artifact. DesktopPlatform's managed packing currently passes PackageVersion separately from assembly Version, so those identities must be checked explicitly.

The quality contract defines PackageVersion as a dependency package version, while the build table refers to package manifests. Neither permits copying AppVersion into the dependency inventory or treating a Contracts package release as a wire-contract major. Initial production capability/format/storage/policy/extension implementations are later producers. Inventing support version 1 for their absent implementations would contradict the stage matrix. Build plumbing must represent that absence honestly while producing every named axis and supporting its independent real sources when present.

## Data and compatibility decisions

Every candidate produces a closed, versioned build-identity report with owner, artifact identity, source commit/dirty state, build identity and exactly the following nine axis entries. Unknown/missing axes, duplicate subjects, alias/expression references to another axis, malformed versions, missing source evidence or contradictory applicability fail validation. Coincidentally equal version strings are not an error: independent sources and mutation tests establish independence.

| Axis | Current source and resolution | Absent producer handling |
|---|---|---|
| AppVersion | The owner's already allocated product/service release input; Android's separate platform versionCode stays packaging metadata | Library-only packages have no installed product version; explicitly not applicable |
| ContractVersion / ContractSet | Authored proto/profile identities in Contracts; consumers read the exact restored producer's schema/descriptor provenance, retaining its package identity separately | No fabricated LocalRpc, Events or business schema version from the Hello example |
| CapabilityVersion | Owned descriptor declarations, with subject/version and source digest | Not produced until the owning capability implementation; WP09 and later product owners replace this state |
| NativeFormatVersion | Owned portable-format definition/version declarations, separately keyed by format | Not produced until the product's format owner; WP18/28, WP34 and WP38 remain responsible |
| StorageSchemaVersion | Owned migration-set head for each store, with migration source identity | Not produced before WP07/21 and the relevant product storage owner; no claim about a deployed database from build metadata |
| NativeAbiVersion | Actual owned C ABI constants and matched runtime metadata; never the NuGet release number | No first-party native boundary in an artifact means explicitly not applicable; DesktopPlatform reports actual probe ABI1.0 |
| PolicySchemaVersion | Owned policy bundle schema definition, independently named/versioned | Not produced before the WP03 schema and WP44 runtime producers; build-policy file format is not a signed policy bundle |
| ExtensionProtocolVersion | Owned extension protocol definition, independently named/versioned | Not produced before WP03/41; a package version or private Hello transport does not invent extension support |
| PackageVersion | Exact dependency package coordinates from committed locks and resolved package/SBOM inputs, retaining ecosystem/subject identity | Empty dependency sets remain explicit; the artifact's own distribution version is separate artifact metadata |

The owner keeps a substantive source catalog for all nine resolvers. Each axis records present values with source paths/digests or restored artifact identities; an empty axis has an explicit not-applicable or not-produced reason, and the latter names its future producer. These states are not nine invented versions and do not close those later producers. Production report generation rejects generic version fallbacks and cross-axis aliases. Tests independently populate and mutate each of the nine source kinds, then confirm only that axis changes; those synthetic source fixtures are labelled mechanism tests. Actual candidates contain only their implemented source values.

Build identity is independent of every compatibility axis. It contains the full source commit, an explicit local/CI distinction and dirty state, a build ID, pipeline run/attempt and URL where applicable, and a deterministic source timestamp. CI build ID uses the actual run ID plus attempt; no constant local identity may appear in a publishable CI artifact. The timestamp is the source commit's UTC timestamp (the SOURCE_DATE_EPOCH convention), not a claim about wall-clock compile time. Actual job times remain in the referenced pipeline record. Local non-repository consumer fixtures are explicitly local; producer candidates require a real source identity and publication still rejects dirty source.

Every owner-authored managed assembly receives assembly metadata through its effective build inputs, including libraries and verification tools. Third-party binaries and already-published dependencies are not rewritten: their exact identities remain package inventory entries. Native ABI signatures and buffer/error semantics remain unchanged; existing build-info exports gain the source/build/run/timestamp fields. C#, Kotlin/JAR, Android and TS/static/Worker artifacts carry equivalent support identities using their own runtime mechanisms. No runtime learns local workspace paths, credentials or CI environment dumps. Only the reviewed identity fields are serialized.

Runtime retrieval must read the built artifact's metadata, not reconstruct it from current environment variables or an external receipt. Desktop offers an explicit offline build-info command and retains native UI smoke evidence. Cloud health reads its compiled metadata. Web serves its sealed build-info asset and verifies it in a real browser. AI's private health/Workflow evidence exposes its compiled candidate identity without creating public routes or new model retries. Android provides an explicit build-information view and device verification against the minified published application. Published Contracts consumers inspect actual assembly/JAR/npm metadata; source files alone do not pass that gate.

The report is a foundation artifact, not the complete compatibility manifest or an assertion of supported historical formats. WP04.05 still owns non-interchangeable runtime version value types; WP03 owns business schema compatibility; WP06 owns the first consolidated foundation integration manifest. Existing package names, IDs, signatures, transport behavior, immutable releases and Maven main SNAPSHOT/tag-only formal publication remain unchanged.

## Current primary-source verification

Checked on 2026-09-21 against installed SDK targets and current official documentation:

- [Microsoft assembly attributes](https://learn.microsoft.com/en-us/dotnet/standard/assembly/set-attributes-project-file) and the installed `Microsoft.NET.GenerateAssemblyInfo.targets`: arbitrary assembly metadata can be generated; informational version normally includes source revision, whereas assembly/file numeric versions omit prerelease suffixes. A package version alone does not establish every assembly's support identity.
- [GitHub workflow variables](https://docs.github.com/en/actions/reference/workflows-and-actions/variables): run ID, attempt, source SHA and repository identify a concrete execution; a rerun changes attempt without changing run ID.
- [Android Gradle build configuration](https://developer.android.com/build/gradle-tips): generated BuildConfig fields are runtime-accessible; generating changing timestamps during every incremental build needlessly invalidates outputs.
- [Reproducible source timestamps](https://reproducible-builds.org/docs/source-date-epoch/): source-derived time is a stable declared input. The report labels that semantic explicitly and preserves separate pipeline execution identity.
