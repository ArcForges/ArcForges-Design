**D-018** produces three different obligations. They were previously conflated, which allowed a design-stage gate to appear satisfiable by registering a finding. They are separated here:

| Obligation | Content | Stage | State |
|---|---|---|---|

| **B — Design traceability** | Each invariant has its applicable architecture rule, a planned verification specification, and an owning work-package completion gate | Design | **Complete** — `§4`–`§5` |
| **C — Implementation evidence** | The enforcement code, the test implementation and passing test results | Implementation | **Not started, and not claimed** — `§6` |

**A and B are the design-stage obligations and are discharged by this document. C is implementation work and is not a Stage 2 deliverable.**

## 4. Obligation B — item-level traceability

Every invariant maps to an architecture home, an enforcement mechanism, a planned verification specification and an owning work-package completion gate. The full table is `§7`.

### 4.1 What a planned verification specification is

| # | Rule |
|---|---|
| PV-01 | **A planned verification identifies what will be checked and its expected outcome** — enough to make the invariant verifiable. It need not exist as executable code; that is obligation C. |
| PV-02 | **The check names the invariant**, so a failure identifies the violated rule rather than only a failed assertion. |
| PV-03 | **The mechanism is the cheapest sufficient one**: a type distinction where the wrong thing can be made not to compile; a repository policy test where a naming or reference rule expresses it; a unit test where it is behavioural; an integration test only where nothing smaller can observe it. |
| PV-04 | **A planned verification is not evidence that the invariant holds.** It is evidence that the invariant is verifiable and that someone owns proving it. |

### 4.2 Mechanism distribution

|---|---|---|---|
