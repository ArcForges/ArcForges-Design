# Producer Artifacts and Real Integration

Authoritative under [P2-010](../decisions/phase-2-specification-decisions.md#rule-p2-010). This is an implementation input to every active work package, together with its numbered substeps. A work package completes only its declared stage. A generated schema, a passing fixture, a registry package, an actual transport probe and an integrated product have different evidence. None substitutes for the next stage. The full product requirements remain the release scope.

The ContentSandbox producer is staged, not duplicated: WP11 owns host, protocol and launch mechanics and publishes a real restricted fixture-parser runtime. NAT.31 (out of V1 under P2-026 S1 and S8, so it is not a current producer) would implement the production still-image parser composition in that same DesktopPlatform source (no PDF parser, per [P2-022](../decisions/phase-2-specification-decisions.md#rule-p2-022) item 4), rebuilds/signs once against its completed native packages, and publishes a new immutable Runtime.<rid> version; WP13 supplies the containment mechanics and hostile regression fixtures that NAT.31 re-runs. Products would consume that NAT.31 runtime only if a reviewed decision reopens it (P2-026 S1). No future parser is an input to WP11 and no already-published artifact is modified.

Contracts is Apache-2.0 throughout. Package access/import direction remains enforced even if source/artifacts are publicly readable. Internal schemas include no secret values. DTOs and validation are generated or derived solely from authored schemas. Domain implementations, client UI and orchestration stay with their product. Product repositories cannot import adjacent source, Git submodules, producer build outputs or unpublished project references.

Schema/generator/runtime versions and executable hashes are pinned in the producer toolchain manifest. Generation is network-free after locked tool restore; protoc, C#/Java/Kotlin/Connect/protobuf-es generators and schema validators are versioned inputs; the Java, Kotlin and Connect generators retire with their Maven channels under [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021) item 4. The protobuf-es generator is retained only for the internal `@arcforges/ai-internal` codec, which P2-021 item 4 keeps; the other TypeScript generators retire with their npm channels. Regeneration must match the tracked generated baseline and descriptor set. NuGet, and any still-published npm or Maven variant, from one Contracts release share its version, schema hash and fixture digest; every consumer pins the matching release. Public clients retain unknown read fields/enum values safely, refuse unknown mutation profiles and test the supported current/previous major window. The Hello bootstrap remains a compatible example, not the production contract inventory.

## 3. Candidate lifecycle and upgrade acceptance

Contracts development Maven publication (retiring under [P2-021](../decisions/phase-2-specification-decisions.md#rule-p2-021) after the Kotlin consumer migrates) follows the [SNAPSHOT channel profile](../architecture/contracts-publication-channels.md). Its separate Maven coordinate does not change formal release version matching or existing immutable consumer locks; snapshot receipts bind the cross-language build identity and resolved remote files.

Use [build/release authority](../architecture/14-build-packaging-and-release.md#complete-producer-candidate-and-promotion-protocol): main automatically allocates a version, builds the full dependency closure, packs once, runs the reduced offline/build checks, publishes all registries and uses successful provider status/identity before advancing the complete manifest, the NuGet latest pointer and, while each channel publishes, the npm and Maven latest pointers; the retained npm package (@arcforges/ai-internal) follows the same promotion gate, and the Maven channels do so until [AND.40](delivery/lanes/android.md#task-and-40) retires them. Consumer CI restores exact versions and compiles/packages the product; it does not execute installed consumers. Producer source is absent. Lock updates come in reviewed dependency PRs and retain source/release hashes. Native output manifest includes ABI minor, dependency build flags, supported RID, licence/source notices and all assets needed at load time.

Minimum injected failures: missing runtime DLL; wrong RID/ABI/contract major; unpublished required package; stale generated client; repeated command after lost reply; old hash under same version; npm succeeds while NuGet/Maven fails (Maven while its channel publishes); NuGet succeeds while the retained npm package fails; interrupted registry publish; old tag delivered from cache; revoked signing key; source unavailable during consumer build. Expected outcomes are explicit failed promotion, reconciliation/resume from immutable bytes or return to previous complete manifest. An old package/lock continues to restore; publishing never silently updates running clients.

Each completion receipt includes WP/substep, source commit, producer release, candidate hashes, runtime/OS/device/provider identity, scenario, observed result and limitations. Unit/fixture/schema/document evidence, clean packaged consumer execution, real provider/device integration and commercial activation occupy separate fields. The release coordinator checks all required evidence and known unresolved effects before activation; it does not infer readiness from a green documentation validator.

Execution venue and cadence follow [P2-017](../decisions/phase-2-specification-decisions.md#rule-p2-017): no macOS or hosted runtime matrices and no routine post-publication downloads. Stage scenario requirements do not reinstate those automated jobs. Relevant runtime checks use available local environments once; receipts state untested coverage separately. Linux runtime checks run once, affected-scope, in the local WSL2 Debian distribution invoked through PowerShell on a Linux-native filesystem, with the distro, kernel, SDK and toolchain recorded ([P2-024](../decisions/phase-2-specification-decisions.md#rule-p2-024)); there is no CI change and no hosted Linux runtime.
