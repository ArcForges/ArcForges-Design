# Producer Artifacts and Real Integration

Authoritative under P2-010. This is an implementation input to every active work package, together with its numbered substeps. A work package completes only its declared stage. A generated schema, a passing fixture, a registry package, an actual transport probe and an integrated product have different evidence. None substitutes for the next stage. The full product requirements remain the release scope.

The ContentSandbox producer is staged, not duplicated: WP11 owns host, protocol and launch mechanics and publishes a real restricted fixture-parser runtime. WP13 implements the production parser composition in that same DesktopPlatform source, rebuilds/signs once against its completed native packages, and publishes a new immutable Runtime.<rid> version. Products consume that WP13 runtime. No future parser is an input to WP11 and no already-published artifact is modified.

Contracts is Apache-2.0 throughout. Package access/import direction remains enforced even if source/artifacts are publicly readable. Internal schemas include no secret values. DTOs and validation are generated or derived solely from authored schemas. Domain implementations, client UI and orchestration stay with their product. Product repositories cannot import adjacent source, Git submodules, producer build outputs or unpublished project references.

Schema/generator/runtime versions and executable hashes are pinned in the producer toolchain manifest. Generation is network-free after locked tool restore; protoc, C#/grpc-java/grpc-kotlin/protobuf-es plugins and schema validators are versioned inputs. Regeneration must match the tracked generated baseline and descriptor set. NuGet/npm/Maven variants from one Contracts release share its version, schema hash and fixture digest; every consumer pins the matching release. Public clients retain unknown read fields/enum values safely, refuse unknown mutation profiles and test the supported current/previous major window. The Hello bootstrap remains a compatible example, not the production contract inventory.

## 3. Candidate lifecycle and upgrade acceptance

Use [build/release authority](../architecture/14-build-packaging-and-release.md#complete-producer-candidate-and-promotion-protocol): main automatically allocates a version, builds the full dependency closure, packs once, tests the actual candidate in isolated consumer projects, publishes all registries, verifies availability and only then advances the complete manifest/npm latest. Consumer CI restores exact versions from an isolated cache/registry and publishes/runs the product; producer source is absent. Lock updates come in reviewed dependency PRs and retain source/release hashes. Native output manifest includes ABI minor, dependency build flags, supported RID, licence/source notices and all assets needed at load time.

Minimum injected failures: missing runtime DLL; wrong RID/ABI/contract major; unpublished required package; stale generated client; repeated command after lost reply; old hash under same version; npm succeeds while NuGet/Maven fails; interrupted registry publish; old tag delivered from cache; revoked signing key; source unavailable during consumer build. Expected outcomes are explicit failed promotion, reconciliation/resume from immutable bytes or return to previous complete manifest. An old package/lock continues to restore; publishing never silently updates running clients.

Each completion receipt includes WP/substep, source commit, producer release, candidate hashes, runtime/OS/device/provider identity, scenario, observed result and limitations. Unit/fixture/schema/document evidence, clean packaged consumer execution, real provider/device integration and commercial activation occupy separate fields. The release coordinator checks all required evidence and known unresolved effects before activation; it does not infer readiness from a green documentation validator.
