### GOV.20 — Build.Policy banned-symbol scanner: audit unmanaged function-pointer invocations instead of throwing

**Outcome.** BannedSymbolScanner.Scan in the existing ArcForges.Build.Policy engine no longer throws "Unresolved invocation cannot be audited" for an invocation whose bound operation is a function-pointer invocation (a delegate* unmanaged or delegate* managed call). Such a call has no managed callee symbol, so no symbol-based category (reflection, code generation, blocking, provider, logging) can apply to the call itself; the scan continues, the invocation's receiver and arguments are still visited by the same node walk (a banned call, secret-bearing logging argument or binary floating-point money value nested in the arguments is still reported), and the BAN-POINTER field rule is unchanged. Every other invocation with no resolved method symbol (except the existing nameof and AOT dynamic-invocation branches) still throws exactly as today, so the scanner stays fail-closed for anything it cannot classify. The seven-ID banned-API catalog, rule identifiers, messages and thresholds are unchanged: the function-pointer call is deliberately not a new category ([WP-05.04](../../work-packages/05-architecture-and-repository-policy-tests.md#rule-wp-05.04) names none, and the sealed catalog is a stable seven IDs). The normal DesktopPlatform merge publishes the fixed candidate under the existing ArcForges.Build.Policy package identity. Positive and negative regressions pass: the exact reproducer (an unsafe class whose method calls a delegate* unmanaged[Cdecl]<uint*, uint*, int> obtained from NativeLibrary.GetExport with a null and an address-of argument, as in ArcScope NativePackageProof.cs) scans without throwing and yields zero findings; a managed function-pointer call does the same; a banned call, a blocking wait in an async method, a reflection entry point on an AOT path, a secret logged and a double price nested in the pointer call's arguments are still reported at their own nodes; a banned call elsewhere in the same file is still reported; an unresolved non-function-pointer invocation still throws.
