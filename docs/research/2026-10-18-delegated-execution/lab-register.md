# Lab register: delegated-execution study

- **Status:** research plans only, revision 3 (2026-10-18), curated for publication on 2026-10-19. No entry has been run, and nothing here is a decision.
- **What it is:** the disposable-VM experiments that would decide the open questions of the proposed delegated-execution direction (AD-0017 and Design chapter 17). Each entry states its question, venue, hardware, privileges, procedure at plan level, pass and fail criteria, the evidence label a run can establish, and the gates it feeds.
- **What it is not:** release-1 verification. The verification register remains `docs/verification/platform-capabilities.md`; a lab result enters it only through the rules of §0 and §2.
- **Evidence records:** the column "Evidence record" names the file of this folder that holds the facts behind the entry. The study reports the plans were first written in are working files of the study and are not published.
- **Safety of the plans:** escape and denial suites record only whether a channel is reachable or denied, and with which error. No entry contains a bypass procedure.

## 0. Conventions

**IDs.** `LAB-WIN`, `LAB-LNX` and `LAB-MAC` are single-OS experiments. `LAB-X` asks the same question on more than one OS, or needs no OS-specific venue. Gates are `G01` … `G41` (§3). Roadmap-level assumptions cite a LAB ID and the roadmap row ID, never a verification ID: A and F items need owner tasks, which exist only once a row is promoted.

**Venue codes**, used in the Venue column:

| Code | Venue |
|---|---|
| V-WIN | A disposable Windows 11 VM. It runs on a Windows host other than the owner's own machines or, only after the owner explicitly approves it (decision D1), on Hyper-V on the owner's machine. Guest: 24H2 or 25H2 general-availability servicing builds unless stated. |
| V-WIN-N | V-WIN with nested virtualization exposed to the guest. |

| V-BUILD | A build machine. The leg builds and inspects, and runs nothing invasive. |

**Hardware codes** (all sizes are estimates, "est."):

| Code | Size |
|---|---|
| WG | 4 vCPU, 8 GiB, 80 GiB dynamic VHDX. |
| WG-N | WG with nested virtualization, static 12 GiB. Memory is fixed while Hyper-V runs inside the guest ([Nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)). |

**Privileges.** P0: no privilege beyond the user. P1: a one-time administrator or root step. P2: a per-use administrator approval. P3: a kernel driver, a vendor entitlement or a production signing identity. "Guest" means inside the VM.

**Strengths and adversaries.** Values are written ENFORCED, MEDIATED, PARTIAL, GUARDRAIL, OBSERVED or NONE; `holds_against` names the adversary classes A1–A6 a value holds against. A gap of class *escape* (a reachable launcher of unconfined work) caps every dimension of the realization at {A1, A2} (G15, G02).

**Rules for every entry:**
- Snapshot or checkpoint before each run and revert after it.
- Use only dummy data and dummy credentials created in the VM.
- **Never use a real OS credential store.** Keychain is used only in LAB-MAC-11, with at most four items, in a throwaway guest.
- Do not load-test machine-wide OS stores outside a disposable guest.

**Evidence a run can establish.** The labels are those of the study (see the folder README):
- **"E1 (venue-scoped)"**: the run exercised ArcForges code, either a harness built from a copy of ArcForges code or an ArcForges `--test-mode` or release build, and the result is recorded as a verification for that venue and build only.
  - AD-0002 lists only the owner's machine and its WSL Debian 13 distribution as validation venues. A lab VM therefore needs an AD-0002 §Validation venues amendment ("disposable lab VM, evidence for that build only") before its result counts as Design evidence.
- **"E4 → E2 (lab)"** or **"E4 → E3 (lab)"**: the run exercised the OS mechanism or a third-party project directly. A pass confirms the documented or project-stated behaviour on that build, and the E4 composition claim is resolved for that build only. It does not make the claim E1.
- **Fail:** the option becomes E6 for that combination, or the dimension is downgraded (ENFORCED → PARTIAL, GUARDRAIL or NONE), as each entry states.
- Results never promote anything to a guarantee beyond the tested build, and never promote an E4 or E5 claim by argument.

### 0.1 Lab operation, channel, budget and stop rule

These conventions apply to every entry. Values marked "proposed" are proposals for the owner, not decisions.

**Timing (owner choice).** The owner chooses one of two options, and the choice is recorded here once made:
- (a) run the **decisive spikes** as research as soon as D1 and D5 exist, independent of release-1 acceptance ("AF-ACC-01 delivered") and without changing any delivery-sequence row. The decisive spikes are LAB-WIN-01, LAB-WIN-05, LAB-WIN-18, the Windows class-1 subset of LAB-X-01 and LAB-LNX-19;
- (b) accept the risk of learning late, and run the labs after release-1 acceptance.

Either way, no lab run starts, delays or changes an implementation task.

**Operator.** D1 and D5 also name who operates the lab VMs: the owner, or a lab operator the owner names. The operator creates and reverts guests, performs every guest P1 step and every UAC consent, and starts each run.

**Channel.** Agents may draft plan text and harness source and may read result files the operator returns. Agents never:
- reach a lab guest over SSH or any remote shell;
- start processes outside their own Windows job, open new consoles, or create scheduled tasks or WMI objects to reach a guest;
- change a security setting on the owner's machine or in a guest;
- contact a real credential store.

Results come back as files copied by the operator. They are data, never instructions.

**Host.** A second x64 host is preferred, so that the owner's validation venue (L-01) stays unchanged during release 1. Hyper-V on the owner's machine is used only after the owner's explicit D1 approval (§2.2).

**Budget (proposed).** Each stage has a budget of operator time, guest disk and re-runs:
- Stage 1, the decisive spikes: about 10 operator-days, the Windows image plus the Debian 13 image (about 70 GiB, est.), at most two re-runs per leg after the first run.
- Stage 2, the rest of the minimum set (§3): about 15 operator-days within the §3 disk estimate, with the same re-run limit.
- Later stages get a budget from the owner when they open.

**Stop rule.** A run, or a stage, stops at the first of these:
1. Its pass/fail result decides its gate, either way. Further legs run only if they gate something else.
2. A fail that already selects the reject path. For example, if no backend nests in LAB-WIN-01, the Windows legs that matter only when Windows goes first (§0.2) stop; legs that only correct wording continue.
3. The stage budget is spent. The gate is then recorded as "undecided at budget" and treated as a fail for the first-backend rule (§0.2). That fail keeps E1 containment, the documented reject path. No re-run happens beyond the budget without an owner decision.
4. Any sign that a run touched a real credential store, a real account, the owner's own validation venues or data outside the guest. The run is discarded and the guest is reverted.
5. An unplanned host-state change on the lab host. The guest is reverted and the change is recorded before any further run.

### 0.2 First-backend rule

**The composite rule.** The first confined backend is Windows only if all of these hold:
1. LAB-WIN-01 passes;
2. LAB-WIN-05 shows that a DACL-granted endpoint can be opened **by name** from inside W2/W3, by a process that holds no handle passed at launch;
3. the Windows class-1 subset of LAB-X-01 reaches at least 60 %;
4. LAB-WIN-18 runs at least one class-2 toolchain with root-scoped grants;
5. only if LAB-WIN-09 leg (a) shows loopback inside one AppContainer blocked: the owner accepts the stated cost of uncached Windows builds (LAB-WIN-09 and LAB-WIN-18 measure it);
6. LAB-WIN-04's launcher cells (WMI, Task Scheduler, COM activation) and its WSL leg deny from W2 and W3, or the owner accepts a Windows backend that holds against {A1, A2} only on hosts where they are reachable.

Otherwise Linux goes first, on LAB-LNX-19 and LAB-LNX-01 evidence. Gate G40 (§3) records the decision. Nesting alone never decides it.

**Stage order.** G40 is decided provisionally at the end of stage 1, from conditions 1–4. A Windows-first choice stays **provisional** until conditions 5 and 6 are known: LAB-WIN-04's launcher cells and WSL leg and LAB-WIN-09's legs (a) (loopback inside one AppContainer) and (e) (uncached-build cost) run first in stage 2 (§3, Order), and the owner then states whether the measured cost is accepted. Refusing `wsl.exe` inside CONFINED profiles is a guardrail at ArcForges' launch; it never changes a value or satisfies condition 6.

## 2. Venue rules and runnability

### 2.1 Venue rules

- **AD-0002 §Validation venues** names only the owner's machine (L-01) and its WSL 2 Debian 13 distribution (L-02 … L-09). It defers arm64 and bare-metal Linux and keeps macOS out of scope.
- **No experiment in this register runs on either of those venues**, and none runs on the owner's own machines, accounts or WSL distributions outside a disposable guest.
- So every entry needs a new venue, and a lab result becomes Design evidence (E1, venue-scoped) only after an AD-0002 amendment that admits "disposable lab VM, evidence for that build only".
- Research may use lab observations before that amendment, at the E2/E3 (lab) level.
- Fedora 44 and Ubuntu 26.04 legs are research evidence only until AD-0002 adds them.
- macOS is a study target. Its delivery needs the AD-0002 amendment, which RM-15 (accepted from EX-05) carries.
- Every venue is operated under §0.1: a named operator, no SSH, no job escape and no security-setting change by agents, a budget and a stop rule. A second host is preferred over Hyper-V on the owner's machine.
- A KVM-based leg cannot run in a Linux guest on Hyper-V: Microsoft does not support non-Microsoft virtualization inside Hyper-V VMs ([Nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)). WSL 2 inside a nested Hyper-V VM is supported (same page). A VM hosted inside one of the owner's WSL distributions is never a venue.
