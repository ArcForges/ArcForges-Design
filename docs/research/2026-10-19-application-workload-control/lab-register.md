# Lab register of the 2026-10-19 vision-correction study (LAB2)

- **What this is:** the disposable-VM experiments that would decide the open questions of the 2026-10-19 vision-correction study (application and workload control), one de-duplicated entry per question, mapped to the decision gates of the [2026-10-18 lab register](../2026-10-18-delegated-execution/lab-register.md) (G01 … G41) or to the new gates G42 … G51 and the interactive leg G20-I.
- **What it is not:** research plans only. Nothing here has been run, and nothing here is a decision. Every value is attainable under stated conditions, never a realized guarantee; no E4 or E5 claim is promoted by argument. A `LAB2-…` ID is never the earlier register's `LAB-…` ID of the same number.
- **Citations:** facts are cited by their IDs in this folder's evidence files (`D2-<file>-<n>`) or in the 2026-10-18 record (`D-<file>-<n>`); earlier labs by their `LAB-…` IDs. Design chapters are cited by number.
- **Safety, for every entry:** disposable guests on a lab host, or neutral lab hardware wiped after the run; a snapshot before and a revert after each run; dummy data and dummy accounts created in the guest; never a real OS credential store and never a load test of a machine-wide OS store; escape and denial suites record only *reachable* or *denied* with the error and hold no bypass procedure; an agent never leaves its own process job to reach a guest.
- **Publication:** curated for the public ArcForges-Design repository from the study's consolidated and independently checked register. No entry describes a particular host of the owner's.

## 1. Conventions

### 1.1 Numbering

One numbering per area: `LAB2-WIN-nn` (single-OS Windows), `LAB2-LNX-nn` (single-OS Linux), `LAB2-MAC-nn` (single-OS macOS), `LAB2-X-nn` (more than one OS, or OS-neutral).
- **Area rule.** `X` is used wherever an experiment needs venues on more than one OS, or no OS-specific venue (a harness, a mock-up, an accounting simulator). An `X` umbrella entry whose measurements are realized per OS names its per-OS legs, so a measurement appears once.
- **Extends versus new.** Where an entry builds on an earlier lab that already measures the cell, it says "extends `LAB-…`" rather than repeating it. An earlier lab extends only where it measures the same cell.
- **Retired IDs.** An ID whose question duplicated another entry's is retired: its row stays as a pointer, and the ID is never reused (LAB2-LNX-09).

### 1.2 Venue codes and the host rule

**Host rule for every code below.** No LAB2 entry runs on the owner's workstation, on its WSL distributions, or on any other machine, account or data of the owner. Every venue is a disposable guest on a lab host, or neutral lab hardware wiped after the run. The earlier register's V-WIN also allowed Hyper-V on an owner machine after its decision D1; no LAB2 entry assumes that option, and using it would be the owner's own explicit decision, outside this register.

| Code | Venue |
|---|---|
| V-WIN | A disposable Windows 11 VM on a lab host; 24H2/25H2 general-availability servicing builds unless stated |
| V-WIN-N | V-WIN with nested virtualization exposed to the guest |
| V-INS | V-WIN on a 26H2 or Insider image; such an image outside the Insider program is not established |
| V-LNX(d) | A disposable Linux VM per distribution *d*, on the same lab hosts as V-WIN or a separate KVM host; never a WSL distribution of the owner's, and never a VM hosted inside one |
| V-BM | A bare-metal disposable PC with the stated GPU or CPU: neutral lab hardware, wiped after the run, never the owner's own machine; **a requirement, never a purchase**, and its use is an owner lab decision |
| V-BUILD | A lab build host or a disposable VM that builds and inspects and runs nothing invasive; building needs the owner's go-ahead (the earlier register's "Build-only") |
| *(macOS)* | **Venue-neutral.** Chosen when macOS development starts: disposable, never the owner's Mac, no Apple ID, no real data, never a real Keychain. No host type or processor architecture is written into the venue; any vendor constraint on running macOS guests is recorded with the venue decision. Signing legs run ad hoc where they can; the source of any signing identity is decided at the same time |

Hardware codes `WG` (4 vCPU, 8 GiB), `WG-N` (nested, 12 GiB static), `LG` (2–4 vCPU, 4 GiB), `LG-D` (desktop, virtual display) and `MG` (macOS guest) are the earlier register's. Privileges: **P0** standard user; **P1** one-time administrator or root step; **P2** per-use elevation; **P3** driver, entitlement or signing identity; "guest" means inside the VM.

### 1.3 Evidence a run can establish

"E4 → E2 (lab)" or "E4 → E3 (lab)" means a run exercised the OS mechanism or a third-party project directly, resolving the composition claim **for the tested build only**. "E1 (venue-scoped)" is a run of ArcForges code (`E1-DP`: DesktopPlatform code); it counts as Design evidence only after the AD-0002 validation-venues amendment the earlier register describes ("disposable lab VM, evidence for that build only"). A fail downgrades the dimension (ENFORCED → PARTIAL, GUARDRAIL or NONE) or marks the option E6 for that combination, as each entry states.

### 1.4 Labels used in the entries

- Windows tiers W0 … W3 and the Linux tiers T-WL, T-WP, T-X and T-LL: [win-confine.md](evidence/win-confine.md) and [lnx-confine.md](evidence/lnx-confine.md). **Drive cells** are channels through which confined code could make unconfined code act for it (input injection, window messages, hooks, accessibility invoke, launchers); a reachable drive cell is an escape-class gap that caps `holds_against` at {A1, A2} (chapter 17 §3.2).
- The client rules W-1 … W-4: [gf10-clients.md](evidence/gf10-clients.md). The interactive cost measures ICM-1 … ICM-8 and the owner's ceilings `Y-start`, `Y-input`, `Y-frame`, `Y-hang`: [gf11-cost.md](evidence/gf11-cost.md). The denial shapes S1 … S3: [gf05-access-denial.md](evidence/gf05-access-denial.md). The hygiene measures TM-01 … TM-08: [gf07-tamper-human.md](evidence/gf07-tamper-human.md). The diagnosis rules `DX-…` and the five verdicts: [gf02-vocabulary.md](evidence/gf02-vocabulary.md).
- The hold term `K`, per resource (Design 03 §10 as amended): `K_mem = presence_mem + Σ_r max(granted_mem_r, peak_observed_mem_r)`, the peak held while the grant lives; `K_cpu = presence_cpu + Σ_r max(granted_cpu_r, ũ_cpu_r)`, with the requester's smoothed CPU, never a peak. It is distinct from chapter 03 §6's host share `H_cpu`.

### 1.5 Per-OS gate rule

A gate that lists legs for several operating systems is decided **per operating system**. A macOS leg decides only the macOS column, and an unrun macOS leg never holds a Windows or Linux decision. This applies to every gate below, new and earlier, that spans operating systems (notably G13, G21, G30, G31, G32, G42, G44, G45, G47, G48, G49, G50 and G51).
