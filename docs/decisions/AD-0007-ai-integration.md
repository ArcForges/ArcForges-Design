# AD-0007 — AI client integration: MCP first, hooks for identity and routing, honest coverage

- Status: Accepted (2026-10-12; revised after the independent review the same day: no worktree hooks, exec-form hooks, `ask` for rewrites, caller-bound rewritten runs, guardrail wording; revised 2026-10-13 after the findings review: managed-command mode, hand-off before client timeouts, coverage map; amended 2026-10-19 by the current-design corrections, which change no route: routed commands run outside the client's own sandbox (§1, §4), and the optional Linux hardening is read back and reported (§8))
- Evidence: V-A01–V-A06, A-A01, A-A03, A-L04 ([platform verification](../verification/platform-capabilities.md))

## Decision

1. **Primary route: MCP.**
   - `arcforges mcp serve` (stdio) is configured in each AI client and translates MCP tool calls into node gRPC calls ([experience/mcp.md](../experience/mcp.md)). AI clients run MCP servers outside their command sandboxes (V-A03, and Codex's MCP launch), so this route reaches the node even when shell commands cannot.
   - *Amended 2026-10-19.* The same fact has a consequence the decision did not state: a command the node runs for the `run` tool, or for a hook rewrite (§3), runs outside the client's own sandbox. It gains resource control and records, not confinement (§4; V-A06, A-A03).
   - It supports MCP revisions **2025-11-25** (initialize handshake) and **2026-07-28** (stateless, `server/discover`), chosen per request by the client's declared version. Task handles are explicit, server-minted tool arguments.
   - Long work returns within a bounded wait (default 45 s, maximum 55 s) with state, an output tail and the handle. Where a client declares the `io.modelcontextprotocol/tasks` extension, the adapter returns task handles as the extension defines.
2. **Identity through hooks.** The `arcforges hook <client> <event>` handler is configured for:
   - Claude Code: SessionStart, SessionEnd, SubagentStart, SubagentStop, Stop, and PreToolUse and PostToolUse (Bash);
   - Codex: SessionStart, SessionEnd, SubagentStart, SubagentStop, PreToolUse and PostToolUse.

   **Never WorktreeCreate or WorktreeRemove.** A configured Claude Code WorktreeCreate hook *replaces* git worktree creation and must print the path; a WorktreeRemove hook that exits 0 counts as removed. Observing them would break `--worktree` sessions and subagent isolation (V-A02). Worktrees are observed instead through the session's `cwd` and `git worktree list` in registered workspaces.

   **Exec form.** Hooks are configured in exec form (`command` = the absolute `arcforges` path, `args` = `["hook", "<client>", "<event>"]`; no shell) wherever the client supports it. The handler finds the agent process by walking up from its parent to the nearest ancestor that is a known client executable (A-A02).

   It registers the session (`session_id`), subagents (`agent_id`, `agent_type`), the working directory, the transcript path where given, and the **agent process identity** (the PID and start time of the nearest client-executable ancestor). On Claude Code it writes `ARCFORGES_SESSION=<id>` to `CLAUDE_ENV_FILE`, so later commands carry the session.
3. **Command routing (opt-in per workspace or client):**

| Mode | Mechanism | Enabled when |
|---|---|---|
| `mcp` | Agent uses `run` and related MCP tools | Always available |
| `rewrite` | PreToolUse returns `updatedInput` replacing a matching heavy command with `arcforges run --session … --agent … --attach --cancel-when-gone --client-timeout <ms> --join-existing -- <original>`, with `permissionDecision: "ask"`, so the user confirms the rewritten command. `"allow"` (which skips the user's permission prompt) is used only under `bypassPermissions` or when a HUMAN sets `routing.rewrite_permission=ALLOW`, with a stated warning. The run **hands off** before the client's tool timeout instead of being cancelled, and a resubmission joins the existing task ([AD-0006](AD-0006-execution-semantics.md) §7). A command known to run longer than the timeout is guided to MCP `run` with `async`. | Only if the per-client **reachability probe** passes inside that client's command environment (A-A01), and policy allows |
| `rewrite-all` | As `rewrite`, for every shell command except the passthrough patterns (simple reads, read-only git, `arcforges` itself, interactive programs). Leading `cd` and `export` segments stay with the client's shell, background launches are not routed, and unclassified commands get a light estimate. Under the default `ask`, every routed command is confirmed by the user. Codex, which has no `ask` (V-A04), rewrites only with `routing.rewrite_permission=ALLOW` and otherwise uses `guide`. | As `rewrite`; chosen per workspace or client |
| `guide` | PreToolUse denies matching heavy commands with a reason directing the agent to the MCP `run` tool | When rewrite is unavailable and policy prefers guidance |
| `observe` | No routing; heavy unmanaged descendants are recorded and reported | Default for unmatched commands, or when hooks are disabled |

   Matching rules (heavy-command patterns per toolchain adapter, and passthrough patterns for `rewrite-all`) are policy data, editable by the user and per workspace.

   **Connecting MCP alone intercepts nothing**: it offers tools. What each route covers, and what stays observed only, is listed in [08](../architecture/08-ai-integration.md) §4.4.
4. **Honesty.**
   - Codex hooks fail open, and Claude Code hooks can be disabled by managed settings. The node therefore reports routing as **guardrails**, never as enforcement.
   - Per session it reports which routes were active, the managed and bypassed counts, and unknowns.
   - It never claims the model, thinking state or internal completion status. It shows only client-reported events (session start and end, subagent start and stop, stop events) and its own observations.
   - **Routing out of a client sandbox** (amended 2026-10-19; [11](../architecture/11-security-privacy.md) §1, T-24). Commands routed through ArcForges (MCP `run`, hook rewrites) gain resource control and records, but run outside the client's own sandbox, and the client's own process keeps the user's full access. The node states this per supported client, static per client, in the Stated limit text of that client's routing row of the release coverage statement ([product definition](../product/product-definition.md) §9: `routing:claude-code`, `routing:codex`). That text is the only wording: every integration plan that enables an MCP or hook route shows it verbatim (the consent diff, §6), and D-14's integration consent panel, `arcforges coverage` and the MCP `session_coverage` tool show it, each from the client's routing row of `GetReleaseScope`; D-07 and `arcforges session coverage` link to the release coverage statement. The MCP `run` tool's description states it in general terms ([experience/mcp.md](../experience/mcp.md) M-01). Detecting a client's sandbox per run is not part of this decision (V-A03, V-A06; A-A03).
5. **Bypass detection.** The node watches descendants of registered agent processes. Heavy unmanaged processes (CPU or memory above the policy threshold, or matching heavy-command patterns) are recorded as `BYPASSED`, with resource usage, as a diagnosis finding. Processes with no attributable ancestry are reported as unattributed.
6. **Configuration consent.**
   - `arcforges integrate <client>` shows the exact file diff before writing. It writes only user-level, project-level or local-level settings that the user selects, never managed or enterprise settings.
   - It preserves unrelated settings and records what it wrote, so it can remove it.
   - A plan that enables an MCP or hook route shows the client's routing statement of §4, verbatim, with the diff, and applying it records the consent (amended 2026-10-19).
   - It reports conflicts: hooks disabled (`disableAllHooks`, `allowManagedHooksOnly`, `allow_managed_hooks_only`), hooks untrusted (Codex `/hooks`), a sandbox denying IPC, or project instructions that prescribe other build entry points.
   - It never edits a repository's instruction files (AGENTS.md, CLAUDE.md). It offers a snippet the user may add.
7. **Packaging.** Claude Code and Codex plugin packages bundle the MCP configuration, hooks and skills. Installing a plugin never installs or authorizes the native node. The plugin's SessionStart hook detects a missing node and prints install guidance (R-DIST-004).
8. **Guardrails against self-modification, not a security boundary.** Managed tasks run as the same user as the node, so nothing that user can do is technically impossible for them. The node raises the cost of accidental damage:
   - **Read-only versions.** Version directories are installed read-only, and the node verifies their digests at startup (with a finding on mismatch). *Amended 2026-10-23 (AF-SEC-01), which had no digest source:* the digests are the version directory's own `digests.json`, written by the packaging step ([13](../architecture/13-distribution-updates.md) §2). After it is ready, the node makes every file of the version directory it runs from read-only if it is not (Windows `FILE_ATTRIBUTE_READONLY`; Linux without write bits) and checks each file against `digests.json`, off the startup path. A missing, changed or unlisted file raises the tamper finding `ENFORCEMENT_DEGRADED` with the paths, and the capability fact `version_integrity` reads `verified`, `mismatch: <n> files`, or `not checked: no digest manifest` (a development build), which is never reported as verified. The manifest lives beside the files it describes, so this detects accidental changes, not a same-user process that rewrites both.
   - **Approvals.** Policy and configuration changes requested through MCP go through `PolicyService` with approval where policy demands it.
   - **Tamper detection.** A file watcher reports out-of-band edits of `node.json` and the store directory by other processes (finding `ENFORCEMENT_DEGRADED`).
   - **Optional Linux hardening.** Managed transient units get `ReadOnlyPaths=` for the installation and `InaccessiblePaths=` for the node store and secrets, where the user manager supports it (A-L04). *Amended 2026-10-19:* where the user manager cannot apply them, the unit may start without them, so the node reads the hardening back after the unit starts and reports it as applied or not applied; a hardening that did not apply is never reported as applied. It is GUARDRAIL hardening of ArcForges' own files, never reported as workload isolation. *Amended 2026-10-23 (AF-SEC-01):* in a user unit the user manager can set up these mount namespaces only inside a user namespace, so the hardening implies `PrivateUsers`; inside a hardened managed task, setuid programs and `sudo` do not gain privileges.

   Documented bypasses include direct same-user writes and spawning a pseudo-terminal to look interactive (R-AI-009, [11](../architecture/11-security-privacy.md) §1).
