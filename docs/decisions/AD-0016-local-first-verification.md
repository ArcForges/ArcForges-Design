# AD-0016 — Local-first verification, owner-only lightweight CI and testing techniques

- Status: Accepted (2026-10-16; the user's instruction of that day, with the coordinator's implementation decisions made under the user's grant to "make implementation decisions independently"; amended 2026-10-17 by the user's decision on secret-store tests: the OS secret-store test tier, §5; amended 2026-10-19 by AD-0017: direction only for §5: the macOS Keychain named in the OS-store rule at RM-15, and a test-residue discipline for confinement objects at the first confined-backend promotion; amended 2026-10-21 by AD-0018: the verification topology of §3 (native legs, pass records, import; no local WSL), and the pre-push and deep tiers lose their WSL terms; the merge gate of §1, the job classes of §2 and the venue of the OS secret-store tier of §5 are unchanged; amended 2026-10-21 by [AD-0019](AD-0019-mcp-first-verification.md): the legs of §3 run through the Windows and Linux MCP servers, with no local WSL and a stop rule, and the Linux venue of the OS secret-store tier of §5 is the isolated Linux secret-store test host; amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md): the verification of §3 runs after the push, on each host, and is reported to GitHub as the commit statuses `arcforges/windows` and `arcforges/linux`, which the `main` rulesets require (§1, §2, §3, the pre-push tier of §5 and the consequences); the pre-push hook, pass records and `import` are retired)
- Amends: [AD-0014](AD-0014-delivery-method.md) §4 (the "Hosted CI" row) and §5 ("hosted CI is the merge gate"), which now apply to external PRs only
- Related: [16 testing strategy](../architecture/16-testing-strategy.md), [15 performance targets](../architecture/15-performance-targets.md), [13 distribution](../architecture/13-distribution-updates.md) §2 (release builds stay hosted), [conflicts](../reuse/conflicts.md) C-07

## Context

Under [AD-0014](AD-0014-delivery-method.md) hosted CI was the merge gate for every PR, so each of the owner's PRs ran its full build and test matrix on GitHub runners after the author had already run the affected suites on the workstation, and main pushes ran it again. On 2026-10-16 the user asked for a coordinated change of the development workflow. The central principle and the intended behaviour, quoted from the user (2026-10-16):

> **The central principle is simple: anything that can be reliably built, tested, or validated on my local Windows/WSL environment should run locally, not on GitHub Actions for my own PRs.**

> | PR author | Local verification | GitHub Actions |
> |---|---|---|
> | deku2026 | Mandatory comprehensive validation through Git hooks | Only genuinely necessary GitHub-specific operations |
> | Everyone else | No mandatory local hook requirement | Existing comprehensive CI |

The user also asked for a more effective local testing strategy ("reliable, meaningful defect detection", not maximum test counts or coverage), evaluated property-based, fault-injection, fuzz, mutation, stress and model-based testing, and asked that flaky tests be fixed at their cause. The decisions below are the coordinator's; the user's statements are attributed where quoted.

## Decision

1. **Merge gate.**
   - **Owner PRs** (author `deku2026`): the repository-managed pre-push verification at the pushed head, recorded in the PR by the hook's PASS line, plus the independent review at the same head ([AD-0014](AD-0014-delivery-method.md) §4). GitHub shows the validation jobs as skipped. *Amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md) §6–§7: the gate is the required commit statuses `arcforges/windows` and `arcforges/linux` that each host reports for the PR's head commit after the push, plus the independent review at that head; the hook and its PASS line are retired.*
   - **External PRs** (anyone else, Dependabot included): full hosted CI as before, plus review. External contributors need no local hook.
2. **CI job classes.** The PR author is read only from the event, `github.event.pull_request.user.login == 'deku2026'`; there are no repository variables, secrets or API lookups.

   | Class | Owner PR | External PR | Push to main | Schedule | `workflow_dispatch`, `merge_group` |
   |---|---|---|---|---|---|
   | Validation: build, test, AOT, packaging checks, format, analyzers, policy and tool tests, workflow lint, cross-platform and ARM64 matrices | skipped | runs, unchanged coverage | skipped | skipped | runs |
   | Security analysis: CodeQL, secret scan, dependency review, dependency audit | skipped | runs | skipped | runs where a schedule exists | runs |
   | Delivery: jobs that build the published or deployed bytes, and the publish and deploy jobs | — | — | runs | — | unchanged |

   - Validation and security jobs carry one job-level condition, identical across repositories apart from the events a workflow has: `github.event_name != 'push' && github.event_name != 'schedule' && !(github.event_name == 'pull_request' && github.event.pull_request.user.login == 'deku2026')` (security jobs with a schedule drop the `schedule` term).
   - **Push to main runs no validation.** Every main commit arrives through a PR verified either by the owner's hook (*amended 2026-10-22 by AD-0020: by the required host statuses*) or by full PR CI. Main-push runs keep only delivery work; a workflow without delivery work has no push trigger.
   - **Delivery pipelines are unchanged.** Where publication embeds its gates in the evidence of the published bytes, the main-push pipeline stays as it is; only jobs that do not feed delivery are skipped on push. Release builds stay hosted ([13](../architecture/13-distribution-updates.md) §2).
   - **Required checks** are reduced to `Verify` where a repository required more. A skipped job reports success to a required check, but a skipped matrix job does not report its expanded name and the code-scanning `CodeQL` check never appears without an analysis, so `Verify` requires every validation and security job for external PRs. Check names that stay required keep their names. *Amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md) §6: each repository's `main` ruleset also requires the host statuses its step table applies to (`arcforges/windows`, `arcforges/linux`), for every PR author, with no bypass actors.*
   - `workflow_dispatch` keeps a manual full run wherever it exists. `merge_group` runs the full validation for every author, owner included; it applies only where a merge queue is configured, and none is today.
3. **Pre-push verification** (decision level; the core is one script, `eng/verify.py`, identical in every active repository, with the repository's steps in `eng/verify_steps.py`).
   > **Amendment (2026-10-22, [AD-0020](AD-0020-post-push-verification-and-required-checks.md)).** This verification now runs after the push. Each host fetches the exact pushed commit from GitHub, runs its leg with `python eng/verify.py run-and-report` and reports the commit status `arcforges/windows` or `arcforges/linux`, which GitHub requires before a merge into `main`. In the items below:
   > - **Installation** now installs only lightweight hooks (such as `pre-commit`) and removes the retired pre-push hook.
   > - **Source state:** a commit reaches each host from GitHub, never as a Git bundle.
   > - **Fail closed:** a failed, timed-out or impossible step reports `failure` or `error` instead of rejecting a push; a missing status blocks the merge.
   > - **Pass records and reuse:** withdrawn, with `import`; the commit statuses are the evidence, and each leg keeps its logs and a `summary.json` on its host.
   > - **Profiles, coverage, the items not reproduced locally and the rules for agents** are unchanged. AD-0020 §9 adds that agents never post a status by hand or change a ruleset to get a PR merged.
   >
   > The text below is kept as history.
   - **Installation:** `python eng/verify.py install`, once per clone, copies the tracked `.githooks/*` into the clone's common hooks directory, which every worktree uses, and removes any `core.hooksPath` (a relative hooks path resolves per worktree and would silently run nothing where a commit lacks `.githooks`). The hook rejects a push from a worktree without `eng/verify.py`, and the core clears Git's hook environment (`GIT_DIR` and related variables) before it acts on the verification checkouts.
   - **Source state** (amended 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §5): every pushed commit is verified, never the working tree. Each leg checks out the commit itself: a detached worktree on the native Windows workstation, a Linux-native clone on a native Linux machine. A commit that is not yet on GitHub reaches the other machine as a Git bundle, which Git verifies object by object. Local WSL Debian is not a dependency. *Former text, kept as history:* every pushed commit is verified, never the working tree: in a dedicated detached worktree on Windows and a Linux-native clone in WSL Debian, both checked out at the pushed commit and cleaned of untracked files (ignored build output stays, so builds are incremental). The step table and the core are read from the pushed commit.
   - **Legs and lanes** (amended 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §5; where each leg runs amended the same day by [AD-0019](AD-0019-mcp-first-verification.md) §2 and §5: the Windows leg through the Windows MCP server, the Linux leg through the Linux MCP server, and verification stops when one is unavailable): each step runs on one host, `win` (native Windows) or `linux` (native Linux); a host's steps are the commit's leg for it. `eng/verify.py` runs only the leg of the machine's own operating system, never through WSL, a VM bridge or a remote shell. *Former text, kept as history:* **Lanes:** steps are grouped into lanes (Windows, WSL and small independent lanes) that run concurrently, each lane in order. Timing- or resource-sensitive steps are `exclusive` and run alone after all lanes.
   - **Fail closed** (amended 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §5): a step that fails, times out (its process tree is killed) or cannot run (a missing tool) rejects the push, naming the step, the last lines of its log and the log path, and so does a missing passed or imported record for any leg of any pushed commit, or a shallow clone. A Linux leg whose steps need a systemd user manager or cgroups v2 delegation checks for them first and fails when they are missing. *Former text, kept as history:* a step that fails, times out (its process tree is killed) or cannot run (a missing tool, WSL Debian unavailable) rejects the push, naming the step, the last lines of its log and the log path.
   - **Pass records and reuse** (amended 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §5): a passed leg writes a record keyed by the commit's tree (its exact commits when a step reads history), the merge base, the profile, the leg's host and step set, the scripts and the step table's context. The record of a leg that passed on another machine is accepted with `python eng/verify.py import`, which recomputes the key and refuses any mismatch or any step that did not pass. The PR quotes each leg's `LEG PASS` line and the combined `arcforges-verify: PASS` line at the pushed head. *Former text, kept as history:* **Reuse:** a pass is recorded under the Git common directory, keyed by the commit's tree (plus the exact base and head commits when a selected step reads history, such as a secret scan of the pushed range), the selected step ids, the hashes of both scripts and the tool versions on each host. An identical key is not verified again.
   - **Profiles:** each repository selects steps from the paths changed since the merge base with `main`. A change that touches only Markdown documentation outside code, tests, scripts and workflows runs a light profile (whitespace, secret scan); anything else runs the full profile. In this repository Markdown is the source, so every change runs the full profile.
   - **Coverage:** the CI-equivalent profile of each repository (build, analyzers, format, tests, closed loop on Native AOT, AOT publish x64, size and startup gates, packaging, contract checks, `actionlint` when workflows change, secret scan of the pushed range with the CI's pinned gitleaks image, NuGet audit through the locked restore and `npm audit --audit-level=high` where a repository has npm).
   - **Not reproduced locally:** CodeQL and GitHub dependency review are GitHub services; they keep running for external PRs and on the existing schedules. ARM64 legs are removed from the owner path by the user's instruction ("ARM64 CI coverage is explicitly removed from my lightweight PR path"). macOS is out of scope ([AD-0002](AD-0002-platform-scope.md)).
   - **Rules for agents** (the user's sentences, also in each repository's `AGENTS.md`): "AI agents must never use `git push --no-verify` to bypass required validation." "They must also never disable, remove, modify, or otherwise circumvent the hooks merely to allow a push." "If validation fails, investigate and fix the underlying issue." "If a required local test cannot run, do not silently skip it or claim successful verification." The coordinator adds that changing the verification scripts as reviewed engineering work is allowed; changing them to get a push through is not.
4. **Startup regression gate.** It compares against the PR's base commit built on the same machine: the merge base in the hook (*amended 2026-10-22 by AD-0020: in the host verification after the push*), the base commit on the same runner in external-PR CI. The previous main run's uploaded binaries are no longer used ([15](../architecture/15-performance-targets.md)).
5. **Testing techniques** (evaluated, not installed wholesale):

   | Technique | Decision | Evidence or reason |
   |---|---|---|
   | Property-based | **Adopt CsCheck** (one test-only package, no dependencies, Apache-2.0) for invariants, boundary conditions, resource constraints and parsers | Works from plain xunit facts, shrinks failures, and includes model-based and linearizability testing. FsCheck's xunit integration would couple to the repositories' `xunit.v3.mtp-v2` runner for no extra capability. |
   | Model-based and concurrency | **Adopt through CsCheck** for state machines and concurrent components | Same package. |
   | Fault injection | **Strengthen with real processes**, no new framework | Kill, crash, memory-limit, disconnect, permission and timeout faults are injected with the existing harness: `TestLoad` scenarios, real node and supervisor processes, real pipes and Unix sockets, real ACLs. Fakes stay limited to [AD-0014](AD-0014-delivery-method.md) §6. |
   | Stress and stability | **Add a repeat mode** to the test scripts (selected suites N times, stop at the first failure, per-iteration timing) for the deep tier | The flakes found so far (a settle window, PID reuse, the commit limit) needed repetition to surface. |
   | Coverage-guided fuzzing | **Not adopted now** | SharpFuzz needs AFL++ (Linux) or libFuzzer (Windows); neither is installed, and installations are the user's. Protobuf parsing is generated upstream code. Generated-input properties cover the parsers ArcForges owns (frames, configuration, CLI arguments, redaction). Revisit when a parser of untrusted input is added. |
   | Mutation testing | **Not adopted now** | Run on 2026-10-16: Stryker.NET 5.0.0 against `ArcForges.Node.Store.Tests` reported that the project uses Microsoft.Testing.Platform, "which is not yet supported by Stryker" (stryker-net issue 3094), and found 0 tests. Every ArcForges test project is xunit v3 on that platform. Switching runners to VSTest only for mutation runs is not justified. Revisit when Stryker supports it. |
   | Deterministic testing | **Fix flakes at the cause** | The Windows commit-limit test fails intermittently. The coordinator's diagnosis, to be confirmed or refuted by the ArcForges local-first test change (owner: step 3 of this effort, the ArcForges PR), is that the .NET GC's default hard limit (75 % of the job's commit limit) throws `OutOfMemoryException` before the job limit is reached, so the job's memory event never occurs. Job notifications are not guaranteed either (V-W03). Whatever the confirmed cause, the test exercises the job limit itself and asserts the guaranteed contract (commit never above the limit, violation classified from a guaranteed source), not an optional notification. Fixed sleeps become condition waits; generous timeouts stay only on the failure path; no retries or weakened assertions hide a defect. |

   **Tiers.**
   - *Routine (inner loop):* the affected suites, built once, then reruns without rebuilding.
   - *Pre-push (the hook):* (*amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md): post-push, on each host after the push, reported as commit statuses*) the full CI-equivalent profile on the native Windows and native Linux legs ([AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §5; amended 2026-10-21, formerly "on Windows and WSL Debian").
   - *Deep (manual, release preparation, after a flaky failure):* stress repeats, performance suites, long property runs (the WSL-bridge suites listed here until 2026-10-21 are superseded by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md)), and ARM64 through a manual `workflow_dispatch` when wanted.

   **Parallelism.** Test projects run concurrently with a bounded default chosen from recorded measurements (wall time, CPU, failures over repeated runs). Serial collections remain only where tests share machine-wide state. Timing-, CPU-share- and memory-sensitive tests carry the trait `isolation=exclusive` and run in a separate exclusive phase.

   > **Amendment (2026-10-17, the OS secret-store test tier).** After a Credential Manager incident, the user decided: "routine tests must not stress or modify my real Windows Credential Manager at scale. Move encryption, key lifecycle, failure-injection, and concurrency tests to isolated or mock secret-store backends." On the integration tests the user said: "Keep routine tests and local pre-push verification isolated or mocked. Run minimal, sequential Windows Credential Manager integration tests on disposable GitHub-hosted Windows runners for external PRs, manual dispatch, and weekly checks. Keep real Windows credential tests disabled locally unless explicitly opted in. Use the isolated ArcForgesTest WSL distribution for Linux Secret Service integration tests. Never run stress or load tests against real OS credential stores, including hosted runners. Keep real OS integration tests separate from the default test suite, with strict operation limits, unique names, timeouts, and safe cleanup. Preserve the existing local-first CI policy." Later that day the user added: "Ensure that routine tests cannot access my real OS credential store, and distinguish the production read-back policy from test verification." Consequences:
   > - The pre-push hook and the routine and deep tiers stay isolated. (*Amended 2026-10-22 by AD-0020: the host verification after the push replaces the pre-push hook here.*) They use the isolated secret-store backend ([16](../architecture/16-testing-strategy.md) §2): in memory, or file-backed under the test data root for nodes run with `--test-mode` ([02](../architecture/02-node-service.md) §4). They never touch a real OS secret store. The backend is added to the substitutes of [AD-0014](AD-0014-delivery-method.md) §6.
   > - A fail-closed structural guard enforces this ([16](../architecture/16-testing-strategy.md) §1). Real OS adapters are reachable from test processes only through the tier fixture, and only with the single opt-in `ARCFORGES_OS_SECRET_STORE_TESTS=1`, which only the tier runner or the hosted tier job sets. The guard has three parts:
   >   - **Runtime tripwire.** Every test project sets the AppContext switch `ArcForges.Security.Secrets.DenyOsStores=true`. The DesktopPlatform OS adapters, and from AF-LAN-01 the node key's CNG access, check it before any OS call and refuse unless the opt-in is set. Release builds never set it. This is a new `ArcForges.Security.Secrets` version that ArcForges admits.
   >   - **Repository check.** It runs in the hook and in external-PR CI (*amended 2026-10-22 by AD-0020: in the host verification after the push*), and covers test, tool and benchmark sources. In production sources these calls are allowed only at reviewed, injectable composition roots.
   >   - **Negative test.** It proves that a routine attempt fails.
   > - Real OS secret-store tests form a separate tier ([16](../architecture/16-testing-strategy.md) §1). The adapters' tier runs in DesktopPlatform; the node binding's tier runs in ArcForges. Windows Credential Manager runs in its own hosted job in each repository, with the run condition `github.event_name == 'schedule' || github.event_name == 'workflow_dispatch' || github.event_name == 'merge_group' || (github.event_name == 'pull_request' && github.event.pull_request.user.login != 'deku2026')`.
   >   - **Runs for:** external PRs, manual dispatch, a weekly schedule, and `merge_group`. `merge_group` is included because it runs the full validation for every author (§2), and none is configured today.
   >   - **Skipped for:** owner PRs, pushes to main and any other event. The standard validation condition of §2 excludes `schedule`, so this job is the one validation job with a schedule. Linux Secret Service runs in `ArcForgesTest` (*amended 2026-10-21 by [AD-0019](AD-0019-mcp-first-verification.md) §6: on the isolated Linux secret-store test host reached through the Linux MCP server*). On the workstation, both run only on explicit opt-in.
   > - The production read-back policy is separate from test verification ([04](../architecture/04-execution.md) §2). Production does not read back a node data key after writing it; read-back and absence checks belong to the tier.
   > - No stress or load test runs against a real OS store, hosted runners included.
   > - The rest of this decision is unchanged, including the owner-PR merge gate of §1; the scheduled job above is the only addition to the job classes of §2. Known limitation: a Credential Manager regression in an owner PR surfaces only through the weekly run, a manual dispatch or an external PR. Evidence: L-26.

   **Direction (roadmap; not release 1).** Amended 2026-10-19 by [AD-0017](AD-0017-delegated-execution-direction.md). The rules above bind every current test unchanged.
   - **The macOS Keychain** (effective when RM-15 is promoted) will be one of the real OS secret stores the 2026-10-17 rule covers: routine and pre-push tests never touch it, real-store tests run only in the separate, sequential tier with exact names and strict limits, Keychain behaviour is studied only on throwaway guests (LAB-MAC-11), and no stress or load test runs against it.
   - **A test-residue discipline for confinement objects** (effective when the first confined backend row, EX-10 or EX-11, is promoted) will apply the same approach to the OS objects confinement tests create: leased AppContainer profiles and their ACEs on Windows, transient units and slices on Linux. Tests create them with bounded churn and unique exact names, remove them by exact name, never at scale and never machine-wide, and verify the residue (for example, that a re-leased AppContainer identity has no access to the prior lessee's grants; [17](../architecture/17-delegated-execution.md) §14.1).

## Consequences

- The owner's PRs use no runner time for build, test or analysis; external PRs keep their full coverage, and merge commits trigger only delivery.
- PR evidence for owner PRs is the hook's PASS line (`arcforges-verify: PASS <sha> tree <tree> profile <name> …`), quoted by the coordinator, plus the review record. *Amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md) §7: the evidence is the required commit statuses at the PR head, plus the review record.*
- The Plan's execution policy, delivery procedure and prompts follow this decision; each active repository's `AGENTS.md` states the local-verification rules.
- **Known limitations:**
  - DesktopPlatform publication re-runs its gates on main, because its evidence chain binds them to the published bytes; changing that chain is out of scope.
  - ARM64 regressions in owner PRs surface only through an external PR or a manual dispatch.
  - CodeQL and GitHub dependency review run only for external PRs and on schedules; owner PRs rely on the local analyzers, NuGet and npm audits and secret scan.
  - Hooks are bypassable by design. The user accepted this for a trusted workflow ("I do not want a complicated enforcement infrastructure"); the rules above and the PASS line in each PR are the controls. *Amended 2026-10-22 by [AD-0020](AD-0020-post-push-verification-and-required-checks.md): the merge gate is now enforced by GitHub's required status checks, with no bypass actors; the statuses themselves are trusted as posted by the hosts (AD-0020, known limitations).*
