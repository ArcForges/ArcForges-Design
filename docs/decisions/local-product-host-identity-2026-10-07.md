# Product-owned DeviceLocal host identity

<a id="rule-p2-061"></a>

P2-061 admits the minimum real identity owner needed by APP.03's account-free ArcScope shell, current local-human endpoint and shared assistant host. The current Shell producer owns lifecycle/window/layout mechanisms, not a persisted Device identity. AssistantHostIdentity and APP.02's InstanceIdentity are typed carriers, not factories or authority. The existing APP.03 LocalProfileRegistry already verifies the actual operating-system subject and owns durable local profile/realm/user/installation/partition/store identifiers. These local identifiers are never a Cloud user, registered Device or live ApplicationTarget.

## Scope and owner

APP.03 owns a DeviceLocal host identity ledger in its existing Core/Shell scope, alongside LocalProfileRegistry. The actual host creates one stable, non-hardware DeviceLocal device identity for this product/installation/OS-subject binding, preserves the existing LocalProfile installation ID, and creates a distinct instance ID for each committed launch. A GUID is legitimate owner-created business identity only after this real owner commits and rereads its exact record; a caller GUID, username, environment alias or helper-generated target is never authority. This product-scoped local device identity does not imply a shared cross-product device, Cloud enrollment, trust elevation or hardware fingerprint.

Bind the record to exact product `arcscope`, actual current OS-subject fingerprint, the retained LocalProfile identity tuple, installation ID and actual canonical installation public SPKI/key version. Reuse the shared PLT.64 InstallationCredentialBroker and its genuine current-platform protected-store adapter for key custody; do not introduce product-private private keys, raw-signing/export operations, copied broker code, permissive key providers or a successful memory fallback. The ledger stores only public key metadata/digests. Its host port may borrow the actual broker, but must validate the broker's exact local realm/product/platform/installation scope before initialization/open and recheck current subject before disclosure. Windows SameUserShared assurance remains explicit, not hostile-sibling OS isolation. Unsupported or unavailable key custody is typed refusal; portable core and all feasible composition/component tests still advance, and the missing OS adapter remains a precise owner prerequisite.

## Initialization, persistence and launch ownership

An explicit local-workspace action may create a bounded, private, create-only pending installation record under the existing subject-owned product directory. This is a durable initialization intent, not a usable grant. Serialize initialization and host-generation mutation through an actual cross-process exclusive kernel file lease; bound acquisition, cancellation and all record sizes. Verify actual directory/file owner and restrictive ACL/mode, reject reparse links/redirected parents/foreign or malformed records, and retain the same exact identity winner across concurrent callers.

The pending record fixes the local device/install/profile binding before shared key initialization. Resolve or initialize the same real protected installation key, then commit and read back its exact public identity. A crash between these steps resumes the same pending identity/key, never chooses a new device/install or rotates an existing key. Once bound, opening uses the shared broker's exact expected-key operation; missing/corrupt/mismatched key state refuses without regeneration. Cancellation or write failure after possible persistence requires readback reconciliation and truthful happened/unknown classification. Never report an uncommitted initialization as a usable local host.

Keep a separately persisted unsigned-64 host generation counter. Each admitted launch atomically allocates the next positive generation and commits its fresh instance ID and original launch command ID before exposing a host lease. Identical launch-command replay returns the exact original committed allocation; changed identity/intent for the same command conflicts. Use exact canonical bounded records and checked uint64 arithmetic, never floating point, wall-clock ordering or a reset on restart. Refuse overflow, malformed/truncated/future records or bounded-capacity exhaustion before mutation; preserve all prior counters and required launch-command fences. Partial/uncertain writes cannot silently lower the counter or permit another allocation with the same command. A ledger rollback cannot be represented as hardware/OS anti-rollback protection; state that assurance limit explicitly.

Different legitimate processes may hold distinct committed local instances concurrently. The newest allocation does not automatically revoke older still-live instances. Each host lease binds its exact instance/generation and installation/subject/key, exposes its own irreversible retirement token, fences new work at shutdown and joins admitted operations before releasing owned resources. Captured local actor/profile evidence must recheck the actual current subject and bound key/record as appropriate; no arbitrary caller can restore a retired lease. Duplicate initialization/replay does not transfer ownership of another process's live lifecycle. Local host generation is only this owner's launch ordering/lifetime value, never the DEV.01 DO epoch or remote execution eligibility.
