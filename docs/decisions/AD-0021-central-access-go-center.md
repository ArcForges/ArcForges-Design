## Context

Until now the design emphasized local direct access (the CLI, Desktop and the stdio MCP adapter talk to the node over its local endpoint), LAN expansion between paired nodes without an account, and cloud access as an additional Pro capability. The Cloud service was a C# Native AOT host on Cloudflare Containers with D1 persistence, of which only the anonymous Hello method was ever served in production.

The product owner decided a different product architecture: user-owned C# execution nodes reached through a configured central service (the **center**), with the center implemented in Go and its relational persistence in Neon/PostgreSQL. Ordinary clients and cloud AI then share one account, device-authorization and access model, while execution authority stays at the node. The language and database decisions are settled; this record makes no performance claim for Go.

## Decision

1. **Execution authority stays on the node.** Nodes and the CLI stay C# ([AD-0003](AD-0003-architecture-and-runtimes.md) §1). A node runs on the user's Windows 11 computer or native Linux machine or VPS (x64 and arm64) and owns execution state, scheduling, priorities, resource limits, output, cancellation, restart recovery, workspaces, local toolchains, diagnostics, cleanup and its SQLite store. Same-machine shared directories and cache reuse across worktrees stay. ArcForges stays a product for user-level workloads: it gains no privileged system-management or elevation feature ([AD-0011](AD-0011-identity-and-login.md) §6).
2. **Ordinary use goes through a configured center.** The normal paths are:

   | Caller | Path |
   |---|---|
   | Desktop, CLI, Web, Android | central business API → the explicitly selected node |
   | Cloud AI | central MCP → the explicitly selected node |
   | Local AI | the optional stdio adapter (`arcforges mcp serve`) → the same center → the selected node |

   The center owns accounts, device ownership, authorization, entitlements, routing and remote access. The node owns durable execution state and enforces its local resource and permission policy; **central authorization never bypasses node policy**. Multiple devices per account and work on an explicitly selected device are device management and remote control, not LAN distribution.
3. **Installation and association.** The node installs as a background service (the Windows per-user supervisor; a Linux systemd user unit); no desktop UI is required. Browser sign-in (PKCE with a loopback redirect) or a device code associates the installation with an account ([AD-0011](AD-0011-identity-and-login.md) §2), and the node then keeps an outbound authenticated connection to its center. Normal use exposes no inbound node port.
4. **The center is configuration.** Official installations use the official center (`https://arcforges.com/api`, the configured default); self-hosted installations use the center their owner configures. No code path depends on a hard-coded official endpoint: the endpoint is a setting of the node, the CLI and the adapter, and the center derives every URL it issues from its own configured public base URL.
5. **Local IPC is internal.** The node's local endpoint ([02](../architecture/02-node-service.md)) stays for node lifecycle and management (start, stop, status, settings), sign-in, diagnostics and recovery, and for the node's own tests. It is not an official route for ordinary task submission: `arcforges run` submits through the center to the selected node (default: the node of this installation). A diagnostic local submission (`arcforges run --local`) stays for recovery while the center is unreachable, bounded so that it cannot become a second ordinary route: it is accepted only from a local caller of HUMAN origin (never AGENT or SCRIPT, never from the stdio adapter, MCP or hook rewrites), the CLI labels it diagnostic, and the task record marks it `local-diagnostic`.
6. **Business API and MCP are separate entry points.** Ordinary clients use the business API (Protobuf over Connect, gRPC and binary gRPC-Web, the contracts of `arcforges.fleet.v1`, `arcforges.publicapi.v1` and the hello contract). AI uses standard MCP over the Streamable HTTP transport. They share the center's Go services; whether they run in one process is an implementation choice, validated by measurement in AF-CTR-07, not a product requirement.
   - **Central MCP** authorizes with OAuth 2.1 as the current MCP authorization specification defines it (protected-resource metadata, authorization-server metadata, PKCE, registered or metadata-document clients, audience-bound tokens). Every call names its target device explicitly; a device ID is an identifier, never a credential. The caller's identity, its scoped permissions and the MCP session (`Mcp-Session-Id`, stored by the center and bound to the grant) are checked on every call, so a session survives reconnection and never depends on a client or adapter process ID.
   - Tools keep task IDs, bounded waits and follow-up status, output and cancellation by ID ([experience/mcp.md](../experience/mcp.md)), and add device selection and bounded file read, write, edit and search, workspace and cleanup operations with path boundaries, limits, permissions and audit (AF-CTR-06, AF-CTR-07).
   - ArcForges provides no AI reasoning and never captures commands that an AI client runs through unrelated MCP servers.
7. **Three credential kinds, kept apart.** Account sessions (`account`, `mobile.limited`), node credentials (`node`) and AI MCP grants (`agent`, new). An agent grant is issued to an AI client by an account holder's consent, is scoped to that account, a set of devices and a set of tool permissions, and expires and refreshes like any OAuth grant. A caller with an agent grant has origin **AGENT** at the node ([AD-0007](AD-0007-ai-integration.md)); signing in to the account never makes it HUMAN, and it can never approve its own requests. Every credential kind can be revoked, and revocation is checked on every call.
8. **The center is implemented in Go and persists to Neon/PostgreSQL.**
   - **Language.** Go, at the latest stable toolchain verified when a task starts and pinned by exact version and archive hash (Go 1.27.3 on 2026-10-28). Go is compiled native code; it is not .NET Native AOT, and health reports say so (`runtime=go`, `nativeAot=false`).
   - **Contracts.** The `.proto` files of the Contracts repository stay the single source, including `service` and `rpc` definitions. Go bindings are generated from them in the Contracts repository, checked for drift, verified for wire compatibility with the C# bindings, and published at the cohort version of the C# packages (AF-CTR-01). No wire code is written by hand.
   - **Persistence.** PostgreSQL (Neon in the official deployment) holds every relational record of the center: accounts, sessions, devices and nodes, grants, entitlements, commerce, notification, support, audit, configuration, command receipts, inbox and outbox. Each module owns a PostgreSQL schema; the guarantees of the D1 storage plans, guarded batches and table-rebuild migrations are re-implemented with native transactions, constraints, row locks and `ALTER TABLE` ([data/cloud-store.md](../data/cloud-store.md) §6). Migrations are versioned and checksummed, applied under an exclusive advisory lock through the direct (unpooled) connection with the migration role, and the runtime uses the pooled connection with a separate least-privilege role.
   - **D1** is no longer the center's store. Production never had a D1 binding ([10](../architecture/10-cloud.md) §1), so no production business rows exist in D1; the `proof` environment's D1 database is inspected, backed up and retained as history by AF-CTR-09, never deleted by automation.
   - **R2 and Durable Object storage** keep their distinct platform roles (release artifacts and consented support bundles; Container lifecycle). The relational migration does not replace them.
9. **The hosted deployment keeps the Cloudflare platform roles.** The Worker stays a thin TypeScript adapter (routing, edge limits, the deny-by-default route table, and the pass-through of node WebSocket upgrades and MCP requests to the Container); the Container runs the Go center; the Container Durable Object keeps its lifecycle role. **Node connections terminate in the Go center** (one implementation of the node channel, the same in hosted and self-hosted centers) instead of a per-account `FleetHub` Durable Object ([AD-0009](AD-0009-cloud-relay-and-cost-controls.md) §1, which is amended accordingly). The channel keeps the Protobuf relay frames of `arcforges.relay.v1`, extended additively with call frames (AF-CTR-05). Consequence: while any node is connected the Container instance stays running; the deployment's `max_instances`, instance type and per-account node limits bound that cost, and a per-account Durable Object hub is recorded as an exploratory scaling option (roadmap EX-28). Workers.dev and preview URLs stay off; Web keeps the apex Custom Domain, and the center keeps the route `arcforges.com/api/*`.
10. **What passes through the center, what it keeps.**

    | Data | Through the center | Persisted by the center |
    |---|---|---|
    | Account, device, node and grant records; entitlements; audit events | — | Yes, for their retention ([data/cloud-store.md](../data/cloud-store.md)) |
    | Task routing records: task ID, node, caller principal and origin, command ID, state summary | Yes | Yes, as receipts for idempotency and audit (retention as `fleet_remote_command`, 90 days); no command line, environment or output |
    | Task specifications (argv, working directory, environment) | Transiently forwarded to the selected node, in memory, bounded | No; the audit event keeps a SHA-256 and the size |
    | Output | Transiently forwarded by offset on request | No; the node keeps output |
    | File contents (read, write, edit, search results) | Transiently forwarded, bounded per call | No; the audit event keeps the path, operation, size and SHA-256 |
    | Workspaces and local caches | Never uploaded | No |
    | Secrets (D3) | Never; redacted by the node | No |

    Minimization, redaction, permissions and audit of [11](../architecture/11-security-privacy.md) apply; the center logs no command line, environment, output or file content.
    **Routed calls are signed end to end** (T-11 unchanged). The center signs every call it routes to a node with its ES256 command-signing key ([AD-0009](AD-0009-cloud-relay-and-cost-controls.md) §5, V-N05): the signed payload carries the key ID, the target node, the caller principal and origin, the command ID, the method, a digest of the request and an expiry of at most 5 minutes. The node verifies the signature against the center keys it received at enrollment and with credential refresh, the target, the expiry (±120 s skew) and its local policy before it acts, and signs its result with its node key (generated at sign-in, with its public key registered by `CompleteNodeSignIn`; the center's public keys reach the node with `CompleteNodeSignIn` and `RefreshNodeSession`, AF-CTR-04). A call that arrives after its expiry is never executed. Neither the Worker that passes the connection through nor anything else on the path can inject or alter a call. Signatures and request digests cover the exact serialized bytes as transmitted: a verifier never re-encodes a decoded message to check a signature or a digest, because the Go and C# Protobuf encoders produce equivalent but not always identical bytes (for example the position of `oneof` fields; V-N07).
11. **Failure behaviour.**

    | Event | Behaviour |
    |---|---|
    | Network loss between node and center | Node-accepted work continues; the node reconnects with jittered backoff (1 s → 60 s); callers resume output by offset and status by task ID |
    | Center restart or deploy | Node connections drop and re-establish; in-flight calls fail with `UNAVAILABLE` and `effect UNKNOWN`; callers retry with the same command ID |
    | Retry after an uncertain submission | The node deduplicates by command ID ([AD-0006](AD-0006-execution-semantics.md)); a task is never executed twice and never silently lost |
    | New command for an offline node | Refused with `UNAVAILABLE/node_offline`; the center does not queue task submissions, because it does not persist task specifications (the earlier per-node envelope buffer of [10](../architecture/10-cloud.md) §3.6 is not built) |
    | Database outage | Calls that need the database fail with `UNAVAILABLE` and retry advice; node-accepted work continues |
    | Revocation of a node credential, session or agent grant | The next call with it is refused; a revoked node's connection is closed; accepted tasks continue at the node, and only a still-authorized principal (or the node's local owner) can read or cancel them |
    | Entitlement change | New center-routed calls are checked against the current entitlement; a lapsed subscription closes the node's connection at the next entitlement check (§13a); accepted tasks are not cancelled |
    | Timeouts | Every center-routed call carries a deadline (≤ 55 s for waits); expiry returns the current state, never a guess |

12. **LAN leaves current delivery.** LAN discovery, LAN pairing, automatic cross-machine scheduling, distributed input and output transfer, and inter-node compiler-cache sharing are not built. Tasks AF-LAN-01, AF-LAN-02 and AF-LAN-03 are superseded; requirements R-LAN-001 … R-LAN-011 are out of current delivery; [AD-0008](AD-0008-lan-trust-and-placement.md) and [09](../architecture/09-lan.md) are kept as history; LAN distribution is roadmap RM-19. Published contracts and fields stay compatible: `arcforges.peer.v1`, `PeerService`, `NodeEnrollmentService.IssueNodeCertificate`, `GetLanHints` and `ReportLanEndpoints` stay in `v1` and are refused as not served. Same-machine cache reuse stays, and no dedicated WSL integration returns ([AD-0018](AD-0018-native-platforms-without-wsl-integration.md)).
13. **Editions and hosting.** User-owned compute and the open-source software (the node, CLI, clients and center under their licences) are distinct from the official hosted center, which is a service. A self-hosted center needs no official service. The earlier promise of account-free, center-free normal operation ([AD-0015](AD-0015-direction-editions-roadmap.md) §2) is withdrawn: normal operation uses a center, official or self-hosted. This record decides no price, free allowance, device limit or package (the structure of hosted plans is decided in §13a); existing limits in [10](../architecture/10-cloud.md) §5 are current settings to assess, and prices remain H-07.
13a. **Hosted subscriptions and self-hosted mode** (the product owner's decision of 2026-10-28, recorded after this record was first accepted).
    - **Official hosted center.** Center-mediated node connectivity, execution, monitoring and control, and MCP access are subscription services. There is no permanent free allowance of hosted nodes at this stage. Essential sign-in, account, billing, security and recovery operations stay available without a subscription.
    - **Free use** remains available through self-hosting. A self-hosted center never requires an official ArcForges subscription.
    - **Self-hosted mode** is an explicitly configured center mode. In it, a built-in default enables the self-hostable capabilities that are available, with optional operator-configured feature and resource limits. External services (e-mail, push, payments, storage) still need the operator's own configuration and credentials.
    - **Fail closed.** The center's mode is explicit configuration. Missing or invalid configuration in official-hosted mode never silently enables every feature: without a valid subscription entitlement, a gated feature stays unavailable.
    - **No bypass.** Feature availability never bypasses authentication, device ownership, authorization, AGENT/HUMAN separation, audit or resource controls; it is one more check after them.
    - **Enrollment and lapse** (design choices under this decision). Node sign-in and device association are account and device operations and stay ungated; the node's connection to the center is the gated connectivity. When a subscription lapses, the center refuses new gated calls and closes the node's existing connection at its next entitlement check, no later than the node's next credential refresh; node-accepted work continues at the node (§11).
    - **Feature keys.** The catalogue's feature keys for these services are `center.nodes` (node connectivity), `center.execute` (center-routed execution and file and workspace operations), `remote.view` (monitoring), `remote.control` (control), `center.mcp` (MCP access) and `push` (notifications); essential operations have no key and are never gated.
    - **Values are configuration.** Exact prices, trials, node limits and traffic allowances remain separate owner decisions (Plan acceptance register H-07, still open for them). The plan catalogue is configuration: development fixtures (tests and the acceptance environment's attributable test identities) are distinct from production settings, and production sales are not activated by this decision.
14. **Retained business capabilities** move to the Go center unchanged in meaning: identity and login ([AD-0011](AD-0011-identity-and-login.md)), devices, entitlements and commerce (Paddle, Google Play; [AD-0010](AD-0010-commerce-and-entitlements.md)), notifications, support, audit, configuration and operating budgets. Their remaining planned tasks are re-targeted to the Go center.
15. **The C# center is retired after its replacement is proven.** The C# Cloud host stays in the image only as the Hello rollback path and the `proof` environment's foundation (delivered note, 2026-10-28: since Cloud #117 the `proof` environment runs the Go center, so only the rollback path remains) until AF-CTR-09's exit criteria hold: every active route served by Go on the deployed revision, the PostgreSQL recovery drill passed, and one release on Go without rollback. Released artifacts, images and historical evidence are kept; nothing is unpublished or deleted.
16. **Verification.** The Go center is verified on both native legs ([AD-0020](AD-0020-post-push-verification-and-required-checks.md)): format, vet, static analysis, unit tests, generation drift and native builds on Windows and Linux; real PostgreSQL integration tests, the race detector and the container image on Linux, where Docker and cgo are available. Cross-compilation is never counted as another platform's execution. The engineering controls of the C# projects are carried over with explicit dispositions (AF-CTR-02).

17. **Owner decisions and design choices.** Items 1–4, 6 (separate entry points, MCP authorization, explicit device selection, identity and session rules), 7, 8 (Go, Neon/PostgreSQL, Go bindings from the single source), 10 (what may pass through or persist, as minimization rules), 12, 13, 13a (except its design choices on enrollment, lapse and feature keys) and 14 restate the product owner's decisions. The following are design choices made under them, recorded here so that a later change needs only a reviewed amendment: node connections terminating in the Go center instead of a per-account Durable Object hub (§9); the bounded diagnostic `arcforges run --local` (§5); signed routed calls (§10); the 90-day retention of routing records (§10); the ungated enrollment, the lapse behaviour and the feature keys (§13a); no store-and-forward of submissions by the center (§11); PostgreSQL schemas per module ([data/cloud-store.md](../data/cloud-store.md) §6).

## Open questions for the owner

These are not decided by this record and block only what their entry names ([Plan acceptance register](https://github.com/ArcForges/Plan/blob/main/acceptance-register.md) H-07):

1. **Plan contents under center access.** *Partly decided 2026-10-28 (§13a):* the gated features of the official hosted center are its center-mediated services, there is no permanent free hosted-node allowance, and essential operations stay ungated. Still open: exact prices, trials, node limits and traffic allowances; activation of the center surfaces and of sales in production (AF-PROD-01) waits for them.
2. **Entitlements on self-hosted centers.** *Decided 2026-10-28 (§13a):* no official subscription is required; an explicitly configured self-hosted mode enables the available self-hostable capabilities by a built-in default, with optional operator-configured feature and resource limits.
