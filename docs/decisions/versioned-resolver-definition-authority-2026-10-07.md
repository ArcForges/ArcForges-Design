## Private canonical artifact and owner contracts

`entitlement.resolver-definitions.v1` is a distinct signed-manifest-referenced private immutable artifact, not another ConfigurationDocument field or a public wire schema. Its exact sorted root is `{allowances,capabilities,definitionsVersion,quotas,schemaVersion}`. `schemaVersion` equals `entitlement.resolver-definitions.v1`; definitionsVersion is nonempty, bounded to128 UTF8 bytes and uses the actual existing owner version rules. Each array has at most64 descriptors and the complete canonical UTF8 document at most65536 bytes. Capability descriptors are exactly `{featureGate,key,requiresPaidTerm}`, with nullable featureGate and Boolean requiresPaidTerm; quota descriptors are exactly `{combination,key}` with Sum/Max/PriorityReplace; allowance descriptors are exactly `{key}`. Arrays sort by unique ordinal key and use existing COM.05 InputRules/RecordSetValidator semantics. Reject malformed UTF8, duplicate/unknown fields or keys, noncanonical bytes, unsupported combinations, invalid references, wrong version/hash/length and overflow. RealmKind is separately retained as the actual `official`/`selfHosted` fact from the fully validated signed Configuration identity; no caller realm flag or default registry is authoritative.

The neutral pure owner validator returns the complete immutable resolver set and canonical hash after defensive capture. Pure validation is not approval. Config first resolves the independently referenced full-definition artifact from the signed proposal manifest and invokes this validator. It then validates the distinct COM.18 unit/mode artifact against that returned complete owner quota set. The unit candidate cannot define its own expected keys. Neither staging step depends on the candidate already being active or materialized.

Neutral production ports expose bounded pure validation, exact immutable version read, current approved association read, exact historical approved association read, separate exact artifact reopening and stable publication. Associations carry actual realm/Guid configuration revision/lowercase64hex document hash/RealmKind/definitionsVersion and exact artifact ID/profile/hash/verified length. Artifact bytes stay in the separate artifact port. Config-owned trusted PublisherRef, not a proposer/approver alias, authorizes materialization. No raw token, signature-as-permission Boolean, foreign module descriptor, SQL or mutable latest fallback crosses the boundary.

## Persistent owner and activation ordering

The new immutable `entitlement.resolver_definition_profile` is keyed by realm and definitionsVersion. It stores complete canonical artifact bytes/hash/length, exact artifact ID/hash, actual original approved Config revision/document hash/RealmKind, configured publisher identity and created_at. Same realm/version cannot acquire different canonical bytes, semantics, artifact identity or realm kind. Its first approved provenance remains unchanged when a later approved Configuration references the identical artifact; a new authorized stable command may write its exact no-change receipt but cannot overwrite that provenance. Immutable UPDATE/DELETE refusal and a guarded same-batch publish/real platform receipt/archive provide concurrent insert safety, seven-day command receipts, exact replay, changed-ID refusal and cancellation-after-commit recovery. Reconcile an unknown write read-only before any bounded identical-command retry; unavailable reconciliation remains UnknownOutcome. No network call occurs inside the batch. Retain profiles while snapshots, grants, old reservations or accepted replay/rebuild need them; removal is an explicit audited retention decision, never automatic head replacement.

Config activation retains its existing atomic head/approval consumption/outbox. Its durable exact materialization commands publish the independent full definitions before quota semantic profiles. Between activation and materialization, current resolver reads reject missing/mismatched current-head definitions instead of returning the old set. Successor staging verifies each previously accepted materialization against the actual owner version store; old stable commands replay without republishing current state. Superseded approved historical materialization may recover only the exact already accepted immutable version under retained authority; an obsolete unpublished command cannot create a stale current source. Both current and historical association readers use actual Config evidence, never a synthetic success adapter.

The production async resolver reads one captured immutable actual definition set for each operation/attempt. It resolves current realm/head association and exact stored version/hash, and reopens the actual current association after awaited work before yielding a current snapshot or preparing mutation. A write must additionally bind the actual Config head/association through its issuer-sealed scope-bound read guard in the same fixed batch as the existing Entitlement writer's revision/activation/records/snapshot; an async reopen alone is insufficient. Admit only the closed `entitlement-definition-resolution` family and its exact `commit-current` plan: Config is read-only, Entitlement alone prepares its existing write, Platform supplies existing commit-tail/recovery authority. No alternate resolver writer or generic cross-owner capability is introduced. Historical rebuild explicitly resolves the snapshot's retained definitionsVersion and immutable owner profile and does not substitute the current version. No `.Result`/`.GetAwaiter().GetResult()` over storage, global mutable registry, candidate-derived expected set, hidden empty source or guessed version is permitted. Existing pure COM.05 algorithms and canonical snapshot bytes stay intact. Synchronous test-fixture compatibility may remain explicitly isolated; production DI selects only the real async source. COM.18's independent quota-definition source projects from this complete versioned producer, retaining typed unavailable/not-found/stale distinctions.
