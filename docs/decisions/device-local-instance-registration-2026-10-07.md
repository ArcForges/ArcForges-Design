# DeviceLocal in-process instance registration

<a id="rule-p2-079"></a>

Status: APP.03 supporting decision P2-079. P2-061 remains unchanged.

The existing Capabilities `InstanceIdentity` requires a non-null delivery epoch supplied by the installation registration authority. It is a typed in-process owner carrier, not a permission or a Cloud registration factory. APP.03's P61 product-owned DeviceLocal ledger already creates, commits and rereads the genuine product/OS-subject/profile/device/install/key tuple, a distinct per-launch instance and a positive checked uint64 HostGeneration under a source-owned sealed current live lease.

For DeviceLocal in-process composition only, that P61 ledger is the installation registration authority. Map the exact committed Receipt.InstanceId and Receipt.HostGeneration to InstanceIdentity.InstanceId and InstanceIdentity.Epoch. Preserve the retained local DeviceId/InstallationId/product tuple. Admission must check the same sealed lease's actual current private OS subject/profile, expected protected installation key and durable record, cancellation and irreversible retirement before disclosure. Keep the lease fence throughout the owning product host; an immutable identity copied after admission is not an independent grant. Missing/foreign/future/corrupt/retired/cancelled evidence refuses, with no guessed epoch, reset, regeneration, fallback or latest-global-generation test.

Different genuine local processes retain independent committed instance/generation lifetimes. A newer launch does not revoke an older still-live lease. Replaying a launch receipt does not restore a retired lease or transfer another process's physical lifecycle. LocalHuman evidence and explicit operation grants remain independently current; assistant/delegated actors still require their own actor-bound endpoint, real lease/approval/task/revocation and audit. The mapping cannot mint LocalHuman authority merely from a generation value.

Use the exact identity directly with existing ProductComposition, local availability/context providers and Shell lifetime owners. Existing ApplicationComposition.Start allocates a fresh InstanceId and has no existing-identity overload; calling it after a P61 launch would silently replace the committed ID and is not this mapping. No Capabilities API, validation range, producer source, package identity or wire schema changes are needed.

HostGeneration remains local ordering/lifetime evidence. It is never DEV.01's Durable Object live epoch, Cloud Device enrollment, hardware identity, signed-in principal, ApplicationTarget.instanceEpoch or remote execution eligibility. Actual C13/current Devices/Workspace authority and acknowledged DEV registration remain mandatory for the separate Cloud adapter; no automatic conversion or fallback is admitted. Existing P61 assurances and rollback limits, genuine published PLT65 custody subset consumption and full PLT64 signer obligations remain intact.

Implement only the owned Core/Shell/LocalProductInstance.cs adapter, existing LocalHostIdentityTests.cs affected cases and already-owned docs/local-host-identity.md actual explanation. Tests must prove exact committed ID/generation, original-command replay, independent simultaneous local lifetimes, no stale/retired/foreign admission, cancellation and current-key refusal using the real ledger/persistence/OS-subject ports. Substitute only genuinely unavailable inputs and distinguish component evidence from installed OS/full Cloud/assistant acceptance. Preserve all existing outcomes, dependencies, top-level graph fields, unrelated tasks, shared assistant capabilities and strict published-package/admission/CI/review/publication obligations.
