## 3. Actual credential immutability and revision discipline

The additive identity__credential-security-invariants pending migration installs actual triggers on identity_auth_identity. The existing physical columns and baseline bytes remain unchanged.

- BEFORE INSERT, refuse an existing auth_identity_id or an existing exact realm_id/provider_id/subject natural-key tuple, preserving the actual unconditional unique index. New credentials require an actual same-realm User in state1/2/3; PendingDeletion4/Deleted5 cannot recreate a removed identity during or after purge. - BEFORE UPDATE, NULL-safe exact comparisons refuse changes to auth_identity_id, user_id, realm_id, method, provider_id, subject, public_key, user_handle, backup_eligible and created_at. These are immutable identity/owner/key facts. New keys, provider linking/rebinding and replacement credentials create a new genuine identity ID and revoke the old one.
- New revision is positive and either the exact old revision or old+1 while old<Int64Max. Changes to password_hash, sign_count, backup_state or revoked_at require old+1. Label or transports changes also require old+1. Pure last_used_at observation may retain revision or accompany an increment, but may never erase or move an existing observation backwards. NULL and empty values are distinct; security mutation at Int64Max refuses.
- Revocation is one-way. A nonNULL revoked_at cannot become NULL or another timestamp. An ordinary removal soft-revokes through actual current-owner guards.
- BEFORE DELETE, require an actual Identity-owned identity_account_deletion row for the same User/realm and exact request timestamp. The final owning purge family contributes actual User/deletion revisions and current state before its records; a stale lifecycle row alone is not current authority. The migration and purge adapter consume the actual CLOUD.79 schema/producer; a missing table/source is typed unavailable, never fabricated or bypassed. Existing active authentication/cancellation guards refuse a concurrently purging/purged User.

No active User may recreate a previously removed credential ID/revision. Restore/recovery preserves the same physical triggers and real owning lifecycle authorization. If an existing legitimate operation conflicts with immutability, review that exact operation as a replacement identity or separately tracked revision; do not weaken every credential's currentness.

Actual migrated SQLite tests cover binding rewrites with and without rev+1, password rehash, passkey counter/backup observations, soft revoke, relabel/transports, monotonic last-used, NULL transitions, overflow/jumps, active-user hard-delete refusal, genuine purge and concurrent-proof refusal.
