## Decision

### Process model

The node runs **as the signed-in user, without elevation**. It launches managed processes as that user and never elevates them. Core features need no administrator or root rights.

> **Amendment (2026-10-19): never elevating is not never causing a privileged change.** ArcForges never elevates, but an unconfined managed process can still obtain privileged changes through channels the OS offers the user ([11](../architecture/11-security-privacy.md) §1, T-26):
> - **Linux:** requests over the system bus that polkit authorizes; no-new-privileges does not stop them, and distribution rules can authorize installs for active administrator-group users without a prompt (V-L08).
> - **Windows:** sudo, which elevates only through UAC and which Microsoft warns can be a potential escalation-of-privilege vector in some configurations, such as the inline mode (V-W09); and, generically: **on an administrator account without Administrator protection, UAC is not a security boundary; unconfined workloads may obtain administrator rights silently** (V-W07, V-W08).
>
> The release coverage statement carries that generic sentence ([product definition](../product/product-definition.md) §9). The host's own account type and Administrator protection state are host posture: only the doctor's HUMAN-only host-posture check reports them ([07](../architecture/07-records-diagnosis-memory.md) §2.4), never the release coverage statement. The decision above is unchanged; only the claim it supports is narrowed.

> **Amendment (2026-10-19): the same-user qualifier.** The managed processes and ArcForges' containers belong to the same user. Every resource guarantee of this decision, on Windows and on Linux, is **ENFORCED against accidental and over-privileged workloads, and a GUARDRAIL against workloads that target ArcForges' objects**: same-user code can change or end ArcForges' containers (V-W11; T-22), and work launched outside the recorded ancestry never joins them (V-W01, V-W10; T-23). The mechanisms are unchanged ([03](../architecture/03-resource-control.md) §5).

Optional privileged features are designed but not part of the current deliverables: a machine-wide Windows service mode (a separate per-machine installer, AR-16), and Linux I/O control. They are never required for development-stage acceptance.

### Windows

1. **Root job.** At startup the node creates (or re-opens) a named root job `Local\ArcForges.<node_id>.root`, with:
   - a hard CPU cap;
   - a job commit limit;
   - a notification limit for soft-pressure signals.

   Values per 03 §5 (V-W03–V-W05). They are updated with hysteresis when budgets change.
2. **Attempt jobs.** Each attempt runs in a child job `Local\ArcForges.<node_id>.<attempt_id>`, nested in the root job (V-W01). Its limits follow 03 §5:
   - weight-based CPU rate control, or a hard cap when a per-task cap is set;
   - the job priority-class limit `BELOW_NORMAL_PRIORITY_CLASS` (`JOB_OBJECT_LIMIT_PRIORITY_CLASS`) for every attempt, because the root job's hard cap alone did not keep the reserved headroom responsive (L-28; amended 2026-10-23);
   - a per-job commit limit;
   - `ActiveProcessLimit` when policy sets one;
   - no breakaway allowed.
3. **Handle holders keep jobs alive across node restarts.** A named job disappears from the namespace as soon as its last handle closes, even while processes still run inside it (L-14). So every attempt has a holder: the launcher role `arcforges node exec-wrap`.
   - **Where it runs.** The holder runs *outside* the job (it is not assigned to it). It inherits handles to the child job and the root job, with `JOB_OBJECT_ASSIGN_PROCESS`, `JOB_OBJECT_QUERY` and `JOB_OBJECT_TERMINATE`, and to the output files.
   - **What it does.** It creates the target process suspended, assigns it to the **root job first and then to the child job**, resumes it and waits for it. Assigning a process that is already in the root job to the child job is what nests the child under the root (V-W01); assigning it to the child alone would leave the child a top-level job outside the root caps. Where available, `PROC_THREAD_ATTRIBUTE_JOB_LIST` with `[root, child]` does the same at creation. No ArcForges job sets UI restrictions, because those prevent nesting. F-W01 verifies the resulting hierarchy. *Reinforced 2026-10-19:* no ArcForges job, root or attempt, sets UI limits. A workload that sets UI limits on jobs for its own children may fail to nest them inside its attempt job. Chromium's sandbox source sets such limits, so Chromium-family programs are expected to; this is unverified for ArcForges workloads, and whether they degrade or fail is unknown, a known compatibility risk ([03](../architecture/03-resource-control.md) §5.2).
   - **Exit record.** It writes the durable exit record with job accounting ([04](../architecture/04-execution.md) §3). For node-gap recovery (MR-17), a peak above the attempt job's current enabled memory-notification threshold is retained as `job_memory` even after current usage/violation flags clear. The holder queries that threshold from the job when recording, rather than substituting the hard cap or cached startup value. The existing nonzero-exit condition still applies; this does not prove allocation refusal ([04](../architecture/04-execution.md) §7).
   - **Disk guard.** While the node's heartbeat is stale, it enforces the attempt's output, temporary-space and low-space limits, because it holds the job handles and the output files ([06](../architecture/06-storage-workspaces.md) §5).
   - **Lifetime.** It keeps both job handles until the node acknowledges the record, through the named event `Local\ArcForges.<node_id>.<attempt_id>.ack`.

   While any holder lives, `OpenJobObject` by name succeeds, so a restarted node re-opens the attempt and root jobs, re-reads accounting and cancels or limits them as before.
4. **Completion ports.** A job accepts one completion port. A restarted node first clears the old association, then attaches its own (L-15). It then queries `JobObjectLimitViolationInformation` and the basic accounting, to catch limit events it missed while down.
5. **Kill with node.** Tasks marked `kill_with_node` are launched by the node itself, without a holder, in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The node's handle is then the only one, so the job is killed when the node exits. Their exit status is captured only while the node runs.
6. **Launch order.** Processes are created suspended (`CREATE_SUSPENDED`), assigned to the job, then resumed, so no child escapes before assignment.
7. **Termination.**
   - **Graceful:** cancellation sends `CTRL_BREAK_EVENT` to the attempt's console process group. The root process starts with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`: a windowless console and its own group. The `arcforges node signal` helper frees its own console, attaches to the root process's console and signals the group; this works on Windows 11 (L-18). Descendants with their own console, GUI processes and failed attaches fall back to `WM_CLOSE` and the forced phase ([04](../architecture/04-execution.md) §6).
   - **Forced:** after the grace period, `TerminateJobObject`.
   - **Escaped processes** (amended 2026-10-19): an ancestry scan finds processes outside the attempt job whose recorded ancestry passes through a job member, reports them as `ESCAPED` (R-RES-012) and terminates them if they are same-user and policy permits. Attempt jobs allow no breakaway (item 2). Launches through WMI, a broker, a service, a scheduled task or a spoofed parent leave no such ancestry (V-W01, V-W10): they are not detected and appear as `UNMANAGED`, a documented gap ([11](../architecture/11-security-privacy.md) §1, T-23; A-W04).
     *Superseded text (until 2026-10-19):* "an ancestry scan finds processes that escaped (WMI-created, broker-launched) and reports them as `ESCAPED` (R-RES-012). It terminates them only if they are same-user descendants by ancestry and policy permits." It overstated the scan: WMI-created and broker-launched processes do not descend from the job's members, so the scan cannot find them. Successor: the text above.
8. **No pause or soft limit.** Windows has no `memory.high` equivalent and no supported job-wide freeze, so the node reports `pause=UNSUPPORTED` on Windows. Commit-limit exhaustion fails allocations. The node records `memory_limit_hit` only after confirming its own attempt-job notification/peak or hard-limit peak evidence; a memory packet from a workload's nested job alone is insufficient (MR-18). `MEMORY_LIMIT` plus nonzero exit is an evidence-based normalization, not a claim of causation or allocation refusal; its detail states that boundary ([04](../architecture/04-execution.md) §7).

### Linux

*Heading amended 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md); formerly "Linux (including WSL2 guests)". A Linux node a user runs in a WSL2 distribution is an ordinary Linux node under this section.*

1. **Node unit.** The node runs as the systemd **user** unit `arcforges-node.service`, and holds no executions in its own cgroup. systemd kills the processes left in a unit's cgroup when the unit stops or restarts after a failure; keeping executions elsewhere means a node crash, update or `systemctl --user restart` never touches them (AD-0006 §2).
2. **Execution containers are transient systemd user units**, created through the user manager's D-Bus API (`org.freedesktop.systemd1.Manager.StartTransientUnit`, using the AOT-compatible `Tmds.DBus.Protocol`).
   - **Slice.** The root container is the slice `arcforges.slice`, installed as a unit file beside the node unit. The node sets its limits at runtime with `SetUnitProperties(runtime=true)`: `CPUQuota`, `MemoryHigh`, `MemoryMax` and `TasksMax` (values per 03 §5).
   - **Attempts.** Each attempt is a transient service `arcforges-a-<attempt_id>.service` in that slice, with:
     - `CPUWeight` (03 §5), plus an optional per-task `CPUQuota`;
     - `MemoryHigh`, `MemoryMax`, `OOMPolicy=stop` and an optional `MemorySwapMax`. After the kernel kills a process at the unit's `MemoryMax`, systemd stops the whole unit through its ordinary stop (`ExecStop`, then the stop signals within `TimeoutStopSec`), and the unit's result is `oom-kill`. No ArcForges unit sets `memory.oom.group`: its group kill also signals the user manager's spawn child while it still shares the manager's address space, and the kernel then kills the user manager itself (amended 2026-10-23, L-27; formerly `OOMPolicy=kill`);
     - `TasksMax`;
     - `KillMode=control-group` with `TimeoutStopSec` = the end-step budget (10 s) + `leftover_grace` (default 5 s) + 5 s; `exec-stop` kills the leftovers with SIGKILL after `leftover_grace`. This applies only to the stop that follows the root process's exit (04 §3; amended 2026-10-16), and to the stop systemd starts after an OOM kill, when the root may still be running and is then ended with the leftovers (04 §3; amended 2026-10-23, L-27);
     - `ExecStopPost=<app>/current/arcforges node exit-record --attempt <id>`;
     - `CollectMode=inactive`: a failed unit is kept until the node has recorded it from its properties (an OOM kill can skip `ExecStopPost`), then reset (amended 2026-10-16).
   - **Launch.**
     - The node passes the working directory and the resolved environment (`Environment=`); `exec-launch` keeps only the resolved names, so the result is exact whatever the user manager adds (amended 2026-10-16).
     - stdio is passed as file descriptors over D-Bus (`StandardInputFileDescriptor`, `StandardOutputFileDescriptor`, `StandardErrorFileDescriptor`).
     - The node's own limits are passed as `Limit*=` properties (`LimitCORE` and `LimitSTACK` with the node's soft and hard values; `LimitNOFILE` with the node's hard value and a soft value of min(1024, hard)) (amended 2026-10-16).
   - **Parent and exit record.**
     - The user manager is the parent of every execution, so executions never depend on the node process.
     - `ExecStopPost` runs in the unit's cgroup and receives `$EXIT_CODE`, `$EXIT_STATUS` and `$SERVICE_RESULT`. It writes `logs/<attempt>/exit.json` with the cgroup accounting (`cpu.stat`, `memory.peak`, `memory.events`, `io.stat`), so the record is durable even while the node is down (L-13).
   - **Control.**
     - **Pause:** `FreezeUnit` / `ThawUnit`.
     - **Graceful cancellation:** `KillUnit("all", <stop_signal>)`, default SIGTERM.
     - **Forced cancellation and limit stops:** `FreezeUnit`, SIGKILL to every process of the cgroup (the main process last), then a direct write of `0` to `cgroup.freeze` and `ThawUnit`. `KillUnit("all", SIGKILL)` is not used, because systemd then skips `ExecStop` and `ExecStopPost`, and the user manager's spawn of `ExecStop` into a frozen cgroup blocks the manager (systemd 257) or leaves the unit deactivating with its exit record pending (systemd 255) until the cgroup is thawed (L-24; amended 2026-10-16). Releasing a freeze is the only cgroup file the node writes.
     - **Limit changes:** `SetUnitProperties(runtime=true)`.
     - **Statistics:** read directly from the unit's cgroup files, which are readable.
     - **Completion:** observed through D-Bus `PropertiesChanged`/`JobRemoved` and `exit.json` (V-L03–V-L05).
3. **Minimum platform.** cgroup v2 unified hierarchy and systemd ≥ 247 with a user manager. Older or absent managers degrade per capability (03 §8).
4. **Without a user manager or controllers.** If no systemd user manager exists, or a controller is missing from its delegation, the node runs in `OBSERVE_ONLY` (or `PARTIAL` per missing controller).
   - Executions are then plain child processes, and their exit status is lost if the node restarts before they finish.
   - The node refuses tasks whose policy requires enforcement (R-RES-008).
   - Without lingering, a non-WSL user manager stops at logout, and with it every execution. This is documented, and `loginctl enable-linger` is offered as a user step.
5. **I/O.** `io` control is not delegated by default (L-06). I/O limits are an optional privileged feature (A-L02). Without it the node only observes I/O (`io.stat`, `io.pressure`).

### WSL2 model

**Items 1–3 superseded 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md)** (kept as history). There is no guest node, guest link, guest budget, shared queue or coordinated admission: a Windows node controls Windows workloads with job objects, and a Linux node, including one a user runs in a WSL2 distribution, controls Linux workloads with systemd and cgroups v2, each within its own budget. The successor of the accounting rule is item 4 below ([AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §2). The wire surfaces named below stay declared in v1 but are retired ([AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §3).

1. **Guest link.** The Windows **host node** and each managed distribution's **guest node** are separate authorities, linked by a **guest link**.
   - **Bridge.** The host launches `wsl.exe -d <distro> --exec <guest arcforges path> bridge wsl`, a long-lived child of the host node. The bridge relays one byte stream between its stdio and the guest node's Unix socket, and the host runs gRPC over it (AD-0004).
   - **Networking.** This works in NAT, mirrored and consomme networking modes alike.
   - **Distribution lifetime.** The bridge keeps the distribution alive while the host holds the link, so the user's `instanceIdleTimeout` (V-L07) needs no change. Whether the user manager stays up with only the bridge connected is verified by F-L01.
   - **Guest executions.** The guest node runs under the user manager (L-08), not under the bridge, and its executions are transient units of that user manager (Linux §2).
2. **Capacity and accounting.**
   - **Guest capacity** is what the VM exposes (`nproc` and MemTotal, bounded by `.wslconfig`).
   - **Host view:** the host counts the VM as one consumer through its VM worker process (vmmem/vmmemWSL; A-L01) and never sums guest-internal processes separately.
   - **Attribution:** guest-reported managed usage is attributed inside that consumer: `guest_other = max(0, vm_usage − guest_managed)`.
3. **Coordinated admission and enforcement** (03 §6).
   - **Admission.** While linked, a guest asks the host for a grant before admitting an attempt: a `GrantRequest` on the `GuestLinkService.OpenLink` stream, answered with `AnswerGrant`. One fair queue spans the host and its guests.
   - **Enforcement.** Demand is admitted, allocations are enforced. The host splits its enforceable CPU budget between its own root and the guest slice in proportion to demand, with positive floors on both sides, so the two always sum to `B_cpu`. Memory grants are never overcommitted. The guest's slice limits arrive by `GuestLinkService.SetGuestBudget` with a lease ([03](../architecture/03-resource-control.md) §6).
   - **Acknowledged allocations.** The guest applies each pushed allocation before answering, and the host reuses capacity the guest gives back only after that acknowledgement. A grant that raises the allocation is acknowledged before the attempt may start.
   - **Unlinked.** While the lease runs, the guest admits only within its last acknowledged allocation. After the lease lapses, it admits new attempts only within the standalone allocation, which is never larger than that acknowledged allocation (at most 25% of the host budget by default). It never lowers its slice limits below running work.
   - **The host keeps the guest's reserved allocation** throughout the outage: the last acknowledged allocation and any larger push not yet acknowledged, persisted before each push. An idle guest can resume and use its whole allocation at any moment, so measured usage never shrinks the reservation.
   - **Ending the reservation.** It ends only when the guest acknowledges a smaller allocation after reconnecting (having reported the allocation it applies and re-registered the attempts it admitted meanwhile), or when the host observes that the guest's distribution or the VM has stopped.
   - **Restarted distributions.** A guest that starts in a new boot of its distribution admits nothing until it links again. A marker in the distribution's own runtime directory detects that boot, because the kernel boot ID is shared by every distribution.
   - **Result.** Host and guest enforced allocations therefore stay within the host budget in force when the guest last acknowledged. If unmanaged load shrinks that budget during an outage, only host work is reduced. `GUEST_LINK_LOST` reports the outage and the reserved allocation (revised 2026-10-13 after the mechanism review: the earlier rule accounted the guest at the larger of its usage and the standalone allocation).
4. **The WSL VM and tasks that cross into it** (restated 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) §2; now part of R-RES-002). The Windows node observes the WSL VM like any other virtual machine: one consumer labelled `GUEST_VM`, part of unmanaged load in the budgets, never summed from guest-internal processes. A Windows task that runs `wsl.exe` (or any launcher into a VM) is flagged `crosses_vm_boundary`; the Linux processes it starts are outside the Windows job and are never presented as controlled.
   *Superseded 2026-10-21 by [AD-0018](AD-0018-native-platforms-without-wsl-integration.md) (kept as history):* "A Windows task that runs `wsl.exe` is flagged `crosses_vm_boundary`. Its Linux processes are outside the Windows job and are labelled unmanaged unless submitted to the guest node (R-RES-011)."

### Observation versus control

- **Observation:** the node samples every visible process (Windows: process snapshots plus per-process times and memory; Linux: `/proc` plus cgroup statistics).
- **Control:** applies only to processes the node launched or that the user explicitly adopted (same user; recorded; R-RES-013).
- **Bypass attribution:** heavy unmanaged processes are attributed to an agent session only through process ancestry from a registered agent process (AD-0007).

### Direction (roadmap; not release 1)

Amended 2026-10-19 by [AD-0017](AD-0017-delegated-execution-direction.md). Nothing above changes; release 1 confines no workload. The first item takes effect when the first confined backend row (EX-10, EX-11 or EX-22) is promoted.
- **Confined profiles will be P0 features when promoted.** Like the core features of the Process model, they will need no administrator or root rights at run time: the hand-built AppContainer brokered by the holder on Windows, the view chain inside the transient unit on Linux ([17](../architecture/17-delegated-execution.md) §5). Where a host needs a one-time privileged step for the full Linux view (the Ubuntu 24.04 AppArmor profile for bwrap), that step is optional; whether ArcForges offers it as an OS-prompted step under the next item is an owner decision ([17](../architecture/17-delegated-execution.md) §17, decision 4). Without it, Ubuntu 24.04 keeps the Landlock-only tier, which gives no boundary against compromised tools or AI-generated commands, only resource control plus guardrails ([17](../architecture/17-delegated-execution.md) §5.2).
- Restated, not new direction: **Optional privileged steps follow AD-0017's boundary 2, which is in force now** (AD-0017, principle 3; its journal entry from EX-08). This item restates it for the privileged steps a confined backend may offer (for example the Ubuntu AppArmor profile, [17](../architecture/17-delegated-execution.md) §17, decision 4). ArcForges never performs an OS-level change silently. An optional privileged step is either the owner's own action or, where [AD-0011](AD-0011-identity-and-login.md) §6 applies, an explicit OS prompt with a journal entry (EX-08) and exact removal. The optional privileged features designed above, the machine-wide Windows service mode (AR-16) and Linux I/O control (A-L02), stay as designed here. At run time ArcForges never elevates.
- **Owner placement** (added 2026-10-19; effective when RM-18 is promoted). Beside managed placement (an attempt job nested in the root job; a transient unit in `arcforges.slice`, Windows §2 and Linux §2 above), owner placement will be the same container beside the root, for the owner's own interactive applications: on Windows a top-level job with the attempts' name pattern, held by the holder, never kill-on-close, with no UI limits and no lethal limit at assignment; on Linux an XDG-named application unit in `app.slice`, or the desktop's own unit adopted in place. It is proposed to be set per application by a local HUMAN only, a SCRIPT or AGENT launch of such an application running in managed placement or being refused (a recommendation; the owner's decision 6, [18](../architecture/18-application-workload-control.md) §19, is pending and is answered before RM-18 is promoted). Owner-placed containers count in unmanaged load `U`, never reach the pressure ladder or the interactive guard (except that a cooperative grant the application asked for can be withdrawn back to the owner's own values), and their limits apply exactly as the owner typed them ([18](../architecture/18-application-workload-control.md) §5, §8; [03](../architecture/03-resource-control.md) §10). Adoption gains an optional placement field whose default keeps root-first adoption; a process adopted under the root stays there until it exits. It is a second placement of the same job and unit mechanisms, not a third container type and not a concept.

## Consequences

- No step of core functionality needs elevation, and every enforcement claim is backed by a real test in its environment. Each claim holds against accidental and over-privileged workloads; against workloads that target ArcForges' objects it is a guardrail (amended 2026-10-19).
- Windows pause and memory soft-limits are honestly unavailable.
- Each Windows attempt costs one holder process (target ≤ 10 MB private, [15](../architecture/15-performance-targets.md) §2; amended 2026-10-16). That is the price of surviving node restarts.
- Optional privileged features are designed but do not gate development-stage completion.
